# Workspace caveats

**Load this when:** adding or upgrading dependencies, editing `package.json`, `pnpm-workspace.yaml`, `nx.json`, `tsconfig*.json` or ESLint/Prettier config, generating a new app or lib, changing Nx tags, or when `pnpm verify` and CI disagree.

- **`pnpm verify` is CI.** It runs `prettier --check`, `nx run-many -t lint typecheck test build` for every project, then `nx run-many -t bench` on its own (so the timing gate never shares the machine with other tasks; see the simulation caveats), and `node tools/check-version-sync.mjs`. If you add a CI step, add it to `verify` in the same PR (and vice versa). Lesson from jansky-observe: CI ran a `ruff format --check` that local verify didn't, and a release went out broken.
- **CI is one reusable workflow on three OSes.** `.github/workflows/ci.yml` (`on: workflow_call`) runs `pnpm verify`, installs Chromium, then `pnpm e2e` and `pnpm e2e:desktop` (under `xvfb-run` on Linux) on `ubuntu-latest`, `macos-latest` and `windows-latest`, with `fail-fast: false` and `dist/.playwright` uploaded on failure. `pr.yml` (with `cancel-in-progress`) and `main.yml` (without) only call it, so a PR runs exactly what `main` runs; edit steps in `ci.yml`, never in a caller. Check names are `ci / verify + e2e (ubuntu|macos|windows)` (before this they were `verify + e2e (ubuntu)` on PRs). `release.yml` is separate: it packages and smoke-tests installers. Lint workflow changes with [actionlint](https://github.com/rhysd/actionlint) (`go install github.com/rhysd/actionlint/cmd/actionlint@latest`, then `actionlint` at the repo root); it is not part of `verify` because it isn't a Node tool and checks only CI config.
- **Actions are pinned to full commit SHAs**, with the release tag as a comment (`actions/checkout@3d3c42e… # v7.0.1`), in `ci.yml`, `release.yml` and `.github/actions/setup/action.yml`. Tags can be moved, and `release.yml` holds a `contents: write` token and runs a third-party action (`pnpm/action-setup`), so only a SHA fixes what runs. Floating majors also lag: in October 2026 `pnpm/action-setup@v6` still pointed at v6.0.10, not v6.1.0. **No Dependabot or Renovate is set up, so updates are manual.** Pick the release, read its notes back to the version you're on, resolve the tag to its commit with `gh api repos/<owner>/<repo>/commits/<tag> --jq .sha` (this dereferences annotated tags; a tag's own object SHA won't work), update every `uses:` and its comment together, and run actionlint. A "Node.js N is deprecated" warning in the CI log means it's time. Never pin to a tag object SHA or to a branch.
- **Action behaviour this repo relies on** (checked at the v4 → Node 24 bump, from each action's release notes):
  - `pnpm/action-setup` (v6) has no `version` input: it reads `packageManager` from `package.json` and installs exactly that pnpm (it bootstraps, then self-updates to the pinned version). CI doesn't use corepack. Its own `cache` input defaults to `false`; leave it off, or the store is cached twice. For pnpm 11+ there is also a successor, `pnpm/setup`, which installs Node too, but from `devEngines.runtime`, not `.nvmrc`. It isn't used here.
  - `actions/setup-node` (v5+) can cache by itself, but since v6 only for npm. pnpm caching is the explicit `cache: pnpm`, which needs pnpm on `PATH` first, so `pnpm/action-setup` must stay the first step. `package-manager-cache: false` is set anyway, so a future default can't add a second cache. The composite takes `cache: 'false'` (release builds).
  - `actions/checkout` (v6+) stores persisted credentials in a file under `$RUNNER_TEMP`, not `.git/config`, but still persists them by default. Every checkout here sets `persist-credentials: false`. A future step that pushes with git has to opt back in on its own checkout. v7 also refuses to check out fork PRs under `pull_request_target`/`workflow_run`; this repo uses neither.
  - `actions/upload-artifact` (v4+): artifacts are immutable and names must be unique within a run, including across re-run attempts, so names end in `-${{ github.run_id }}-${{ github.run_attempt }}`. **Hidden files are skipped by default, and "hidden" includes everything inside a dot-directory.** Playwright writes to `dist/.playwright`, so both uploads set `include-hidden-files: true`. Without it the failure artifacts were silently empty (`No files were found with the provided path`).
- **Format failures:** run `pnpm format` (Prettier `--write`), then re-run `pnpm verify`. Prettier checks Markdown too, so docs-only PRs can fail CI.
- **TypeScript is pinned to 6.0.x.** Angular 22's compiler requires `>=6.0 <6.1`. TypeScript 7 (the Go-native compiler, `tsgo`) is **not** usable for Angular projects; don't upgrade or add a second compiler without an ADR.
- **No `baseUrl`.** It is deprecated in TypeScript 6. `tsconfig.base.json` declares `paths` with paths relative to the config file and no `baseUrl`.
- **Integrated paths style, not project references.** `@nx/angular` refuses the TypeScript project-references ("solution") setup, so libraries are resolved through `tsconfig.base.json` `paths` (`@controls/units`, `@controls/ipc-contract`, `@controls/renderer`, `@controls/platform-api`, …). Generators must be run in that style.
- **Vitest is 4.1.** Angular 22.0's Vitest integration required `vitest@^4`. Since 22.2 it also accepts `^5`, but 4.1 is kept through P1 by choice ([ADR 0001](../decisions/0001-stack.md)).
- **pnpm 11 install scripts need `allowBuilds`.** Any dependency with a `postinstall`/build script (Electron, esbuild, `@swc/core`, nx, …) must be listed under `allowBuilds` in `pnpm-workspace.yaml`, or its script is skipped silently and things break later (for example a missing Electron binary).
- **pnpm 11 enforces a minimum release age** (24 hours by default). A version published very recently can refuse to install, and `pnpm install` may instead write a `minimumReleaseAgeExclude` list into `pnpm-workspace.yaml`. Never commit those exclusions: pin the previous version, or wait until the release has aged in (P1 deps PR: Nx 24.0.2 was deferred this way, then landed in its own PR a day later).
- **Node 24 LTS** is pinned in `.nvmrc`; pnpm via `packageManager` (`pnpm@11.28.8`), picked up by `corepack enable`.
- **Nx tags** are `type:app`, `type:feature`, `type:ui`, `type:domain`, `type:rendering`, `type:platform`, `type:contract`, `type:e2e`, since F1.9 `type:content`, and since the P2 kickoff `type:worker`. Every new project needs exactly one `type:*` tag, or the boundary rule can't place it. The constraints are in the root `eslint.config.mjs`; see the [architecture overview](../architecture/overview.md#module-boundaries).
- **`type:domain` libs stay framework-free and deterministic**, because the same code runs in `sim-cli` (plain Node), the renderer and (from P2) the sim worker. Four mechanisms enforce it; each was proven to fire when it landed:
  - **Banned npm imports** (`bannedExternalImports` on `type:domain` in the root `eslint.config.mjs`): `@angular/*`, `@angular-devkit/*`, `zone.js`, `rxjs`, `electron`, `electron-updater`, `three`, `three-mesh-bvh`, CodeMirror, dockview, `jsdom`, Playwright. Nx tag constraints alone only cover workspace libs. Nx matches against the project graph, so a pattern only fires once the package is installed; listing planned UI packages early is deliberate.
  - **No DOM, no ambient Node types:** every domain lib's `tsconfig.json` extends `libs/domain/tsconfig.domain.json` (`lib: ["es2022"]`, `types: []`), so `window`, `document`, `performance`, `process` and `Buffer` fail typecheck. Spec configs add `node` and Vitest types back. Note that `console`, `setTimeout` and `TextEncoder` are not ES-lib globals either; if domain code genuinely needs a cross-runtime global, declare that one narrowly rather than adding `dom` or `node`. Nx generators write `types: ["node"]` into `tsconfig.lib.json`: delete it.
  - **No Node built-ins in domain source** (`no-restricted-imports`, `fs`, `node:*`, …). Specs may use them (for example `node:fs` to read fixtures).
  - **Determinism lint**, scoped by path to `libs/domain/**` (and `libs/sim-worker`, below) (an absolute `basePath`, because each project's ESLint config resolves globs from its own directory), **including specs**: `Math.random`, `Date.now`, `new Date()`/`Date()`, the `performance` and `crypto` globals and their `globalThis.*` forms. Use the seeded PRNG and the sim tick (F1.2). A domain test that reads the clock is a flaky test; fast-check supplies seeds. Tooling configs (`*.config.*`, `vitest.domain.mts`) are exempt. **Domain libs must live under `libs/domain/`** or the path-scoped rules miss them.
- **P2 sim libs (kickoff step 6):** `libs/domain/sim-core` (`@controls/sim-core`), `libs/domain/sim-protocol` (`@controls/sim-protocol`) and `libs/domain/catalog` (`@controls/catalog`) are ordinary `type:domain` libs, set up exactly like `units` (copy its `project.json`, `tsconfig*.json`, `eslint.config.mjs` and `vitest.config.mts`). They shipped empty, each with one placeholder constant (`src/lib/package.ts`) and a test so the coverage gate has something to measure; delete the placeholder when real code lands (`catalog` has real code since the world v2 kickoff PRs: the device catalogue, [save-format caveats](save-format.md#the-device-catalogue-p2-kickoff-catalogue-v1); `sim-core` holds `SIM_ENGINE_VERSION` until F2.1). New domain aliases are picked up by the `sim-cli` script loader automatically, and `apps/sim-cli/src/cli.spec.ts` lists them, so update that list too.
- **`type:worker` (`libs/sim-worker`, `@controls/sim-worker`, also `scope:game`)** is the sim worker: the module Web Worker entry and its pacing (F2.3b). It may depend only on `type:domain` libs, with domain's banned npm imports. No other lib's constraint lists `type:worker`, so only apps can import it: the renderer and features read snapshot types from `@controls/sim-protocol` (`type:domain`), never from the worker. A `SimHost` in a feature therefore can't name the worker module; the app has to supply it (decided in F2.3b, ADR 0011). Its `tsconfig.json` uses `lib: ["es2022", "webworker"]` and `types: []` (no DOM, no Node), it gets the no-Node-built-ins rule for source, and its `vitest.config.mts` reuses `defineDomainVitestConfig`, so it has the 90 % gate too. It lives outside `libs/domain/`, so it needs its own entries in the path-scoped ESLint blocks (`simWorkerDir`).
- **The worker's determinism exemption is `libs/sim-worker/src/lib/pacing/**` only.** Pacing turns wall time into integer tick targets; wall-clock readings must never reach `sim-core`, a snapshot or anything hashed. Everything else in the worker, specs included, has the domain determinism lint. Likewise `apps/sim-cli/src/bench/clock.ts` is the only sim-cli file allowed the wall clock (for `sim bench`).
- **D6 lint: deterministic maths in `sim-core` source** (decision D6 in `plans/phase-2-circuit-engine.md`; ADR 0014, to be written in F2.1). `no-restricted-properties` bans `Math.exp`, `expm1`, `log`, `log1p`, `log2`, `log10`, `pow`, `sin`, `cos`, `tan`, `asin`, `acos`, `atan`, `atan2`, `sinh`, `cosh`, `tanh`, `asinh`, `acosh`, `atanh`, `hypot` and `cbrt` (including destructuring and `Math['exp']`), and `no-restricted-syntax` bans `**` and `**=`. ECMAScript leaves those functions "implementation-approximated", so Node's V8 and Electron's Chromium V8 may differ in the last bit; use `+ - * /`, `Math.sqrt` (correctly rounded), `Math.fround`, `abs`, `min`/`max`, rounding, and sim-core's own `dmath`. Specs are exempt (they run only in Node and may compare `dmath` with `Math`). **Flat config replaces a rule's options wholesale**, so the sim-core block repeats the determinism entries (`simCoreRules` merges them) and must stay after the determinism block; a test checks `Math.random` still fails in sim-core source.
- **Every path-scoped rule is proven to fire.** `apps/sim-cli/src/lint-boundary.spec.ts` (module boundaries, including `type:worker` both ways) and `apps/sim-cli/src/lint-determinism.spec.ts` (determinism lint per path and exemption, D6, Node built-ins) lint probe files with the real config. They live in `sim-cli` because its `test` target has the root ESLint config, `tsconfig.base.json` and every `project.json` as inputs; a lint test in another project would be replayed from cache after a rule change. A new rule or exemption gets a probe there.
- **The `bench` target** (`apps/sim-cli`, P2) runs `node dist/apps/sim-cli/main.mjs bench` after `build`, uncached, as its own step of `pnpm verify` after the parallel run, with `"parallelism": false`. CI prints its report with `tools/print-bench-report.mjs` (the gated ratio first). It runs the bundle rather than a Vitest spec because domain tests always run with coverage instrumentation, which distorts timings. Budgets are never loosened or skipped per OS to get CI green; raise it with the user (plan P2 risks). Details in [scripting caveats](scripting.md).
- **Domain coverage gate:** every domain lib's `vitest.config.mts` is `defineDomainVitestConfig(import.meta.dirname, '<name>')` from `libs/domain/vitest.domain.mts`: Node environment, coverage always on, 90 % lines/statements/functions/branches over `src/**/*.ts` (plan §8). It runs inside `test`, so it is part of `pnpm verify`. Don't pad coverage with export-only tests; untested code is the signal. The atomised `test-ci--<file>` targets (unused, not in `verify`) run one spec at a time and will trip the gate.
- **`libs/domain/tsconfig.domain.json` and `libs/domain/vitest.domain.mts` are in `sharedGlobals`** (`nx.json`), so editing them invalidates the cache. Any new shared config file outside a project root needs the same, or Nx will replay stale results.
- **`scope:headless`** (`apps/sim-cli`, F1.6) may depend only on `type:domain` libs and gets the same banned npm imports. Nx applies every matching constraint, so it narrows the app's `type:app` wildcard; `scope:desktop` is the naming precedent. `apps/sim-cli/src/lint-boundary.spec.ts` lints a probe file with the real config, so loosening the rule fails `pnpm verify`. npm packages that aren't banned (esbuild, Node built-ins) stay allowed in the app itself. The determinism lint also covers `apps/sim-cli` (see [scripting caveats](scripting.md)).
- **fast-check** (MIT, dev only) is the property-testing library for domain tests. Like other test tooling it has no `THIRD_PARTY_NOTICES.md` row.
- **`apps/desktop/package.json` is not a workspace package** (`'!apps/desktop'` in `pnpm-workspace.yaml`): it is the template for the packaged app's `package.json` and shares the root's name.
- **Playwright browsers are not in `node_modules`**: run `pnpm exec playwright install chromium` once (CI uses `--with-deps`). The web e2e project is Chromium-only on purpose, since Electron is Chromium.
- **`@nx/web:file-server` (`serve-static`) ignores the `headers` option**, so it isn't cross-origin isolated. The CI web e2e serves `game:serve:production` through the Angular dev server instead.
- **E2E projects are tagged `type:e2e`** and may not import workspace libs (`onlyDependOnLibsWithTags: []`). Both e2e projects have the tag and a `typecheck` target.
- **Nx generators add other-agent config** (`.cursor`, `.gemini`, `AGENTS.md`, …) and an Nx block in `CLAUDE.md`. Delete them after generating; don't run `nx configure-ai-agents`.
- **Angular selector prefix is `ctl`.**
- **Angular libs** (`type:ui`, `type:feature`) are generated with `@nx/angular:library --unitTestRunner=none` (the `vitest-angular` runner refuses non-buildable libs), then given a `test` target on `@angular/build:unit-test` with `buildTarget: game:build:development` and a `typecheck` target. Copy them from `libs/ui/project.json`. The generator also adds `@nx/angular:*` defaults to `nx.json`; revert that. Details in [UI caveats](ui.md).
- Run Nx through pnpm (`pnpm nx …`, `pnpm exec nx …`), never a globally installed `nx`.
- **`content/` is an Nx project (`content`, tag `type:content`, F1.9)** so apps can bundle data through the `@controls/content/*` path alias (`import workshop from '@controls/content/levels/workshop.json'`). A relative import of `content/` fails `@nx/enforce-module-boundaries` ("External resources cannot be imported using a relative or absolute path"). `type:content` may import nothing. `apps/game` sets `resolveJsonModule`. Specs and `sim-cli` read level files from disk instead, so `content/**/*` is in `sharedGlobals` (`nx.json`): editing a level re-runs every cached target that might read it.
