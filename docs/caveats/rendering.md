# Rendering caveats

**Load this when:** working in `libs/rendering/renderer` (scene, world sync, cameras, picking, selection, the placement ghost and gestures, overlays, the frame loop), the snap maths in `libs/domain/world-model/src/lib/snap`, or the Angular viewport host, or adding a Three.js-side dependency. Background: [rendering architecture](../architecture/rendering.md), plan §4.9. WebGPU/WebGL2 and headless-browser notes are in the [Electron caveats](electron.md).

- **The renderer draws the world; it never owns or mutates it.** Hover, selection, the ghost, mode and camera pose are view state. Gestures leave the controller as `ViewportIntent`s (`place`, `move`, `cancelPlacement`) and the `Viewport` component executes them through `Session.exec`. Never give the renderer a `Session` or an `exec` callback. Selection is not saved and not logged; a Command that acts on it takes the entity id as an argument (the Delete binding reads `selection.entityId`).
- **Two layers: `ViewportController` (no GPU) and `ViewportRenderer` (GPU shell).** All scene, camera, input and picking logic sits in the controller so it can be unit-tested in Node with fake DOM targets (`viewport-controller.spec.ts`). Don't put logic in `ViewportRenderer` or the Angular component; it can't be tested there.
- **Pure modules are lint-fenced.** `cameras/camera-math`, `input/input-actions`, `picking/selection` and `stats/frame-timer` may not import `three`, `three-mesh-bvh`, the viewport or the picker, and may not touch `Math.random`, `Date.now`, `performance`, `window` or `document` (`libs/rendering/renderer/eslint.config.mjs`). This keeps them GPU-free and deterministic.
- **Snap and placement maths live in `@controls/world-model` (`snap/`), not the renderer** (moved in F1.7), so scripts and `sim-cli` snap identically to the mouse. Domain rules apply there: 90 % coverage and the determinism lint. The renderer only turns a ray hit into integer mm and calls `placeOnTargets`; put any new placement rule in `world-model`, or the mouse and scripts will disagree.
- **Snap inputs and outputs are integer millimetres, anchored at the footprint's lower-left corner.** Centres of odd-sized footprints would be half-millimetres, so the anchor is the min corner. Convert a raycast hit with `metresToMm` (rounds half away from zero, never `-0`) before calling `snap()`; it throws on non-integers. A device centred on a DIN rail sits at `v = -floor(h / 2)`, so odd heights are biased 0.5 mm down. That's deliberate and deterministic.
- **Stud positions are `round(first + i × 406.4)`**, never a running sum of a rounded 406 mm step (which drifts 5 mm over 12 studs). Keep published values exact in `snap/constants.ts` and round once at the end.
- **Every snap constant has a `source`, and `kind: 'game-design'` values say so in the text** (realism charter, plan §3). A spec checks this. `electrical-realism-reviewer` re-checks them in P2.
- **Surface frames are axis-aligned in P1** (`normal: '+x' | '-x' | '+z' | '-z'`, `u = up × normal`). A mounted entity's orientation is the ADR 0007 triple; `orientationForNormal` maps each normal to a yaw quarter-turn (`+z` 0, `+x` 90 000, `-z` 180 000, `-x` 270 000 mdeg). Don't invent a second rotation type.
- **An entity's `positionMm` is the snap anchor:** the footprint's lower-left corner on the mounting face. Prop geometry is built with its origin at its min corner and spans +x (width), +y (height), +z (depth). Change one side and the other must follow, or placed props float off their snap point.
- **Scene units are metres and world units are integer mm and millidegrees.** Convert only with `mm()` / `metresToMm()` / `mdegToRadians()` from `@controls/units`, and only at draw time. Euler order `YXZ` is ADR 0007's intrinsic yaw, pitch, roll.
- **Picking is two-level BVH, never a whole-scene raycast.** An `ObjectBVH` over the selectable roots narrows the ray, then each candidate mesh raycasts through its geometry's `MeshBVH` (`acceleratedRaycast`). At 500 synthetic devices: about 2.4 µs per pick and 28 ms to build (Node, F1.7).
  - BVHs are built with `{ indirect: true }`, so the geometry's index buffer, already uploaded to the GPU, is never reordered.
  - `Mesh.prototype.raycast` is **not** patched globally. Only registered meshes get `acceleratedRaycast` as an own property, and `Picker.dispose()` deletes it.
  - `ObjectBVH` can't be built over zero objects (it takes `log2` of the count), so the picker skips it when empty.
  - `ObjectBVH.raycast` allocates a few small objects per call. Hover raycasts therefore run at most once per frame, and only when the pointer, the camera or the walk pose changed (`hoverDirty`).
  - After moving selectables, call `Picker.refit()`; after adding or removing them, call `setRoots()`. World sync drives both. `setRoots()` also drops the BVH and the own `raycast` of any mesh no longer under a root, so removing entities returns memory to baseline.
  - **Placement aims with a second picker over snap surfaces only.** The main picker returns the nearest hit (`firstHitOnly`), so a prop in front of the plate would block the ghost. Both pickers share geometry BVHs: whichever builds one owns it, and both are disposed.
- **Selectables are marked with `userData.selectable`** (JSON-plain `SelectableInfo`), so the scene-graph snapshot shows them. Nested selectables belong to their outermost marked ancestor. Keyboard cycling order is code-unit id order (`<`), never `localeCompare`, so it's the same on every machine.
- **Input actions are not Commands.** WASD, mouse look, selection cycling and the placement keys (`commitPlacement` Enter, `moveSelection` M) go through `input/input-actions.ts` (a rebindable `KeyboardEvent.code` map), so per-frame input never enters the replay log (ADR 0006); F1.4 feeds user bindings in via `setBindings()`. Since F1.7, switching mode (`V`) and focusing (`F`) are the `view.mode` / `view.focus` Commands, bound by the keybinding service; the renderer must leave those keys alone so they reach it. Chords with Ctrl, Meta or Alt are ignored here because they belong to Commands.
- **Gestures commit once.** Only a click, `Enter`, or releasing a drag produces an intent, and at most one. Pointer moves only re-aim the ghost (at most one surface pick per frame, through `hoverDirty`). A drop at the entity's current position, or on no valid snap, produces nothing. A move keeps the entity's orientation, so only same-facing targets count: one `entity.move`, never a rotate as well.
- **Our pointer listeners are registered before `OrbitControls`, in the capture phase.** A press on an entity sets `orbit.enabled = false` before OrbitControls' own `pointerdown` runs, so that drag moves the entity instead of orbiting; `pointerup` re-enables it. Constructing OrbitControls first breaks drag-to-move.
- **The ghost borrows recipe geometry and gives it back.** It never keeps a pointer to a released geometry (it swaps in its own empty placeholder), so it has no "disposed twice" or "rendered after dispose" path. Prop recipes are reference-counted across entities and the ghost; `recipeCount` reaching 0 is the baseline check.
- **Keyboard input listens on the canvas only.** The canvas has `tabindex="0"` and is focused on pointer-down, so typing in a text field never moves the camera. Held keys are cleared on canvas or window `blur`, otherwise a key released elsewhere stays stuck down.
- **Pointer lock:** `requestPointerLock()` must run inside a user gesture (a click in walk mode). The browser releases it on Esc by itself; we only listen for `pointerlockchange`. Chromium returns a promise that rejects when the lock is denied, so the rejection is swallowed. **E2E never asserts pointer lock** (flaky headless). Drive modes through the `?e2e=1` hook and assert on the host's `data-*` attributes.
- **The `?e2e=1` hook** (`window.__controlsViewport`) exposes the `ViewportRenderer` API (`setMode`, `focus`, `select`, `selectNext`, `pickAt`, `projectMm`, `cameraPositionMm`, `stats`, …). It is view state only and can't touch the world. It's gated by the query param, not by dev mode, because CI runs E2E against the production build. E2E aims the mouse with `projectMm` (integer-mm world point → canvas pixels) and lets snapping absorb the rounding.
- **E2E must wait for placement to be armed before clicking.** Pressing a tool-belt key arms placement through an Angular effect, a tick later. Wait for `data-placement-ref` to name the expected prop (`data-placement-valid` may still be `true` from the previous prop), or the click can place the wrong prop or select instead.
- **OrbitControls in work mode:** the pan limit is `cursor` + `maxTargetRadius` (the focus sphere), and orbit is clamped to ±75° azimuth and ±60° elevation around the face normal. Damping is switched off for the `update()` that applies a new focus, or momentum from the old target carries over. A press and release within 4 px (`CLICK_SLOP_PX`) is a click (select); anything more is an orbit drag.
- **Camera rotation order is `YXZ`** (yaw, then pitch) for walk mode. `OrbitControls` writes the quaternion directly, so switching modes is safe.
- **Disposal** goes through a LIFO `Disposer`. The controller registers the scene first, so it's disposed last, after the overlays and BVHs that reference it. `viewport-controller.spec.ts` proves that after `dispose()` no listeners are left on the canvas, document or window, every geometry and material is disposed exactly once, no BVH or own `raycast` remains (overlays keep their deliberate no-op `raycast`), and pointer lock is released; a second test does the same with world entities and an armed ghost. `WorldSync` and the ghost take their meshes out of the scene before `disposeScene` runs, because their geometry belongs to the shared recipes, not the scene: a recipe disposed by both would fail the "exactly once" check. Any new resource owner must register with the disposer and be added to those tests.
- **Frame-time HUD:** dev builds, or `?hud` in any build. It shows the mean and worst frame per 500 ms window (not an EMA: the first frame includes shader compilation and would skew an average for seconds). Calling `stats()` from the hook also starts a new window.
- **Headless frame times aren't representative.** Software WebGL2 (SwiftShader) at 1920×1080 rendered the bare panel at about 3 fps in F1.7 part 1, while WebGPU-on-SwiftShader-Vulkan held 60 fps. With 500 props (258 draw calls after culling) it flips: WebGL2 holds 60 fps and WebGPU-on-SwiftShader drops to about 3.8 fps, because each WebGPU draw is expensive on the CPU. The same 500 props hold 60 fps on both backends on a real GPU (RX 7600). Don't tune against headless numbers; measure the 500-device budget on real integrated GPUs, and consider instancing repeated props if WebGPU per-draw cost shows up there too.
- **Run E2E against your own server when other worktrees are active.** `playwright.config.mts` reuses whatever is listening on port 4200 (`reuseExistingServer`), which may be another checkout's build. Start `nx run game:serve:development --port <free>` and point a config with `webServer` unset and `baseURL` set at it. Under heavy machine load, "waiting for element to be stable" timeouts are load, not regressions: rerun with `--workers=1`.
