# Rendering caveats

**Load this when:** working in `libs/rendering/renderer` (scene, world sync, cameras, picking, selection, the placement ghost and gestures, overlays, the frame loop), the snap maths in `libs/domain/world-model/src/lib/snap`, or the Angular viewport host, or adding a Three.js-side dependency. Background: [rendering architecture](../architecture/rendering.md), plan §4.9. WebGPU/WebGL2 and headless-browser notes are in the [Electron caveats](electron.md).

- **The renderer draws the world; it never owns or mutates it.** Hover, selection, the ghost, mode and camera pose are view state. Gestures leave the controller as `ViewportIntent`s (`place`, `move`, `cancelPlacement`) and the `Viewport` component executes them through `Session.exec`. Never give the renderer a `Session` or an `exec` callback. Selection is not saved and not logged; a Command that acts on it takes the entity id as an argument (the Delete binding reads `selection.entityId`).
- **Two layers: `ViewportController` (no GPU) and `ViewportRenderer` (GPU shell).** All scene, camera, input and picking logic sits in the controller so it can be unit-tested in Node with fake DOM targets (`viewport-controller.spec.ts`). Don't put logic in `ViewportRenderer` or the Angular component; it can't be tested there.
- **Pure modules are lint-fenced.** `cameras/camera-math`, `input/input-actions`, `picking/selection`, `stats/frame-timer`, `sim/display-curve` and `sim/lamp-display` may not import `three`, `three-mesh-bvh`, the viewport or the picker, and may not touch `Math.random`, `Date.now`, `performance`, `window` or `document` (`libs/rendering/renderer/eslint.config.mjs`). This keeps them GPU-free and deterministic.
- **Snap and placement maths live in `@controls/world-model` (`snap/`), not the renderer** (moved in F1.7), so scripts and `sim-cli` snap identically to the mouse. Domain rules apply there: 90 % coverage and the determinism lint. The renderer only turns a ray hit into integer mm and calls `placeOnTargets`; put any new placement rule in `world-model`, or the mouse and scripts will disagree.
- **Snap inputs and outputs are integer millimetres, anchored at the footprint's lower-left corner.** Centres of odd-sized footprints would be half-millimetres, so the anchor is the min corner. Convert a raycast hit with `metresToMm` (rounds half away from zero, never `-0`) before calling `snap()`; it throws on non-integers. A device centred on a DIN rail sits at `v = -floor(h / 2)`, so odd heights are biased 0.5 mm down. That's deliberate and deterministic.
- **Stud positions are `round(first + i × 406.4)`**, never a running sum of a rounded 406 mm step (which drifts 5 mm over 12 studs). Keep published values exact in `snap/constants.ts` and round once at the end.
- **Every snap constant has a `source`, and `kind: 'game-design'` values say so in the text** (realism charter, plan §3). A spec checks this. `electrical-realism-reviewer` re-checks them in P2.
- **Surface frames are axis-aligned in P1** (`normal: '+x' | '-x' | '+z' | '-z'`, `u = up × normal`). A mounted entity's orientation is the ADR 0007 triple; `orientationForNormal` maps each normal to a yaw quarter-turn (`+z` 0, `+x` 90 000, `-z` 180 000, `-x` 270 000 mdeg). Don't invent a second rotation type.
- **An entity's `positionMm` is the snap anchor:** the footprint's lower-left corner on the mounting face. Prop geometry is built with its origin at its min corner and spans +x (width), +y (height), +z (depth). Change one side and the other must follow, or placed props float off their snap point.
- **Scene units are metres and world units are integer mm and millidegrees.** Convert only with `mm()` / `metresToMm()` / `mdegToRadians()` from `@controls/units`, and only at draw time. Euler order `YXZ` is ADR 0007's intrinsic yaw, pitch, roll.
- **Picking is two-level BVH, never a whole-scene raycast.** An `ObjectBVH` over the selectable roots narrows the ray, then each candidate mesh raycasts through its geometry's `MeshBVH` (`acceleratedRaycast`). At 500 synthetic devices: about 2.4 µs per pick and 28 ms to build (Node, F1.7).
  - BVHs are built with `{ indirect: true }`, so the geometry's index buffer, already uploaded to the GPU, is never reordered.
  - `Mesh.prototype.raycast` is **not** patched globally. Only registered meshes get `acceleratedRaycast` as an own property, and `Picker.dispose()` deletes it.
  - `ObjectBVH` can't be built over zero objects (it takes `log2` of the count), so the picker skips it when empty.
  - `ObjectBVH.raycast` allocates a few small objects per call. Hover raycasts therefore run at most once per frame, and only when the pointer, the camera or the walk pose changed (`hoverDirty`).
  - After moving selectables, call `Picker.refit()`; after adding or removing them, call `setRoots()`. World sync drives both. `setRoots()` also drops the BVH and the own `raycast` of any mesh no longer under a root, so removing entities returns memory to baseline.
  - **Placement aims with a second picker over snap surfaces only.** The main picker returns the nearest hit (`firstHitOnly`), so a prop in front of the plate would block the ghost. Both pickers share geometry BVHs: whichever builds one owns it, and both are disposed.
- **Selectables are marked with `userData.selectable`** (JSON-plain `SelectableInfo`), so the scene-graph snapshot shows them. Nested selectables belong to their outermost marked ancestor. Keyboard cycling order is code-unit id order (`<`), never `localeCompare`, so it's the same on every machine.
- **Input actions are not Commands.** WASD, mouse look, selection cycling and the placement keys (`commitPlacement` Enter, `moveSelection` M) go through `input/input-actions.ts` (a rebindable `KeyboardEvent.code` map), so per-frame input never enters the replay log (ADR 0006); F1.4 feeds user bindings in via `setBindings()`. Since F1.7, switching mode (`V`) and focusing (`F`) are the `view.mode` / `view.focus` Commands, bound by the keybinding service; the renderer must leave those keys alone so they reach it. Chords with Ctrl, Meta or Alt are ignored here because they belong to Commands.
- **Gestures commit once.** Only a click, `Enter`, or releasing a drag produces an intent, and at most one. Pointer moves only re-aim the ghost (at most one surface pick per frame, through `hoverDirty`). A drop at the entity's current position, or on no valid snap, produces nothing. A move keeps the entity's orientation, so only same-facing targets count: one `entity.move`, never a rotate as well.
- **Our pointer listeners are registered before `OrbitControls`, in the capture phase.** A press on an entity sets `orbit.enabled = false` before OrbitControls' own `pointerdown` runs, so that drag moves the entity instead of orbiting; `pointerup` re-enables it. Constructing OrbitControls first breaks drag-to-move.
- **The ghost borrows recipe geometry and gives it back.** It never keeps a pointer to a released geometry (it swaps in its own empty placeholder), so it has no "disposed twice" or "rendered after dispose" path. Prop recipes are reference-counted across entities and the ghost; `recipeCount` reaching 0 is the baseline check.
- **Keyboard input listens on the canvas only.** The canvas has `tabindex="0"` and is focused on pointer-down, so typing in a text field never moves the camera. Held keys are cleared on canvas or window `blur`, otherwise a key released elsewhere stays stuck down.
- **Pointer lock:** `requestPointerLock()` must run inside a user gesture (a click in walk mode). The browser releases it on Esc by itself; we only listen for `pointerlockchange`. Chromium returns a promise that rejects when the lock is denied, so the rejection is swallowed. **E2E never asserts pointer lock** (flaky headless). Drive modes through the `?e2e=1` hook and assert on the host's `data-*` attributes.
- **The `?e2e=1` hook** (`window.__controlsViewport`) exposes the `ViewportRenderer` API (`setMode`, `focus`, `select`, `selectNext`, `pickAt`, `projectMm`, `cameraPositionMm`, `stats`, …). It is view state only and can't touch the world. It's gated by the query param, not by dev mode, because CI runs E2E against the production build. E2E aims the mouse with `projectMm` (integer-mm world point → canvas pixels) and lets snapping absorb the rounding.
- **E2E must wait for placement to be armed before clicking.** Pressing a tool-belt key arms placement through an Angular effect, a tick later. Wait for `data-placement-ref` to name the expected prop (`data-placement-valid` may still be `true` from the previous prop), or the click can place the wrong prop or select instead.
- **OrbitControls in work mode:** the pan limit is `cursor` + `maxTargetRadius` (the focus sphere), and orbit is clamped to ±75° azimuth and ±60° elevation around the face normal. Damping is switched off for the `update()` that applies a new focus, or momentum from the old target carries over. A press and release within 4 px (`CLICK_SLOP_PX`) is a click (select); anything more is an orbit drag.
- **Camera rotation order is `YXZ`** (yaw, then pitch) for walk mode. `OrbitControls` writes the quaternion directly, so switching modes is safe.
- **Disposal** goes through a LIFO `Disposer`. The controller registers the scene first, so it's disposed last, after the overlays and BVHs that reference it. `viewport-controller.spec.ts` proves that after `dispose()` no listeners are left on the canvas, document or window, every geometry and material is disposed exactly once, no BVH or own `raycast` remains (overlays keep their deliberate no-op `raycast`), and pointer lock is released; a second test does the same with world entities and an armed ghost. `WorldSync` and the ghost take their meshes out of the scene before `disposeScene` runs, because their geometry belongs to the shared recipes, not the scene: a recipe disposed by both would fail the "exactly once" check. `viewport-renderer.spec.ts` does the same for the GPU shell with a mocked `WebGPURenderer`: no listener, pending frame or idle-stats timer survives `dispose()`. Any new resource owner must register with the disposer and be added to those tests.
- **The viewport renders on demand: a change nobody reports is never drawn.** `RenderLoop` (`loop/render-loop.ts`) requests an animation frame only when asked, and none while idle (behind the main menu it draws once, then nothing). Requests come from the controller's `invalidate()`, which is already called by `markHoverDirty()`, `emit()`, held-key changes, mouse look and OrbitControls' `change`; and from `ViewportRenderer` (first frame, resize, `webglcontextrestored`, `visibilitychange`). **If you add something that changes what is drawn without going through those** (a new overlay that animates, a material or light tweak, a texture that finishes loading, a sim-snapshot-driven effect from P2), call `controller.invalidate()` or `ViewportRenderer.requestRender()`; if it animates, return `true` from `update()` until it settles. Forget it and the screen shows the old frame until the next mouse move, and e2e that waits on the change times out. Never "fix" that by going back to a continuous loop. Inside `update()`, `invalidate()` is ignored (the frame in progress draws the change); return `true` to get another frame.
  - **Tests wait on the loop, never on time.** Unit tests drive `RenderLoop` with `ManualFrameClock`. E2E uses the hook's `whenIdle()` (everything requested is on screen; never resolves while a key is held) and `afterFrames(n)` (draws n frames, requesting them). A browser `requestAnimationFrame` no longer implies a render.
  - **three r186 runs its own rAF loop from `Renderer.init()`** even without `setAnimationLoop`. `ViewportRenderer` stops it through the private `_animation.stop()` (guarded: if a release renames it, drawing stays on demand but the page wakes every vsync again; check after a three upgrade) and calls `info.reset()` before each draw, since nothing else resets the counters now.
  - **Resize and thumbnails draw synchronously** (`renderNow()`): resizing clears the canvas, and the thumbnail must copy the drawing buffer in the task that drew it.
- **Frame-time HUD:** dev builds, or `?hud` in any build. It shows each frame's **main-thread cost** (`update` + draw submission), mean and worst per 500 ms window (not an EMA: the first frame includes shader compilation and would skew an average for seconds), and an fps figure only over back-to-back frames (walking, orbit damping). When nothing was drawn in a window it reads `idle · last frame N ms`. The cost excludes GPU-process time: under SwiftShader a walk showed 0.7 ms a frame at 39 fps. Calling `stats()` from the hook also starts a new window.
- **Headless WebGPU (`--enable-unsafe-webgpu --use-webgpu-adapter=swiftshader`) is unreliable here.** On Fedora 44 with Playwright's Chromium the device logs `Instance dropped in popErrorScope` at start-up; after New sandbox, buffer creation fails, and `captureThumbnail()` returns a blank image even on the menu. This is the same before and after on-demand rendering (checked in October 2026). CI exercises WebGL2; check WebGPU on a real GPU.
- **Headless frame times aren't representative.** Software WebGL2 (SwiftShader) at 1920×1080 rendered the bare panel at about 3 fps in F1.7 part 1, while WebGPU-on-SwiftShader-Vulkan held 60 fps. With 500 props (258 draw calls after culling) it flips: WebGL2 holds 60 fps and WebGPU-on-SwiftShader drops to about 3.8 fps, because each WebGPU draw is expensive on the CPU. The same 500 props hold 60 fps on both backends on a real GPU (RX 7600). Don't tune against headless numbers; measure the 500-device budget on real integrated GPUs, and consider instancing repeated props if WebGPU per-draw cost shows up there too.
- **Run E2E against your own server when other worktrees are active.** `playwright.config.mts` reuses whatever is listening on port 4200 (`reuseExistingServer`), which may be another checkout's build. Start `nx run game:serve:development --port <free>` and point a config with `webServer` unset and `baseURL` set at it. Under heavy machine load, "waiting for element to be stable" timeouts are load, not regressions: rerun with `--workers=1`.
- **The scene is the world's fixtures (F1.9).** `buildBaseScene()` holds only lights; `FixtureSync` draws `world.fixtures` (one group per fixture, named by its id, with ref-counted recipes from `geometry/fixtures`) and `WorldSync` draws entities. Never add level geometry to the scene directly: put it in the level document, or scripts and the hash won't know about it. A fixture's id is its selectable id, `view.focus` target and snap-target id.
- **Snap targets come from `worldSnapTargets(world)`**, not from the scene's `userData`. The selectables still carry `snapTarget` (for the scene-graph snapshot and tests), and a spec checks the two agree.
- **Raycasts skip invisible objects.** three-mesh-bvh's `ObjectBVH.raycast` ignores `object.visible === false`, so the stud wall's snap plane (the ray must find the wall between studs) is a visible mesh whose **material** has `visible: false`: picked, never drawn. The scene-graph snapshot marks it `drawn: false`.
- **The placement picker also holds fixtures without a snap target** (the backboard), so they hide the surfaces behind them. A hit on the backboard is on no target and the ghost hides; without it, a click on the board would place a box on the studs behind it.
- **The initial focus is the first backplate**, else the first focusable (not simply the first selectable in id order: `backboard` sorts before `backplate`). It is applied when the first world with fixtures arrives, and again if the focused fixture disappears. `resetView()` (on a new session, `Session.generation`) returns to it in work mode.
- **Selection cycles in code-unit id order**, so on the workshop: `backboard`, `backplate`, `bench`, `din-rail-1`, `din-rail-2`, `entity-1…`, `stud-wall` (`entity-` sorts before `stud-wall`). E2E that cycles with `]` must count from that list.
- **Bench tops are horizontal frames** (`normal: '+y'`, `right` along the front edge, `v` from the front edge to the back). A prop set on one is turned by `orientationForFrame`: yaw for `right`, then pitch 270 000 mdeg (-90°), so its depth stands up and its footprint (width × height) lies on the top. A move keeps orientation, so a wall-mounted prop can't be dragged onto a bench in one `entity.move` (`placeOnTargets` filters targets by `orientationForFrame`).
- **DIN slots start at `round(k × 17.5)` mm** (DIN 43880 module width, rounded once, F1.9), not at multiples of an integer pitch. Use `dinSlotStartMm(k)`; never step by 18 (the pre-F1.9 rounded pitch, which drifted 0.5 mm per module).
- **The workshop screenshot baseline** (`apps/game-e2e/src/workshop.spec.ts`, `workshop.spec.ts-snapshots/workshop-chromium-linux.png`, owned by `test-engineer`) is stable because everything that varies is pinned: seed 0, six props placed through the session hook at fixed positions, `?renderer=webgl2`, Chromium's SwiftShader (`--use-angle=swiftshader`, so a developer GPU and a GPU-less runner rasterise alike), a 1280 × 720 viewport at DPR 1, `view.focus stud-wall`, the pointer off the canvas, and a stylesheet that hides the HUDs, crosshair and focus ring. Tolerance: threshold 0.2 per pixel, at most 1 % of pixels. It runs on Linux only (other OSes skip). **To update it** after an intended visual change: `pnpm nx run game-e2e:e2e -- workshop.spec.ts --update-snapshots` on Linux, look at the PNG, commit it with the change. It passes against both the dev server and the production build CI serves.
- **Hide overlays with `page.addStyleTag`, not the screenshot `style` option.** With Playwright 1.64 and this app, `toHaveScreenshot({ style })` left the HUD and focus ring in the captured image; a style tag added before the assertion works. Don't use `mask` for the dev HUD: it exists only in dev builds and its width changes with its numbers.
- **Don't use `addUpdateRange()` on a large instanced attribute (three r186).** In the F1.10 spike, a partial upload of the `instanceMatrix` of a large `InstancedMesh` (102 400 instances) made every later frame cost 40 to 250 ms of CPU on both WebGPU and WebGL2; a full upload (`needsUpdate = true`, no ranges) cost nothing measurable. Re-upload the whole buffer, or split into smaller meshes, until a three.js release fixes it. Details: [ADR 0010](../decisions/0010-wire-routing-spike.md).
- **Catalogue devices with a recipe draw from their catalogue entry** (F2.4, F2.5, `geometry/devices.ts`): the battery, the bench supply, the DIN PSU, the SPST switch, the lamp, the resistor and the heater. Size and terminal positions come from `content/devices/`, the same numbers the simulator and leads use; only the look is the renderer's. Bench devices put their top at z = depth and their front at y = 0 (they're laid on a bench top pitched −90°); the DIN PSU faces +z. The F2.5 "on a base" devices stand up their depth from z = 0, with a screw head on the base top at each terminal. A catalogue kind without a recipe draws as the unknown cube: since F2.5 part 2 that includes the fuse and the breaker, which have engine models but no recipe yet.
- **A lamp that isn't `solved` is never drawn as an off lamp** (the validity rule, `sim/lamp-display.ts`; ADR 0011 §9.6). `solved`: drawn at its display level, and level 0 (clear glass, no glow) is a real "off". `unsettled`: drawn at its level with a violet-grey bulb tint. `unsolved` (unmodelled, AC pending, mixed), `singular`, or no entry in the map given to `setLampOutputs` (before the first snapshot, after a source reset): **unknown**, with no glow and a blue-grey tint. An empty map therefore shows every lamp as unknown, not dark. The scene-graph snapshot records `lamp: { level, status }` with status `solved | unknown | unsettled`. Don't "simplify" an unknown lamp to level 0 solved; that's the "dark = 0 W" bug (#52 review).
- **The lamp display curve is a game-design choice, not photometry** (`sim/display-curve.ts`, pure and lint-fenced): `level = round(255 × (1 − e^(−ln5·L)))`, 0 below `L = 1/255`. Rated light is level 204 (`LAMP_RATED_LEVEL`); over-voltage is brighter and saturates toward 255. Change it there only, and update the snapshots on purpose.
- **Lamp outputs redraw only when a drawn step moves.** `setLampOutputs` compares each lamp's quantised level and status with what it drew, and calls `invalidate()` only on a change; a step writes only uniforms (bulb colour and `emissiveIntensity`), never `visible` or defines. The half-step hysteresis ADR 0011 §9.2 mentions is **not** applied to lamps: a lamp settling exponentially toward its steady value would park one step short of it for ever (it never crosses the extra half step), so its drawn level would depend on history. Plain rounding is stateless, and sim output settles, so boundary flicker lasts a frame or two at most.
- **Each lamp entity has its own bulb material**, a clone of the recipe's `bulb` slot (`BULB_SLOT`); the other slots stay the shared recipe materials. `WorldSync.remove` disposes the clone, and the recipe disposes its own bulb with the recipe. The ghost never sees a clone (it draws the recipe geometry with its single material).
- **A switch's lever is a child mesh** (`lever`, shared geometry owned by the recipe, the recipe's `accent` material). It turns ±25° about x from the entity's **commanded** `state.closed` on each sync of a new entity snapshot, so a `device.operate` shows at once; it's world state, not sim output. Its geometry gets a BVH like any mesh under a selectable root, and a pick on it selects the switch.
- **One mesh per device, a material per geometry group.** A device recipe is one merged geometry with a group per material slot (`DEVICE_SLOTS`) and a material array, so a device is one pick, one BVH and one recipe in `PropRecipes`, which disposes every material on the last release. The placement ghost draws the same geometry with its single material, which three draws over every group; don't give the ghost a material array.
- **A device's label is data, not a texture.** The fictional brand and model (`Ferrovane FV12-7`) is on the mesh's `userData.label` and in the scene-graph snapshot (`label`); the label plate is plain geometry. No canvas text: it needs the DOM, and the controller is tested in Node.
- **Catalogue devices are `device` selectables**, props are `prop`. The mouse can't place a catalogue device yet: `propFootprint` (world-model snap) knows only the built-in props, so devices are placed by `entity.place` (the console, the palette, scripts) with an explicit orientation.
- **The debug overlays draw their own leads and terminals** (F2.6, `overlays/sim-overlays.ts`). ADR 0011 §9.2 has overlays recolour "the existing lead and terminal meshes", but nothing draws leads until P3's wire routing, and device recipes don't mark terminals, so the overlays draw a straight two-half segment per connection and a marker per catalogue terminal (`positionMm` turned by the entity's transform). When P3 draws real conductors, recolour those instead and drop the overlay's own lead layer. A lead whose end is on a device the catalogue doesn't know isn't drawn.
- **Band 0 is "no scale", and a band needs a row to get one.** `scalesByBand(NOMINAL_BANDS)` resolves each band index to a voltage scale by **name** (`dc12`, `dc24`, `ac120-240`, `ac208y120`, `ac480y277` in `sim/overlay-scale.ts`); index 0 and any name without a row resolve to `null`, drawn light grey with "No nominal band" in the legend, never as bin 0. A spec fails if `NOMINAL_BANDS` gains a name the table lacks: when sim-core starts choosing bands, use these names or add rows. Until then every island is band 0, so the voltage overlay shows no colours on solved circuits; only the current overlay has a scale for every band.
- **Unknown is not zero.** Steps start _unknown_ (`STEP_UNKNOWN`), and stay so for an island that isn't `solved` (singular, non-converged, unmodelled, mixed, 0 iterations), a solved island with no reference node (voltage only), an item missing from the current generation (a lead connected since the last descriptor) and after a source reset (`null`). A solved 0 V or 0 A is bin 0, a real colour. Unknown draws dark grey, thinner, with diamond terminal markers, so it isn't told apart by colour alone; the legend says it in words.
- **AC current has no direction in the overlay (a documented abstraction).** A phasor's sign is a phase, not a flow, so AC (and mixed) leads get swaying diamonds whose rate follows |I|; only DC gets arrows, pointing by the sign of the real part (positive from the connection's `a` to `b`). Arrow speed shows magnitude bins (20–200 mm/s), not drift velocity.
- **Current animates only while the sim runs.** `SimOverlays.update()` returns `true` (another frame) only while `SnapshotFeed.running` (`SimHost.running`), the current overlay is on, reduced motion is off and some lead is above bin 0; otherwise the arrows go back to rest and the loop idles. Reduced motion is settings `display.reducedMotion` (`reduce`), or `prefers-reduced-motion` while it is `system` (`connectViewportOverlays`). Tests drive it with a fake feed's `running` flag, never with time.
- **The overlays read every snapshot, drawn or not,** so switching one on while the sim is paused (no new snapshot) still shows the latest values. The per-snapshot path is `NetlistReadout.read` (allocation-free, `sim bench` `overlay-read-500-devices`), then `updateOverlaySteps` into preallocated arrays; colours and matrices are rewritten only when a step changed, and only then is a frame requested.
- **Overlay meshes stay out of the scene while nothing is shown,** so every existing scene-graph snapshot (and the workshop screenshot) is unchanged with the overlays off. Their names start `overlay:sim`, which the controller disposal spec's own-`raycast` exemption relies on. Instance buffers grow by doubling into a new `InstancedMesh`; the old one is `dispose()`d (its instance attributes are freed on that event), never resized in place.
- **Overlay e2e reads the overlay graph, not pixels.** `window.__controlsViewport.overlayGraph()` gives each terminal's and lead's step (`noScale`, `unknown` or a bin), the direction and arrow count; poll it with `expect.poll` until the worker's snapshot has arrived. Don't wait on `whenIdle()` with the current overlay on and the sim running: the arrows animate, so the loop is never idle and it never resolves (use `afterFrames(n)` to measure frames).
