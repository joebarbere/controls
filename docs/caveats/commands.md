# Commands caveats

**Load this when:** working on `libs/domain/commands`, `libs/domain/world-model`, `libs/features/session`, adding or changing a command or a default keybinding, anything that feeds `world.hash` or the replay log, or a replay that no longer reaches the live hash. Decisions: [ADR 0006](../decisions/0006-command-system.md), [ADR 0007](../decisions/0007-world-document-v1.md). Architecture: [commands](../architecture/commands.md).

- **`run` gets the logged args, not Zod's raw output.** `z.int()` keeps `-0`, but the log (JSON) can't. The bus passes `run` the `ReplayEntry`-parsed (normalised) args, so the live run and its replay see the same values. Don't "optimise" this back to `parsed.data`: a property test caught live `-0` against replayed `0`.
- **`when` is not checked by `exec`.** The UI context (mode, selection) isn't in the replay log, so a replay couldn't evaluate it. Put world preconditions in `run`; use `when` only to hide, disable or resolve commands in surfaces.
- **Changes are pure and must not mutate.** `apply` and `invert` return new objects; the property tests deep-freeze worlds to prove it. Logged args are frozen too, so copy any args object you store in the world (`entity.place` does).
- **A view command must be declared in domain code** (`defineViewCommand`, currently in `@controls/commands`), with the effect applied by the UI through `Session.onCommand`. A view command that exists only in a component can't be replayed headless: `sim-cli` would fail with `unknown-command`.
- **Undo and redo on an empty stack must fail.** Failures aren't logged, and that is what keeps replay consistent after a load clears the history (ADR 0006). Don't turn them into silent successes.
- **No undo cap without care.** The stacks are unbounded. A cap changes which undos succeed, so it must be a fixed constant that replay applies identically.
- **Lookup tables keyed by user text need `hasOwnProperty`.** The `when` tokeniser once used `key in KEYWORDS`, so `toString` became a function-valued "literal". The same goes for context keys (`Object.prototype.hasOwnProperty.call`).
- **Iteration order:** never let a `Map`, `Set` or `Object.keys` order without sorting reach the world, the log or the hash. `registry.list()` sorts by id; canonical JSON sorts keys.
- **Floats and maths in the hash path:** `Math.sin`, `Math.cbrt` and friends are implementation-approximated, so they can differ between engines. The world stays integer (mm, millidegrees). The SHA-256 constants are a literal table (checked in the spec with exact `BigInt` roots), not computed with `Math.cbrt`.
- **The cross-runtime golden hashes live in two places:** `libs/domain/world-model/src/lib/hash.spec.ts` (Node) and `apps/game-e2e/src/world-hash.spec.ts` (Chromium, which can't import workspace libs). Change both or neither. A golden that changes means every existing save's hash changed.
- **No wall clock, no ambient randomness.** Time is `world.tick` (0 in P1, recorded in every entry and checked on replay); randomness is `deriveStream(world.seed, commandStreamKey(ctx.seq))`. The determinism lint enforces this in domain code, but the session adapter is Angular code: never put `Date.now()` or `Math.random()` into command args there either.
- **The PRNG derivation and golden vectors are frozen** once v0.2.0 ships (ADR 0006). A change needs a `schemaVersion` bump.
- **`TextEncoder` isn't available in domain code** (no `dom` lib). Use `utf8Encode` from `world-model`, which matches `TextEncoder` (lone surrogates become U+FFFD).
- **fast-check arbitraries for the save documents** are importable as `@controls/save-format/testing` (a `tsconfig.base.json` path). Use them from specs only.
- **`Session` is `providedIn: 'root'`**, so each Angular `TestBed` gets a fresh one. With `?e2e=1` it puts `window.__controlsSession` (exec, hash, entries, hashWorld) on the page; e2e tests drive commands through it.
- **Binding ids for extra bindings live on the command** (`CommandDef.bindings`, F1.7), and `defaultBindingDecls` collects them from the registry, so a command and its keys are declared together. They follow the same uniqueness and `input.` rules as every binding.
- **Binding ids are a second namespace in the same grammar.** Settings `controls.keybindings` keys are binding ids: a command id, a fixed-argument binding (`toolbelt.select.slot3`) or an input action (`input.moveForward`). No command may use the `input.` prefix (`Keymap.create` throws), and binding ids must be unique across all three. Renaming a binding id orphans players' overrides (they are ignored, not migrated), so treat binding ids as stable too.
- **Context-argument bindings read the context at key time.** A binding with `contextArgs` (`entity.delete.selection` takes `id` from `selection.entityId`) resolves only while every such key is set, and `KeybindingService` passes `bindingArgs(target, context)` to `exec`, so the log holds the concrete id. Read the context once and use the same snapshot for `resolve` and `bindingArgs`. A key that is set but stale (a deleted entity) just makes the command fail `not-found`, which isn't logged.
- **Toggles are two bindings on disjoint `when`s, not a toggle command.** `V` is `view.mode.walk` (`mode == 'work'`) and `view.mode.work` (`mode == 'walk'`), so the log always says which mode was chosen. Before the viewport publishes `mode`, neither fires. Keep such pairs provably disjoint or the conflict check fails.
- **`view.mode {mode}` and `view.focus {target}` are save format** (F1.7), like `toolbelt.select`. `view.focus` can't check that its target exists (a view command's `run` is a no-op); the viewport ignores ids it can't focus, so a log replays the same either way.
- **`toolbelt.select {slot}` is save format.** The id and its strict `{ slot: int 1..9 }` shape are logged in every replay that touches the tool belt; changing either needs a `schemaVersion` bump and a log migration, like any command.
- **Conflict analysis must stay sound, not complete.** `provablyDisjoint` may say "overlap" when two `when`s are actually disjoint (the UI then shows a harmless conflict), but must never say "disjoint" when some context satisfies both, or a real conflict would be hidden. The fast-check soundness property in `disjoint.spec.ts` guards this; extend it if you add an atom type. Remember `evaluateWhen`'s truthiness: `null`, a missing key, `false`, `0` and `''` are falsy.
- **Resolution order is user-first, then binding id.** Never let registration order or object-key order decide which binding wins (`Keymap` sorts explicitly).
- **Default keybindings must stay conflict-free.** `keymap.spec.ts` (commands) and `entity-commands.spec.ts` (world registry) assert no conflicts on either platform. A new default chord that clashes fails there; give one side a disjoint `when` or another chord.
- **`.meta()` arg hints are not save format, but `.meta()` itself must not change parsing.** The palette reads `title`, `description` and `x-controls-ref` (`ARG_REF_KEYWORD`, `entityRefMeta`) from `z.toJSONSchema`; adding one to a persisted args shape is safe because it only adds JSON Schema keywords. Never use `.meta()` to smuggle behaviour (a transform, a default) into a schema: that would change the logged args. Entity ids in the `entity.*` args carry `entityRefMeta`.
- **UI chrome is `logged: false`, and must stay stateless.** `palette.open` (and F1.5's `console.toggle`) run and fire listeners but are never logged and take no `seq`. The registry refuses `logged: false` with `undoable` or `cheat`, and `exec` refuses (`unlogged-change`) one whose `run` returns a change or a history move, because replay would never see it. Code that reads `ExecResult.entry` or `ExecutedEvent.entry` must handle `null` (check `logged`); use `command.id` / `command.args` to react to a command whatever its logging. Don't flip an existing logged command to `logged: false` lightly: old logs still replay (`replayEntries` carries their entries over verbatim with `CommandBus.carryOver`), but the new log shape differs from the old one.
- **`seq` comes from `bus.nextSeq()`** (`firstSeq` + the entries logged), never from `log.length` (world v2, ADR 0011 §3). A bus continuing a rebased or restarted log is built with `firstSeq` (`CommandBusOptions.firstSeq`, `createWorldBus(world, registry, { firstSeq })`), so seeded streams keyed by `commandStreamKey(seq)` don't repeat. `replayEntries` expects the first entry at `bus.nextSeq()`.
- **Every world change keeps `tick`, the solution record (`world.sim`) and each surviving entity's `sim` bag** (ADR 0011 §1, §3; a property test in `world-model`). Build a new entity only on insert; when changing an entity, spread it (`{ ...e, transform }`) so its bags stay the same objects.
- **The world registry takes the catalogue** (`createWorldRegistry({ catalog })`, default `BUILTIN_CATALOG`): `entity.place` gives a catalogue device its initial bags and refuses a connection kind (`not-placeable`). Every host and the sim worker's mirror bus must use the same catalogue, or replay diverges.
- **`device.operate` never reads sim-owned state** (ADR 0011 §1): its `run` looks only at the entity's commanded `state` and the catalogue, and a property test checks the result is the same whatever the entity's `sim` bag holds. It records intent (a switch's `closed`, later a breaker's handle); the engine decides the effect at the command's tick. A control is a commanded state key of the device's model kind; its value is checked with `checkControlValue`. Setting a control to the value it already has succeeds and is logged.
- **`lead.connect` checks terminals against the catalogue in `run`:** an unknown entity (`not-found`), a prop (`no-terminals`), a terminal its device doesn't have or a device the catalogue doesn't know (`unknown-terminal`), `a == b` (`same-terminal`) and a second lead between the same two terminals in either direction (`duplicate-lead`) are refused. A lead between two terminals of one device is allowed (a jumper). Lead ids come from `nextConnectionId`; undoing a disconnect reinserts the same id.
- **A union of scalar types is the only union an argument may use** (`device.operate`'s `value`): the palette shows it as one text field typed like a console word, and the console types the word lexically (`true` → boolean, `12` → number, `on` → text; quote it to force text). Any other union still fails the palette's every-command spec.
