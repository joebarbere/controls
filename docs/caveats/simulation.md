# Simulation caveats

**Load this when:** working on `libs/domain/sim-core` (the netlist compiler, the DC and phasor solvers and the LUs, and from F2.3 the device models and engine loop), the region profile (`@controls/catalog` `region.ts`), `libs/domain/sim-protocol` or `libs/sim-worker`, adding a device model kind, the oracle corpus (`src/oracle/`, `oracle/`) or `sim bench`, or when a netlist, `topologyHash`, oracle, bench or determinism test fails. Contract: [ADR 0011](../decisions/0011-sim-worker-contract.md). Architecture: [simulation](../architecture/simulation.md). Decisions D1–D8: [phase 2 plan](../../plans/phase-2-circuit-engine.md).

- **A new placed model kind needs a netlist model.** `models.spec.ts` checks that `DEVICE_NETLIST_MODELS` and `CONNECTION_NETLIST_MODELS` cover every kind in `MODEL_KINDS`, so adding a kind to the catalogue without one fails `pnpm verify`. Until it has one, an entity of that kind is absent from the netlist (`no-model`).
- **A netlist model sees only the sim keys it declares.** `DeviceNetlistModel.simTopologyKeys` lists the sim-owned keys that change its topology (a fuse's `blown`). The compiler hands the model only those keys, taken from the engine's state (`options.sim`), and recompiles the device when one changes. Any other sim-owned value (a filament temperature, a state of charge) is the device model's business at solve time, never the netlist's. The world's own `sim` bags are only a fallback, correct at a session start or a load; during play the engine must pass its live state, or a blown fuse would compile intact.
- **Nodes have no fixed identity.** One merge or split renumbers every later node and branch, because the numbering is canonical (by smallest member), not historical. Never cache a node or branch index across topology generations; key by a member terminal or an element ref, and rejoin on the next descriptor (ADR 0011 §7).
- **Ideal joins carry no current.** A closed switch merges its terminals into one node with no branch, so the solver never knows the current through it; it is the current of the leads on either side. A device whose current matters (a fuse's I²t, a breaker's thermal state) must compile to a branch even while closed, not to a join. So must a switch once it has ratings, wear or a high-resistance-contact fault (P3/P4): closed, it becomes a resistive contact branch, like fuses and breakers.
- **A branch can have `a === b`.** A lead across a closed switch, or between two terminals a device joins, is still exactly one branch (ADR 0011 §7), with both ends on the same node. Solvers must accept it; it carries no current.
- **`topologyHash` is persisted.** It is in every save's `WorldV2.sim` and in every snapshot's hashed bytes, and the engine refuses to start (`start-failed`) on a save whose record doesn't match. Changing what it covers or how it is encoded (`netlist/hash.ts`: the version byte, `ELEMENT_KIND_CODES`, the field order) moves every persisted hash: bump the encoding's version byte and `SIM_ENGINE_VERSION`, and re-pin `hash.spec.ts` with the snapshot goldens. `ELEMENT_KIND_CODES` and `SOURCE_CODES` are append-only. **Any change to a built-in netlist model's terminals, parts, joins, element kinds, source domains or `simTopologyKeys` also needs a `SIM_ENGINE_VERSION` bump**: `hash.spec.ts` pins a golden per built-in model kind, so the change fails until you re-pin it deliberately. The rules are in ADR 0013, "Solution order and `topologyHash`".
- **Values never enter `topologyHash`, but element refs and model kinds do.** A value-only change (a lead of another length, a supply setpoint) must keep the hash, so the factorisation cache can reuse a symbolic factorisation (a property test). Replacing a lead with one of another id is a structural change, because the solution record is ordered by branch.
- **The hash runs inside the re-solve budget.** About 0.3 ms of a 0.94 ms structural recompile at 2,000 nodes is the SHA-256 (0.6 ms of 1.3 ms before F2.2 part 3 made `sha256` hash whole blocks in place). That is why the hashed form is a compact binary encoding, not text. Keep it compact, and measure (F2.7's bench) before adding fields. SHA-256 is now the largest single cost of a recompile, and it can't shrink without changing the bytes: hashing only what changed would need a different (tree) hash, which moves every persisted `topologyHash`.
- **The compiler writes the topology bytes itself; `topologyBytes` is the reference.** `NetlistCompiler` hashes through `TopologyWriter` (`netlist/encode.ts`), which writes the same bytes into a buffer the compiler keeps (F2.2 part 3b). Change the encoding in both, or neither: the netlist properties check every compiled `topologyHash` against `computeTopologyHash` of the netlist's own nodes and branches, and `encode.spec.ts` checks the edges (ids past 2³¹, 255-unit strings, buffer reuse). Caching each fragment's encoded pieces was tried and dropped: it saved 0.1 ms per recompile and cost 0.75 ms per from-scratch compile.
- **The compiler's structure list is overwritten in place.** A compile compares each entry with the previous compile's as it writes it (no second list, no second pass), so a compile clears `previous` before it writes: one that throws part-way (a broken model) must not leave a half-written list that a later world could match, which would return a stale netlist. `compile.spec.ts` pins it. Connection ends are cached on the connection's entry against the entity entry they resolved to, and trusted only while that entry's `epoch` is the current compile's; a rebuilt or deleted entity's entry is never stamped again.
- **The compiler sorts its input by id.** World documents are already sorted, but `compileNetlist` must not rely on it: the permutation property feeds it shuffled arrays. Keep any new input loop on the sorted copies (`byId`).
- **Part names and ids are ASCII by grammar.** The topology encoding writes terminal ids, parts and model kinds as length-prefixed ASCII and throws on anything else. Terminal ids (`TERMINAL_ID_PATTERN`) and model kinds (the catalogue's kind grammar) are ASCII; parts must match `^[a-z][a-zA-Z0-9]{0,31}$` and be unique within a device, or compiling throws (a programming error in a model, never a world error).
- **The test lead's conductor temperature is a constant.** `LEAD_CONDUCTOR_TEMPERATURE_K` (293.15 K, game-design: a 20 °C bench, also the IACS reference temperature) until P3 adds conductor heating. `leadResistanceOhm` doesn't clamp: anything that later varies the temperature must clamp it to the linear-α range (about 223 to 423 K) or say why not.
- **Netlists are read-only.** The incremental compiler shares fragments, and the `values` objects in them, between compiles and netlists. `values` are frozen; never mutate any part of a returned netlist.
- **Property tests compile only on flagged steps.** Compiling after every edit hid a stale-netlist bug (an undo, then a reconnect reusing the lead's id). Keep the `[op, compile?]` steps, the seeded benches and the generator-health floors in `properties.spec.ts`; if a test gets slow, split it by concern (its own arbitrary, health at the cut and after it, as the F2.4 source sessions are) rather than lowering `numRuns` or the circuit size, which weakens it. The incremental property compares netlists with `firstDifference` (exact: `Object.is` on primitives, prototypes, own keys), falling back to `toStrictEqual` only for the diff: `toStrictEqual` on every step was 40 % of its time. `firstDifference` builds its path only once it finds a difference (16 % less time in it), and a flagged step whose edit left the world (the same object) and the sim state (no blow since) as they were reuses the last from-scratch netlist, about 15 % of compiles; the incremental compiler is still called and compared on every flagged step. Profiled warm under coverage, what's left is about a third running the world commands (mostly Zod parsing the args and the replay entry), a third compiling (incremental and from scratch), a tenth comparing. That is about 200 ms for the test alone under coverage (220 before), and 400–650 ms in sim-core's full suite, where it runs first in its file while every other worker starts. Planted compiler mutants (a cached entity keeping its old terminal base, a connection end never re-resolved, a shorter structure counted as unchanged, the entity cache ignoring `state` or the sim keys, the connection cache keyed by id alone) are each killed on 28–30 of 30 seeds, as before. Two gaps: a values-only change to a lead (same id, other lead type, which needs an undo and a reconnect) is reached on 2 of 30 seeds, and dropping the cache prune is not observable (stale entries are never read).
- **Test-only model kinds live in `src/testing/bench.ts`** (a fuse that blows, an AC source and a supply with a setpoint, with a catalogue built on `TEST_MODEL_KINDS`). They exercise sim topology events, AC and mixed islands and value-only changes before the real kinds exist (F2.4, F2.5). `src/testing/` is excluded from the lib build, like `save-format`'s arbitraries, but counts towards coverage.
- **The DC solver needs a value for every branch it solves.** `dcBranchValues` takes a hook's value, else the model kind's default in `DC_DEFAULT_VALUES` (a `lead`'s resistance; a `battery`'s full-charge EMF behind its internal resistance, a new battery, since F2.4 removed the nominal-EMF placeholder), and throws when neither exists. The lamp has no default: its filament resistance is sim-owned state, so only its engine bank values it (F2.5), and a raw solver caller must supply it through a hook. A new placed kind whose element the DC solver reaches needs a default or a hook. The battery default must not reach a player build: a sealed lead-acid battery resting at 12.0 V is only about 25–30 % charged, so F2.4 removes it or makes it the open-circuit voltage against state of charge (plan F2.4).
- **Stamps must suit the element kind.** A `resistor` element takes `resistor` or `isource`; a `vsource` element takes `vsource` or `isource`. A `vsource` element keeps its branch-current unknown even while stamped as a current source, so the matrix layout depends only on the topology (part 3's factorisation cache keys on `topologyHash`). Don't make the unknown set depend on a value or a mode.
- **Singular is structural, not a pivot tolerance.** An island is singular exactly when its zero-ohm voltage sources close a loop (two ideal sources in parallel; one whose ends a closed switch joins). `DcSolver` checks that with a union-find before any arithmetic. Don't drop it for the numerical backstop: pivoting through a resistive mesh makes the singular pivot rounding noise rather than 0, and a planted fault showed about 3 in 4 such loops returning garbage currents unflagged (`properties.spec.ts`, the mesh-loop property). A device that can be an ideal source (a supply with no series resistance) must expect `singular` when two of them are paralleled.
- **`gmin` holds nodes, it doesn't model anything.** `GMIN_S` (1e-12 S, `kind: 'numerical'`) goes from every node to its island's reference. A node that only a current source reaches settles at I / gmin (1 mA gives 1e9 V): finite and not singular, but not physical. A current-limited source needs its compliance limit (F2.2 part 3's CV/CC loop), never a bigger `gmin`. F2.7's ngspice decks match it with an explicit 1e12 Ω shunt resistor from each circuit node to the reference, which is exactly sim-core's stamp. Neither ngspice option does that: its `gmin` only shunts semiconductor junctions, and its `rshunt` also shunts the decks' 0 V sense-source nodes and each source's internal node (F2.7 measured 434 DC values moving out of tolerance with it).
- **Floating components need their structural pinning.** A conductive component (resistors and voltage-mode sources) that doesn't hold the island's reference, reached only through current sources, is held by gmin alone. Stamped node by node, its KCL rows are nearly dependent: once its conductance exceeds about gmin / ε (≈ 4.5e3 S, R below ≈ 0.2 mΩ; a busbar section behind an open breaker), G + gmin rounds to G and the last pivot is exactly 0, a false `singular`. Below that it isn't singular, but its common mode comes from a pivot that is mostly rounding. `DcSolver` therefore solves it in exact new variables (common mode c = V(rep), u = V − c) with the representative's row replaced by the component's structural sum row. The sparse path (part 3) keeps it, since both paths stamp through the same routine: don't "simplify" back to per-node rows, and don't raise `gmin` or add a pivot tolerance instead. Voltages are c + u, and currents inside the component come from u. Test it with exact values, not KCL floors: on a floating cluster the floor is dominated by the common mode (5e8 V × 1e4 S), so check gmin · Σ V = the feed current, and internal currents against analytic values. Feed it both through a current source on a resistor element and through a `vsource` element in current limit, since they reach the sum row by different paths (`kclRhs`, `kclEntry`).
- **`gmin` shifts results by about gmin × R_th.** The relative error at a node is about gmin times the Thévenin resistance it sees: 1e-10 at 100 Ω, 1e-6 at 1 MΩ, and 1 at 1 TΩ. So an **insulation-resistance measurement** (megohmmeter, P5 meters) must exclude `gmin` from the path it measures, or show that `gmin`'s 1 TΩ per node stays far outside the meter's range. A difference current such as a near-balanced bridge's is affected the most (its golden allows 1e-8 for it).
- **Solver properties and goldens use the floor policy** in the plan's F2.2 section, never a bare 1e-12 A. A resistor's current is g · (Va − Vb) from node voltages known only to an ulp, so it carries about g · ulp(V) of rounding however exact the solve (4e-14 A for the bench's 41 mΩ leads at 12 V, about 1.4e-11 A for a 1 mΩ busbar at 120 V). The KCL floor is therefore `1e-9 · max|I| + 1e-12 A` plus the island's sum of those terms, at every node. Not only the terms at node n: elimination's residual is normwise (|L||U|), so a weak node can carry a stiff neighbour's rounding through a source current (27× a per-node floor on seed −710639118). It also adds 2 · 16 ε · (largest source-row term) · (stiffest node conductance), because elimination mixes the volt-scaled source rows into the amp-scaled KCL rows: an ideal 28 650 V source off a 1 S node leaves about 6e-12 A where the voltages are 3e-8 V. Source rows hold within 1e-9 of the island's largest row term plus their own rounding. Power balance adds Σ|V_n| × node n's floor (Tellegen). `src/testing/mna.ts` implements it (`kclFloors`, `branchRounding`, `sourceRows`). For phasors (part 2), use complex magnitudes.
- **Never compare two solves' values against a floor.** A value comparison (linearity, superposition, dense against sparse, an oracle) measures forward error: the residual times |A⁻¹|. Near-ideal source loops held by weak ties make that unbounded by any local or island term. An ideal source paralleled with one behind 1 µΩ circulates 7e4 A, so a node tied to the reference by 1e-4 S carries ε·I/G ≈ 7e-8 V. Measured bounds fail too: a Skeel |A⁻¹||A||x̂| bound and an a-posteriori 2·|A⁻¹ r| bound both flaked over fresh seeds, because GEPP's error is |L||U|, not |A|, and the measured A⁻¹ carries cond·ε error. Use one of two things instead:
  - **exact equality** for factors of 0 or a power of two (scaling every right-hand side by 2^m scales every rounding exactly);
  - **the residual-space check** (`linearResidual`), after each solve passes KCL and its source rows (`checkRows`). Every row of d = Σ c_p x̂_p must hold within Σ |c_p| × each solve's row bound, and the sources must cancel.

  The dense-against-sparse property (`mna/sparse.spec.ts`) and F2.7's oracle do both: residuals on every circuit, values only on a stated well-conditioned subset (1 Ω–10 kΩ, every source behind ≥ 0.1 Ω), with the ε·G·V current floor.

- **Tiny currents are resolved only to ε · G · V absolute.** On an island where nothing but `gmin` carries current (a lamp dangling off a battery), each current of about 1e-11 A comes out of KCL rows holding much larger conductances (24 S leads), so the solve can leave about 6e-14 A of absolute error, about 2e-3 relative, depending on pivot order. Bound such checks by the stated absolute floor (1e-13 A), never by a relative tolerance that one LU happens to meet: part 3's sparse LU pivots differently.
- **The solver's bits are pinned.** `mna/properties.spec.ts` pins a SHA-256 over 300 seeded solves. Pivot tie-breaking, `/ R` against `* (1 / R)`, where `gmin` is stamped: anything that changes a result bit moves it. A deliberate numeric change re-pins it together with the other numeric goldens and bumps `SIM_ENGINE_VERSION` (D8).
- **Small islands stay dense, and that is what keeps the pin.** `SPARSE_MIN_UNKNOWNS` (64) routes an island to sparse LU; the two LUs pivot differently, so their bits differ. Every circuit of the pinned 300-solve hash has at most 40 unknowns, so lowering the threshold below 41 moves the pin: re-pin with a `SIM_ENGINE_VERSION` bump (D8), or don't. The crossover was measured (warm sparse wins from about 30 unknowns, cold from about 130); re-measure before moving it. The DC oracle runs on both paths (`dc-oracle.spec.ts`).
- **The cache trusts `topologyHash`, so every netlist needs a real one.** Two different netlists under one hash would share a symbolic factorisation. A hit checks the unknown count and a fingerprint of the island's branch ends and throws on a mismatch, but that is a tripwire, not a guarantee. `syntheticNetlist` and `oracleNetlist` compute a real hash; any hand-made netlist in a spec must too.
- **Stamp modes are part of the cache key.** A `vsource` element in current limit has a different row, and a current source can split a conductive component, without changing `topologyHash`. So an island keeps one symbolic factorisation per stamp-mode signature (up to 4). A CV/CC supply crossing over costs a miss the first time in each mode, then hits.
- **`stamp` and the stamp program must agree.** On a cache hit the sparse path doesn't run `stamp`: it replays the program recorded on the miss (`assemble`): each call's value code (`gmin`, ±1, R, ±1/R) and branch, and the right-hand-side steps, in call order. A new stamp needs a new value code in `add`, `assemble` and `rhsOp`, computed exactly as `stamp` computes it (`-(1 / R)`, not `-1 / R`). The dense-against-sparse properties catch a mismatch (a planted −g as +g failed 9 specs).
- **A replayed factorisation is only bit-identical because the pivot rule is order-free.** `SparseLu` replays the last pivot sequence when the rule (the largest |x|, the lowest row on a tie, the diagonal kept above `PIVOT_THRESHOLD`) still picks the same row at every column, else it refactors afresh. Replay scans the candidates in a different order from a fresh factorisation, so the rule must never depend on scan order. Don't add a first-found tie-break or a tolerance that does.
- **Singular islands are never cached.** The structural singular check runs before any symbolic work, so a topology whose islands are all singular leaves nothing in the cache. Count on that in cache specs (it bit a property once).
- **The outer loop's hook is pure, and `values` is its working buffer.** `solveNonlinear` calls the hook with the iterate (`null` on a cold start) before each solve; the hook may write only its island's branches, from its inputs alone. `values` is left holding the last solve's values (restored if the cap is hit), and the solution is always that last linear solve, never a damped blend. A warm start must come from exported state (the solution record), never from the solver's history.
- **The sparse LU must be as stable as the dense one.** `PIVOT_THRESHOLD` is 1 (plain partial pivoting) since #51. The outer loop's per-branch `currentResolution` and the floor policy's 2 · 16 ε both assume partial pivoting's multipliers of at most 1. At u = 0.1 (multipliers up to 10) a fresh-seed island had about 3,000 ulps of noise on one node, so a source current of 3.5e-7 A behind 1.85 Ω moved by 5e-12 A between solves, three times its tolerance, and the loop stalled until iteration 41 (dense: 18; kept as an example in `nonlinear.spec.ts`). Don't lower the threshold for fill without re-deriving those resolutions: on these AMD-ordered systems u = 1 cost only 0.33 % more fill and fewer replay fallbacks.
- **The outer loop stops in value space first (#51).** After each solve, the hook is asked for its values at the solution; if they match the values it was solved with (to `OUTER_LOOP_RELTOL`, same stamp modes), that is the fixed point and the loop stops. The hook is called once more per iteration for this, so it must stay pure. Don't go back to a current-space test alone: a current repeats between solves only to cond · ε · V · g, so a 2e-7 A current between two 108 kV nodes (ill-conditioned synthetic islands) repeated only to 5e-5 relative, and the loop stalled on both LU paths (42 iterations, then 50 and `nonConverged`). Value-space tolerance is pinned by the accuracy tests: a 1000× looser one failed seven of them.
- **The loop can't converge below a current's own resolution, and must not stop above it.** Successive solves differ in a current by about its own rounding, so each branch's tolerance adds `OUTER_LOOP_ABSTOL` to that branch's term (`currentResolution`): a resistor's 32 ε (|Va| + |Vb|) / R, a voltage-mode source's sum over the branches at its two nodes, 0 for a current source. Without a rounding term, a 2.2e-7 A current wobbling by 6e-13 A ran an island to `nonConverged` (fresh-seed counterexample, kept as an example). **Never make the term island-wide** (the floor policy's KCL sum): it grows with the island and swamps a small current. A 1e-5 A load on a 1e-4 Ω busbar loop of 2 × 400 segments was reported converged with its R off by ×35.6 and its current by 84 % (#49 review; `nonlinear.spec.ts` keeps the case, failing already at 10 segments). A meter would show that error.
- **A `nonConverged` island's values look real.** At the cap the solution is the last linear solve, which is self-consistent for the values the hook set last (10 A or 0.1 A in the discontinuous test, never a blend). So any player-facing readout (meters, overlays, the inspector, `game.probe`) on an island flagged `nonConverged` must show it as unsettled, never as a steady reading (`electrical-realism-reviewer`, #49; plan F2.4 and P5).
- **Damping halves on oscillation and doubles back on steady progress.** Halving alone crawled back from a far cold start (42 iterations on a 620× hot/cold resistance); with recovery the same cases take 14–22. A device model with a very nonlinear law should give a good initial guess (a lamp's last temperature) rather than rely on the cold start. A discontinuous law with no fixed point ends `nonConverged` at the cap, by design.
- **Voltages from different islands aren't comparable.** Each island's voltages are against its own reference node, so a meter or probe whose two leads are on different islands has no defined reading from the solution: model the meter as an element that joins them (P5), or report a floating reading (`game.probe`, F2.3a). Never subtract two islands' node voltages.
- **Absolute node voltages can be negative.** The reference is the negative end of an island's first source, which may sit mid-string (a second battery in series below it), so other nodes can read negative. Overlays and readouts show differences against a chosen node (ADR 0011 §5.3), never a node's raw value as "the voltage".
- **Solver output is a pure function of (netlist, values).** `DcSolver` reuses its LU storage and index maps between solves, and `solve` reuses `out` when it fits; neither may ever change a result (a bit-identity property). The factorisation cache (part 3) keeps that, and the solution record's warm start must come from exported state (ADR 0011 §9.6), never from solver history.
- **AC values are RMS phasors, and L and C are stamp modes.** `AcSolver` (F2.2 part 2) reads `AcBranchValues`: an inductor or capacitor is a `resistor` element stamped `inductor` or `capacitor`, as a DC current source is a stamp mode, so F2.1's `ElementKind`, `ELEMENT_KIND_CODES` and `topologyHash` are unchanged and every passive stamp has one pattern. Don't add `inductor` or `capacitor` element kinds: that moves every hash (ADR 0013). There is **no AC current source**: one can leave a component held by gmin alone, which needs the DC solver's floating-component pinning in complex form first. Until then every AC element conducts and an island is one component holding its reference.
- **Solve DC first, then AC, into one record.** `AcSolver.solve` writes only `ac` islands and leaves every other island's entries in `out` as they are; `DcSolver.solve` zeroes every island it doesn't solve (`ac` and `mixed`). So the engine runs DC then AC into the same `DcSolution`; the other order wipes the AC islands. `mixed` islands are solved by neither (P2 has no converters): a readout must not show their zeros as a reading.
- **Phasor angles are exact constants only.** `phasorUnit` knows 0°, 180° and ±120° (cos 120° = −0.5, sin 120° = `Math.sqrt(3) / 2`). Another angle needs its own exact constants (30° has them; 45° is √2/2), never `Math.cos` (D6). The oracle generator draws from the same table, so changing it regenerates the corpus.
- **Nominal voltages are names, not exact values.** `RegionProfile`'s 208 V and 480 V are the rounded names of 120 × √3 = 207.85 V and 277 × √3 = 479.78 V. A three-phase source model builds its phases from the line-to-neutral magnitude and the exact ±120° angles, and gets the exact √3 multiple; never solve with the name as a line-to-line EMF.
- **The AC stamp program records codes, never admittances.** Each solve computes every admittance from its own ω and values before stamping or assembling (`admittance`), and the numeric factors are replayed only when the pivot rule re-picks them. Caching an admittance, ω or a numeric factorisation in the symbolic entry would carry one frequency or value into the next solve (two planted faults, both killed by `ac-sparse.spec.ts`).
- **Complex pivots are chosen by |re| + |im| (CABS1), not the modulus.** It needs no square root, is within √2 of |z|, and is what LAPACK uses. Switching to the modulus, or to Smith's division in place of the reciprocal, moves the AC pins (`ac-properties.spec.ts`, dense; `ac-sparse.spec.ts`, sparse): re-pin with a `SIM_ENGINE_VERSION` bump (D8), or don't. The DC pins are separate and must not move with an AC change.
- **Linearity is bit-exact for ±2^m and ±j · 2^m only.** A quarter turn only swaps and negates the parts, so it scales every rounding exactly, like a power of two. The exact 120° rotation is irrational in binary: check it, and every other complex factor, in residual space (`acLinearResidual`).
- **Power balances need the apparent power as a source's term.** Each part of E conj(I) rounds at about ε |E| |I|, so a purely resistive island's reactive power is 0 only to that: a self-looped source's Q = Im(|E|² / R) came out 2.9e-11 var against 1e5 VA, failing a bound built from |Q| alone. `acPower` takes |E| |I| as each source's term in both the real and the reactive balance.
- **A source behind a series R is a branch of admittance 1 / R in the floor (DC and AC).** Its current is (E − Vb + Va) / R, resolved only to 16 ε (|Va| + |Vb| + |E|) / R, the slack its own source-row bound already allows, so `branchRounding` (DC) and `acBranchRounding` (AC) count it (the floor policy, amended in #51). Without it, a tree island carrying only gmin current behind a 4 mΩ, 700 V source left 1.1e-12 A of KCL imbalance on the AC sparse path, 1.07× the floor (fresh seed, kept as an example in `ac-sparse.spec.ts`). It is not the DC outer loop's `currentResolution` term, which uses the voltages only (|Va| + |Vb|) for a convergence tolerance; the floor adds |E| because it bounds the source row's whole residual. **The term grows as 1 / R, so generators must keep source R ≥ 1e-4 Ω** (`MIN_SOURCE_OHMS`, and the DC generators' clamp): at 1 µΩ it made floors up to 6e6× looser. The generator-health tests cap the 99th percentile of floor / max|I| on live islands (3e-5 DC, 1e-4 AC); if one fails, fix the generator, never the ceiling.
- **AC value comparisons need a resistive spanning tree.** An L–C pair near resonance is ill-conditioned (only gmin and the resistors around it hold it), so a value comparison there measures forward error, which is unbounded. The well-conditioned AC subset (`testing/ac-circuits.ts`) keeps a resistive 1 Ω–10 kΩ tree, which keeps Re(Y) definite and bounds ‖M⁻¹‖ however the reactances cancel; everything else is checked on residuals.
- **The AC generator needs loops from its extras.** AC has no current source to drive a loop-free tree, so a circuit without extra elements carries only gmin current. `ac-properties.spec.ts` draws at least two extras per circuit and keeps a quarter of them free to merge islands; the generator-health floors pin both.
- **The oracle corpus is frozen by its generator.** Any change to `src/oracle/generate.ts`, `deck.ts`, `ORACLE_CORPUS` or the oracle's `gmin` changes the decks, and `corpus.spec.ts` fails as stale. Regenerate with `pnpm sim oracle regen` (needs ngspice 47; [oracle guide](../guides/oracle.md)) and commit decks and results together. Never edit the corpus by hand, and never regenerate to make a solver comparison pass ([ADR 0012](../decisions/0012-oracle-corpus.md)).
- **Oracle node 0 is sim-core's island reference, not just SPICE ground.** sim-core references an island to the negative end of its first voltage source in branch order (else its smallest node) and stamps `gmin` to it; the generator relabels nodes so that node is 0. If F2.2 changes how it picks the reference, change `referencedToGround` in the generator and regenerate, or the gmin stamps and every reported voltage disagree.
- **`gmin` in the decks is explicit `RG<n>` resistors, not `.options rshunt`.** `rshunt` also shunts the decks' internal sense (`s<k>`) and source (`e<k>`) nodes, which would add (m + 1)·gmin at a node with m elements. ngspice's `gmin` option only touches semiconductor junctions. The decks take `gmin` from `GMIN_S.value`, so changing it changes every deck: regenerate.
- **Always run ngspice with `-n`.** A `.spiceinit` in the working directory or HOME is read otherwise, and silently changed results in review. `regen` passes `-n -b`; do the same when running a deck by hand.
- **ngspice prints 6 digits unless told otherwise.** Every deck sets `set numdgt=17`; without it a 1e-6 relative comparison is meaningless. ngspice 47 reports no complex device currents in AC (`@r1[i]` is real), which is why each element sits behind a 0 V sense source.
- **A branch on no loop with a source tests only gmin.** A dead end of a tree, or a loop hanging from a single node, carries about 1e-10 A of gmin current, pure rounding. The generator biconnects every circuit, current sources ignored (`articulation`); about a fifth of the branches were dead before it did. `corpus.spec.ts` requires at least 95 % of branches to carry more than 1e-6 of the circuit's largest current. Keep both when adding kinds.
- **Branch currents are only good to about ε · V · G_max in doubles** (about 2e-11 A with 10 mΩ and 820 V; F2.2 part 1 measured 1.4e-11 A for 1 mΩ at 120 V). So the oracle's floor scales with the circuit: `max(1e-12, 1e-7·max|x_ref|)`, about 30 times ngspice's own noise (3e-9 of the circuit's largest value, against exact solutions). That floor is for comparing against a noisy reference; F2.2's floor policy for sim-core's own KCL residuals (#46) is a different check. Resistances below 0.1 Ω (10 mΩ in a source) stay out of the oracle: at 1e-4 Ω ngspice itself misses the exact answer.
- **Bench cases have spec budgets or none.** A case's `budgetMs` comes only from spec §4.5/§4.9; the plant's compile cases (one topology change per run, set up by an untimed `prepare`) report with `budgetMs: null`, the 2 ms re-solve is gated through the calibration loop (below), and the 0.3 ms per-tick budget gates `tick-device-mix` since F2.3a (one step's layers, never a solve: prepare puts the engine on a non-cadence tick; since F2.5 part 2 on the real catalogue's battery, fuse, breaker and lamp, materialised at tick 2001 so the lamps have settled and no continuous re-solve lands in the timed step, about 0.053 ms). The plant is built lazily on the first bench run, not at import (every `sim` command imports the cases). On a loaded machine the medians move by 2× (the from-scratch compile measured 4.6 ms quiet, 8.5–11 ms loaded), so a budget must have headroom on the slowest CI runner before it is switched on.
- **The re-solve gate is calibrated, run for run.** `plant-resolve-topology-change` is held to spec §4.5's 2 ms _on the reference machine_: each timed re-solve tᵢ is followed at once by a run of the calibration loop cᵢ (`apps/sim-cli/src/bench/calibration.ts`), and the gate is `median(tᵢ × CALIBRATION_REFERENCE_MS / cᵢ) ≤ 2 ms` (plan F2.2 part 3b; the user's decision of 2026-10-31). A raw-millisecond gate would fail the CI runners, and a per-OS budget or skip is never allowed. The report keeps the raw median beside it (`medianMs`, and `calibration.scale` = median(c) / reference), and `ratio` is what is gated (≤ 1 passes). The CI step after `pnpm verify` prints the JSON on every OS (Nx hides a passing task's stdout, so a `console.log` in a bench case never shows in CI).
- **The gate runs alone.** `pnpm verify` runs `nx run-many -t lint typecheck test build`, then `nx run-many -t bench` as a step of its own, and `sim-cli:bench` also has `"parallelism": false`, so nothing else runs while it times (#53 review: beside other Nx tasks the local proxies for CI failed 7 % to over 70 % of runs at the Windows ratio). The spec that runs the built bundle inside Vitest checks the report's shape, determinism and calibration, never `ok` or `ratio`. Don't add a timing assertion anywhere else.
- **Why the pairing.** The plain form, `median(t) ≤ 2 ms × median(c) / reference`, was measured first: over 32 runs beside a saturating parallel test load (load average about 24 on 12 threads) its ratio spread 3.2× and failed one run (1.75), because a burst of load can land on more re-solve runs than calibration runs. The paired median spread 1.7× and peaked at 0.91. Under ambient load (31 runs) the paired ratio was 0.50–0.79, median 0.67.
- **The calibration must share no code with what it calibrates.** A regression in sim-core, the catalogue or `world-model` (its SHA-256) must not slow the calibration too, or the gate absorbs it. `calibration.ts` imports one type and calls nothing outside itself, and `bench.spec.ts` checks its import lines. It does the same _kinds_ of work as a re-solve, in fixed amounts: a scattered multiply-add over 128 KiB of doubles, SHA-like integer rounds, 20,000 short-lived records, and a pointer chase round a 4,096-record ring. Larger memory-bound parts (a 1 MiB gather, a 32 Ki-record ring) slowed 3–6× under contention where the re-solve slowed 2×, and keeping each run's records alive into the next run (as the compiler keeps its last netlist) spread the calibration 2.7× across processes, by putting a major GC in some runs and not others. Measure before changing the mix. The calibration's working set stays in cache and the re-solve's (a 2,000-node plant, its caches and netlists, about 40 MiB of heap) doesn't, so memory contention from other processes slows the re-solve more and pushes the ratio up: that is why the bench target runs on its own (below).
- **Re-baselining the calibration.** Change `CALIBRATION_REFERENCE_MS` only when `calibration.ts`'s workload changes, when Node is bumped (`.nvmrc`; a new V8 moves the calibration and the re-solve by different amounts), or when the reference machine is replaced, and never to make a failing gate pass: a re-solve that got slower is a regression to fix. To re-measure, on the reference machine (now an AMD Ryzen 5 5600X, Node 24.12.0) with no other work of yours running: `pnpm nx build sim-cli`, then run `node dist/apps/sim-cli/main.mjs bench` 31 times and take the median of the reports' `plant-resolve-topology-change.calibration.medianMs`. Write the value, the machine, the Node version, the date, the range and the load into the constant's `source`, and say in the PR why it changed. A reference measured under load is larger, so the gate gets stricter, never looser.
- **What the gate can and can't catch.** On the reference machine the paired ratio sits at about 0.67, so the gate fails a re-solve that has become about 1.5× slower: a planted exact 1.5× slowdown (a spin to 1.5× each run's own time) failed 25 of 30 runs, median ratio 1.10. Smaller regressions pass until they add up; the bench prints `ratio` on every CI run, so watch it drift. Under a saturating load the ratio reached 0.91, so the gate has about 10 % headroom there and more in a normal `pnpm verify`. On CI (the PR that switched it on) it was 0.76 on Ubuntu, 0.58 on macOS and 0.85 on Windows: if Windows starts failing, look at the re-solve first, then report it to the user; don't re-baseline to make it pass.

### The engine loop (F2.3a)

- **A device's sim bag must hold everything that affects its future.** The engine rebuilds every bank from the bags at each topology change (branch indices move then) and on every load, so a value kept only in a bank's arrays is lost at the next switch flip and on a save. The save-and-load property in `engine/properties.spec.ts` catches it. Hidden constants that are a pure function of the device (a tolerance from its seeded stream, a parameter) are fine. Finite floats survive JSON bit for bit, so a bag can hold the exact state.
- **A device record must follow from the bag and the solution.** `writeRecord` gets the current solution: compute a power from the bag's temperature and the solved current, never from a value the last step cached, or a loaded engine writes other bytes (a planted mutant did exactly this and the reload test failed).
- **A branch nothing can value leaves its island `unmodelled`.** In engines 3 and 4 the built-in lamp had no filament model, so an island holding one was solved with placeholder stamps only to keep the solver going, then zeroed and recorded with 0 iterations. Since engine 5 (F2.5) the lamp is modelled; the rule still holds for any kind that reaches the solver without a value. `iterations === 0` is the one sign of "not solved" in the record and the snapshot (ADR 0011, "Implementation notes"): every reader must treat such an island like an AC one before F2.2 part 2, never as 0 V.
- **Every command that changes the netlist solves at once, one solve per command.** Two commands at the same tick give two solves, the second warm-started from the first's record. The sim worker (F2.3b) must do the same, solve for solve: batching commands at a tick would change the warm start of a nonlinear island and so its bits.
- **The warm start is the solution record, and nothing else.** `SimEngine` keeps two `DcSolution`s and swaps them, so the warm start is never the buffer being written. A structural change drops it (the topology differs); a load restores it from the record bit for bit.
- **Island events need an identity across topology changes, and islands have none.** A flag rises only if none of the new island's entities was in an island with that flag before the change. Keying by the island's whole entity set raised a second `singular` when a lead merged a load into a singular island (a planted case in `engine.spec.ts`).
- **Tombstones follow `nextEntityId`.** A device that leaves the netlist while its id is below `nextEntityId` was deleted: its bag is kept, unpersisted, and restored if the id comes back (undo). One at or above it had its `entity.place` undone: its bag is dropped, so the id can start fresh. A compile also reads tombstones for `simTopologyKeys`, so an undone delete of a blown fuse compiles blown.
- **No solution, no `lastSolveTick`.** With an empty netlist the engine holds no solution: the export is `null` and the snapshot writes `lastSolveTick` 0, as a freshly loaded engine would. Writing the last real solve's tick there made a reload differ (a fuzzed counterexample: delete everything, save, load).
- **The game never runs the engine on the main thread** (F2.3b, ADR 0011 §1). The session's `Game` is created with `time: SimHost.time`, so no engine starts there; `game.hash()`, `save()`, `probe()`, `snapshot()` and `islands()` throw `NotAvailableError` (phase `worker`). A loaded save's log is replayed on main for the commanded state only (`resumeLogGame` with a time host), and verified in a worker.
- **Test-only engine models live in `src/testing/engine.ts`** (`@controls/sim-core/testing`): a self-heating load, an I²t fuse, a resistance that never settles, an ideal twin source and layer-order probes, on `ENGINE_TEST_CATALOG`. Their numbers are game-design test values, never a real device's. `sim bench`'s per-tick case uses them too, so the alias is allowed in scripts (it needs no fast-check).
- **`SIM_ENGINE_VERSION` is 5** (2 was #51's pivoting change; 3 is F2.3a's materialised record; 4 F2.4's sources; 5 F2.5's lamp; [history](../history.md)). What follows was written at 3 and still holds. Engine 1 never ran, so its saves (the world v2 kickoff's fixtures) hold `sim: null`; replayed by engine 3 they materialise a solution and hash differently, so they load as `engine-changed` (D8) and `sim replay` on one fails with a note naming both engines. A props-only world exports `sim: null` and hashes as before.
- **The per-tick path allocates a few bytes a step, DC and AC, alone or all together.** Measured by `engine/allocation.spec.ts` (below, uncovered), worst median of 100 runs under load: a battery into a heating load 1.0 B/step, a DIN PSU regulating 0.6, shorted and hiccuping 1.7, hiccuping into a heating load 0.7, the AC loop 1.1, a mixed DC world 0.0 and a mixed AC world 3.4 (one world of every kind was 28 before the fixes below). F2.3a's "about 100 bytes per cadence solve, 32 inside `solveNonlinear`" (about 21 B/step) was heap numbers: doubles passed into the dense stamp's `add`/`kclEntry`, and `valuesWithin`'s closure (next bullets). The rest of the AC figure (about 18 B/step) was the same in `ac.ts`'s `add`, plus array iterators (below). Keep layer and solve paths on indexed loops and preallocated objects (one `solveNonlinear` options object, reused); an options literal per solve cost about 40 bytes.
- **Allocation that depends on inlining differs from process to process.** A non-integer double that crosses a call V8 doesn't inline is boxed into a heap number, and so is one held in a variable that also takes a constant (`let v; if (…) v = GMIN_S.value; else v = 1 / r; a[k] += v` boxed every value, though every call was optimized). What V8 inlines depends on the type feedback the process has seen and on when the concurrent compiler finishes, so the same code ran at 21 B/step in most processes and at a steady 26 or 42 in 2–3 % under load, for the whole run (the F2.4 flake: the gates sat at the end of `engine.spec.ts`, after some thirty tests of other device kinds through the same call sites; `--no-concurrent-recompilation` made it worse, not better). So the dense stamp passes only a value's code and branch, and `add`/`rhsOp` read the value from the typed arrays with one store per case, exactly as `assemble` computes it; `valuesWithin` is written out with no helper. Both are bit-identical (no golden moved). `ac.ts`'s `add` does the same since F2.4's review. Still inlining-dependent: `DC_DEFAULT_VALUES.lead` → `DcBranchValues.resistor` → `finite` (the regulating PSU's second regime, 3.4 B/step). Find a site with the sampling heap profiler (a failing gate prints its top sites), never by guessing.
- **A `for…of` over an array allocates its iterator when the loop isn't fully optimized.** A DIN PSU into a heating load, measured after the other gates in their process, allocated 70 B/step in `DcSolver.solveIsland`'s own frame (alone, 8.5): escape analysis dropped the `for…of` loops' array iterators when the solver's feedback was monomorphic and kept them once the process had seen other device kinds. So `dc.ts` and `ac.ts` iterate `island.nodes`, `island.branches` and `netlist.islands` by index (70 → 3.4 B/step; the AC loop 19.7 → 1.6). The same change in their write-back made a rarer regime visible (11 B/step in `solveIsland` in 1 run of 120): `positiveZero`, a call returning a double, boxed its result whenever it wasn't inlined. The write-back now normalises −0 inline with `x + 0` (−0 + 0 is +0, every other value unchanged, NaN stays NaN), and the helper is gone. Both are bit-identical (no golden, oracle or pinned hash moved).
- **Pass a slot, not a value, on a per-solve path.** A process running many device kinds (the game's worker: one engine, every kind) stops inlining calls that a process with one kind inlines, so every double crossing them is boxed. In one world with every source kind, measured in the gates' process: the regulated outputs' `regulate`/`stampRegulated` arguments (now `RegulatorSettings` slots read by index, the CV/CC law written out in `iterateRegulated`, and a property checks it against `regulate`), the setters' `finite` helper (now an inline check, with only the throw in a cold helper), `DcBranchValues.vsource`/`isource`/`resistor` from the battery, the supplies and the lead default (now `vsourceAt`, `isourceAt`, `resistorFrom`, which read the value from a typed array or object themselves; a test checks each against its by-value twin over finite, zero, negative and non-finite inputs), and `AcSolver`'s ω, passed to `solveIsland` and `admittance` every solve (now kept in a one-slot array, recomputed only when the frequency changes; the AC loop 1.7 → 0 B/step). The battery's two EMFs are computed into its bank's slots (`batteryEmfsInto`, the one definition; `batteryEmfV` and `batteryChargeEmfV` read it through a scratch slot): their returns were boxed in a mixed world, about 6 B/step in 1 run in 120. Still there, below 1 B/step: the lead default's property read when its closure isn't optimized (it runs once a solve).
- **Look a bank's hooks up once, not per solve.** Each kind's bank is an object of its own shape, so `fillValues` reading `bank.dcValue` (and the iterate hook reading `bank.iterate`) loaded a property across many maps: every new kind's bank deoptimized `fillValues` ("wrong map"), and until V8 optimized it again the code boxed values (episodes of about 10 B/step for 14 000 steps, 112 000–126 000 into a mixed world). The engine now builds per-branch arrays of the hooks at each rebuild and calls them with the bank as `this`; a mixed world's steady state is 0 B/step and it reaches it sooner.
- **The engine solves AC islands after DC, into one record** (F2.3a after #51). The order matters: `DcSolver.solveNonlinear` zeroes every island it doesn't solve, and `AcSolver.solve` writes only `ac` islands, so DC then AC leaves both; the other way round would zero the AC islands. `engine.spec.ts` checks a world with both against each alone. A device model on an AC island gives its phasor value through `acValue`; one without leaves the island unmodelled. A layer reading a current on an AC island must take its magnitude (re² + im²), never just the real part.
- **No angle in `sim-core`, and none hashed.** `probe` returns the phasor (`re`, `im`) and `rmsVolts` (a correctly rounded `Math.sqrt`); the scripting API's `phaseDeg` comes from `Math.atan2` (engine-dependent, D6), for display only.
- **Measuring allocation in a spec: sample it, gate on the median, in a file of its own.** `allocation.spec.ts` runs V8's sampling heap profiler (`node:inspector`, `HeapProfiler.startSampling` with `includeObjectsCollectedByMajorGC` and `…MinorGC`) around each window and counts only the samples under `SimEngine.advanceTo`: the bytes allocated, whenever a GC ran, never the measuring code's own, and where (a failing gate prints its windows and top sites). The F2.3a method, heap growth plus what each `GCProfiler` record freed after a forced `gc()`, was off by up to ±1.4 MB in a 10 000-step window (−48 to +142 B/step), and the smallest of ten windows let a planted 8 B/step through when one window read low. Gate on the median of eight 10 000-step windows after a 100 000-step warm-up: a per-step allocation raises every window, a late tier-up or a short slower regime a few. **The windows settle before they count:** measurement continues until the last four windows lie within 2 B/step of each other (at most three times the window count), and the gate takes the median of the last eight. A steady allocation settles at once and is measured in full, so the rule can't hide one; only a falling sequence, tier-up still finishing, keeps it going. A fixed warm-up wasn't enough on CI's slowest runner, which finished a late tier-up inside the AC gate's windows (11.97 9.65 10.28 10.04 2.70 0.50 0.51 0.00, median 6.18 against a gate of 6). The failure message lists every window and which ones the gate took. **The gates run without coverage**, alone: sim-core's `test` target runs the covered suite (`vitest.config.mts` excludes the file), then `vitest run -c vitest.allocation.mts`, so they stay in `pnpm verify` and CI. Coverage instrumentation changes what V8 optimizes and made them 4–5× slower (the mixed world took 6–10 s on CI's runners, past Vitest's 5 s timeout, and the DC gate up to 4.1 s); the game runs the uninstrumented engine. Locally the file takes about 1.4 s (each gate under 0.35 s under load). The gates are alone in their file, so their process's feedback comes from their own workloads (Vitest runs each file in its own process); they share it in order, so add a gate at the end and measure its baseline there, never in another file's process: a planted allocation measured after the four gates read 87 B/step, alone 17. Never raise a gate to pass: set it between the worst baseline median of at least 80 runs (uncovered, measured in place), and that baseline + 8, and check that a planted 8 B/step and 64 B/step in `SimEngine.step` fail it every run. The file's last test plants 32 B/step through a wrapped test model and expects more than 24: a renamed `advanceTo` or engine module, or an empty profile, would otherwise measure 0 and pass every gate (checked: with the filter broken, the four gates passed and it failed).
- **Measuring allocation outside sim-core (the sim-cli bench, sim-protocol): `--expose-gc` at run time.** `v8.setFlagsFromString('--expose-gc')` then `vm.runInNewContext('gc')` gives a callable `gc()` inside a Vitest worker, with no command-line flag. Collect before each measured window: a scavenge inside the window otherwise frees garbage made earlier (by other tests in the worker) and counts it as the window's. Measure bytes (heap growth plus what each `GCProfiler` record freed), never GC counts, and take the smallest of several windows: code not yet optimized allocates more, and when optimized code lands varies.

### Power sources (F2.4)

- **The nominal voltage is never an EMF.** A lead-acid battery resting at its nominal 12.0 V is about a quarter charged. The battery's EMF is its open-circuit voltage against state of charge (`batteryEmfV`); `DC_DEFAULT_VALUES.battery` is the full-charge EMF (a new battery) for callers that run no engine model. A golden that wants a round 12 V sets it through its own hook (`dc-goldens.ts` does), never through the default.
- **Battery abstractions** (for `electrical-realism-reviewer`): the EMF is linear in state of charge (published charts sag towards empty: resting at 12.0 V reads about 18 % charged here, nearer 25 % on a chart); the internal resistance is the full-charge 1 kHz figure at every charge (it rises as a battery empties, and DC resistance reads higher); capacity ignores the discharge rate (Peukert) and temperature; capacity is therefore optimistic by about 20 % at C/5, 40 % at C/2 and roughly 70 % at 1C (at 0.7C a real 7 Ah VRLA is near its cutoff within the hour, where the model has used 71 %), so jobs from P3 on must not rely on run time at high rates; charging counts at 100 % coulombic efficiency, and the charge EMF is a straight line from E(s) at 80 % to the 14.4 V gassing voltage at full, not a measured charge curve; there is no charge overpotential, so a bulk charge reads low and runs fast (a half-charged battery taking 5 A reads about 12.47 V, and a stiff source drives about 9C into it), a 13.8 V float charges only to about 93 % (where E_c reaches 13.8 V), and an overcharge is limited by the internal resistance alone (about 26 A at 15 V, where a real battery past gassing takes about C/50 to C/20); sulphation, wear and the recovery of a rested cell are not modelled. Each is a later feature, not a bug to work around.
- **A regulated output decides its mode from its stamp, not its bag.** The outer loop calls `iterate` with the iterate and `values` holding the stamps that iterate was solved with (restored after each self-consistency check), so `regulate` reads the current mode from the branch's stamp (`isource` is CC). The bag's mode is only the cold start and `dcValue`'s first stamp. Deciding from the bag inside a solve would make the hysteresis relative to the last solve rather than the last iterate, and the self-consistency stop would disagree with the mode actually stamped.
- **Commit what a solve decided in `afterSolve`, not in a layer.** The engine calls each bank's `afterSolve(ctx, values)` right after a solve, with the values that solve used. A supply commits its mode there, so `exportState`, the record and a save right after a command's solve agree with the solution. Committing it in the continuous layer left one tick where the bag and the solution disagreed, and a save in it reloaded into the other mode inside the hysteresis band. Unsolved and singular islands commit nothing (their stamps decided nothing).
- **The hysteresis band is the tolerance of "never past a setpoint".** In CV the current may reach `I_lim (1 + h) + 1 µA`, in CC the voltage `V_knee + h·V + 1 µV` (h = 0.1 %, `CV_CC_HYSTERESIS`). The never-exceeds property checks exactly that, so widening the band is a realism change, not a test fix. A fresh supply at exactly the crossover stays in CV (it leaves CV only past the band).
- **Supplies can sink in CV.** The CV stamp is an ideal source behind R_out, so a higher source paralleled with a supply drives current into it (negative `outputA`). Real bench supplies mostly can't sink; until a model needs it, this is a recorded abstraction. Paralleled supplies still settle, because R_out is never 0 (never `singular`).
- **A value change from a layer needs a re-solve too.** Since F2.4 a layer returning `true` re-solves within its step even if the netlist didn't change (`recompile` returns false for a value held in a bank). Without it a PSU switching off would wait for the next cadence solve, up to 9 ticks late, and the hiccup period would drift with the cadence. It recompiles first only when the bank's kind lists `simTopologyKeys` (a fuse): the compile reads a bag through those keys alone, so another kind's change can't move the netlist, and compiling anyway walked the whole world and allocated (two hiccuping PSUs in a 15-device world: about 12 B/step, all in `compile`).
- **The hiccup timer counts ticks, never the wall clock.** `phaseTicks` counts steps in limit (only on a solved island) and steps off; both are in the `sim` bag with `mode`, so a save mid-hiccup resumes the same period. Its timing values are game-design choices inside the class's published behaviour (the catalogue says so).
- **Records follow the validity rule** (ADR 0011 §5.4, amended in F2.4): `status` is the island's (`readingStatusCode`), solved quantities are written only when it is `solved`, the device's own state always. F2.5's loads follow it too; a reader must never show an `unsettled` value or mode as steady.
- **An hour of sim time is too slow under coverage.** sim-core always runs with coverage instrumentation, which makes 3.6 million ticks take about 4 s (about 0.8–1.9 s without), close to Vitest's 5 s default and past it on a slow runner. The battery's one-hour golden is in `apps/sim-cli/src/battery-hour.spec.ts` (no instrumentation); sim-core keeps a one-minute version for coverage. Don't move it back or raise the timeout.
- **A hand-built world may lack bag keys.** The bench plant (`apps/sim-cli/src/bench/plant.ts`) builds entities with `sim: {}`, which the loader would refuse; the battery bank starts such a battery full (its kind's initial value) instead of reading `undefined` as a NaN EMF. Validated worlds always have the key.
- **A non-integer double passed to a call allocates.** V8 boxes a typed-array double into a heap number when it crosses a call it doesn't inline, unless it is a small integer. The battery's 12.9 V EMF (the placeholder's 12 V was a small integer) made the dense stamp's `rhsOp(k, emfV, …)` allocate on every solve. The stamp now passes no values at all (see "Allocation that depends on inlining" above). Before raising a gate, look for a value crossing a call in a hot path.
- **A battery never creates energy** (F2.4 realism review). Below 2 % of charge (`BATTERY_COLLAPSE_SOC`) its EMF collapses linearly to 0 V at empty, so a discharge slows and stops at empty; and charging, the cell is a piecewise-linear element (discharge EMF E(s), charge EMF E_c(s) rising to 14.4 V above 80 %, no current in between) chosen by the outer loop from the iterate's terminal voltage, so a full battery on a 13.8 V float settles at no current. The segment is a function of the iterate, never stored, so nothing about it is in the `sim` bag. The state of charge still clamps at 0 and 1 for a source that forces current through the cell regardless (a reversed supply in CC, a charger above gassing).
- **A DIN PSU counts a limit only on a solved island.** On an unsettled island (`nonConverged`) its limit is no overload: `phaseTicks` stays frozen and nothing hiccups, as a meter would show the island as unsettled. The test shorts the PSU and hangs a never-settling load across the same terminals, because a current-limited source alone fixes its current and so can't be unsettled by a current-dependent load.
- **Events are canonical per delivered batch, not across batches; a batch ends at every command.** `takeEvents` sorts what it delivers (`compareSimEvents`: tick, entity, kind), so a host that drains after every command sees, at one tick, a later command's island event before an earlier-sorting one from the next batch. The sim worker keeps exactly headless's batches whatever the wall-clock throttling (F2.3b): the runner (and `FakeSimWorker`) cut the engine's events before applying each command (`cutEvents`) and post the cuts, concatenated, with the next publish, so never re-sort an `events` message or merge pending events across a command (a time-driven event that changes no topology, so no forced publish flushes it, would swap with a command's at the same tick; `runner.spec.ts` pins it under throttled, per-chunk and in-between timings). The source replay property compared such a live concatenation with a replay's single batch and failed about 1–3 % of fresh seeds (seed 682033826: `nonConverged` for entities 8, 9 from one batch, then 6, 7 from an undone delete's): the engine emitted the same events, in the same order, on both sides, and the island numbering was identical (the snapshots matched). Compare a per-command drain with one batch after sorting it, which is exact because the sort is stable; a regression test pins that seed's session.
- **Allocation gates per source, and for mixed worlds** (`allocation.spec.ts`, uncovered; worst baseline median of 100 runs under load, measured in place): the battery's DC path (1.04; gate 4), the DIN PSU regulating (0.59; gate 6), shorted, in limit and hiccuping (1.70; gate 6, from 10.5), hiccuping into a heating load (0.73; gate 6, new: a 2 Ω cold load asks 12 A of the 5 A supply, so it limits, switches off and retries into a load whose resistance moved), the AC path (1.09; gate 6, from 36), a mixed DC world (0.00; gate 6: a battery into a load whose resistance rises with its current, a DIN PSU hiccuping into a heating load, a bench supply in current limit into a rheostat) and a mixed AC world (3.40; gate 6: the AC source into a reactor and into a heating load, and since F2.4 part 2 a split-phase and a 208Y/120 V service each into a heating load), and the split-phase service with series inductance into a heating load (F2.4 part 2; 0.50 over 100 runs on the part 2 tip, where the other baselines were within 1 B/step of these; gate 6, from 38). The mixed worlds exist because the game's worker runs every kind in one process, and a per-source gate's world never shows the call sites that polymorphism (the F2.5 loads measured 70–96 B/step beside the other gates, 0.2–0.8 alone). They are two worlds, not one, for the cost: V8 keeps type feedback per call site, shared by every engine in the process, so two worlds see the same polymorphism as one, at about half the work each; and they measure eight 2 000-step windows after an 80 000-step warm-up, because the gates before them have already tiered up their call sites (measured: at 20 000 and 40 000 the windows still caught tier-up, from 80 000 they read steady over 150 runs). A planted 8 B/step in `SimEngine.step` (a one-field object every fourth step) failed every gate in all 30 runs (lowest readings 8.1 against gate 4, and 7.5 against 6).
- **A source's series inductance needs a series resistance.** `AcBranchValues.vsource(…, ohms, henries)` refuses L > 0 with R = 0, so a zero-ohm source is still exactly a zero-impedance one and the structural singular check (a loop of zero-ohm sources) stays exact. Every real transformer and alternator has some resistance; give a model one rather than relaxing the check.
- **A new stamp value needs the stamp, the program and the floor helpers together.** The source's jωL is on the source row's diagonal (`VALUE_Z`: R real, ωL imaginary, from the `yIm` slot computed each solve), in `stamp` and in `assemble`, and in `testing/ac.ts`'s source rows, rounding terms and reactive-power balance (`sourceImpedance`). Planting a sparse path without it, or a helper without it, each failed a test; a missed one would compare a wrong solver against a wrong check.
- **Utility impedance comes from kVA and %Z, never a table.** Z_base = V_LL² / S on the source's own base, with V_LL = √3 · V_LN (`Math.sqrt`) for wye, never the 208 or 480 name. The split-phase halves each take half the full winding's impedance, so a line-to-neutral bolted fault equals a line-to-line one; real centre-tapped transformers give a higher L–N fault (about 1.5× is the usual rule of thumb). That is acceptable while P2's services are headless with no protective devices. The simple model that gives both is a T-equivalent: Z_full / 2 in each line plus a neutral branch Z_n = Z_LN − Z_full / 2, with the half-winding R_LN = 1.5 R and X_LN = 1.2 X per-unit on the 120 V base, so Z_n is negative (about −0.125 R − j0.2 X, fine in a passive phasor network) and I_LN / I_LL ≈ 1.5 (8.2 kA against 5.2 kA for the 25 kVA unit); mutual coupling between the halves would do as well. **P4's service entrance must adopt one, with an I_LN / I_LL ≈ 1.5 test.** The resistor stamp's validation (R > 0) refuses the T-equivalent's negative neutral R: permit it for an AC island's internal source branch, or use coupled halves. The generator stub inherits the same abstraction. The bolted fault currents are transformer-limited (an infinite primary): an upper bound.
- **A bolted fault in a test needs a bolted connection.** A 1 m test lead (41 mΩ) is as big as a service transformer's impedance (11.5–46 mΩ), so the fault goldens use the test busbar link (`BUSBAR` in `@controls/sim-core/testing`: 1 mm of 1000 mm² copper, no contact resistance, 17 nΩ). Don't add a zero-ohm lead: a zero-ohm resistor isn't a valid stamp.
- **The battery's and supplies' records are in the protocol table** (`DEVICE_OUTPUT_SCHEMAS`, protocol 3, F2.3b; the lamp's, resistor's, heater's, fuse's and breaker's since protocol 4, F2.5), and `outputs.spec.ts` requires `BUILTIN_DEVICE_OUTPUTS` to equal it exactly: a model that adds or changes a record registers it there and bumps `SIM_PROTOCOL_VERSION` in the same PR. The AC services publish no record, and `NOMINAL_BANDS` still has only `none` (choosing a band from the sources is open). Read a service's voltages with `game.probe` (RMS magnitude by default; any angle is the scripting API's display-only `phaseDeg`).
- **A precomputed winding is copied, not rebuilt, at each solve.** An AC source bank works out each winding's EMF phasor, R and L once at bank build (through `vsourcePolar` into a scratch value set, so they are validated) and copies them into the value arrays at each solve; building them per solve allocated a phasor unit object and boxed doubles (41 B/step on the service's allocation gate). The source row's R + jωL is likewise added in place on the dense path, not through `add`. Allocation gate for a split-phase service into a heating load: see "Allocation gates per source".

### The sim worker and transport (F2.3b)

- **The worker must apply commands solve for solve.** It runs each logged entry through `replayEntries(bus, [entry], {time: engine})`, one at a time, at its tick, exactly as a headless replay does; never batch a tick's commands into one recompile (a nonlinear island's warm start would differ, the engine-loop caveat above). The runner property in `runner.spec.ts` compares its bytes with the headless `Game` after random sessions, both transports, any slicing.
- **Chunks end on cadence boundaries.** `runTo` steps the engine to the next multiple of `SOLVE_INTERVAL_TICKS`, then checks the slice and the publish throttle. Which ticks get published depends on wall time; the bytes of a tick's snapshot never do. Never read the worker clock anywhere but `pacing/worker-clock.ts`, and never let a reading reach the engine.
- **A publish whose encoding throws is never seen.** `SnapshotWriter.publish` leaves the slot's word odd if `encode` throws, so readers keep the previous slot; the runner then reports `engine-threw` and the host terminates the worker.
- **The reader's copy is double-buffered.** A copy is made into the back buffer and swapped in only when accepted, so a slot held back for its descriptor (`awaitingDescriptor`) never disturbs the view listeners hold. Don't "simplify" it to one buffer: the previous view would show the rejected slot's bytes.
- **`encodeSnapshot` must never write slot bytes 0–3 except with the `slotSeq` it is given.** The writer makes the seqlock word odd before calling it; an earlier `slot.fill(0, 0, used)` zeroed the word, so it read even (complete) for the whole encode, and a lapped reader accepted a half-written slot (#57 review). The fill starts at byte 4. `transport.spec.ts` watches the word through every step of a publish and checks the writer's Atomics order (word odd, encode, word even, `latestSlot`, then `publishSeq`); both mutants fail it deterministically.
- **A torn read can't be produced in one thread by publishing during the first load.** Publishing twice before the copy gives a consistent (newer) slot, so a reader without the second check passes such a test. `transport.spec.ts` starts rewriting the slot being copied after the reader's first load and finishes it before the second (the planted "no recheck" mutant fails it). It also runs the **real** `SnapshotWriter` and `encodeSnapshot` on a worker thread (bundled from the sources with esbuild, `eval: true`), counts only fresh reads (`stats.reads`, at least 20) and checks each is whole and never older than the `publishSeq` loaded before it.
- **A replay start goes through the inbox.** Its entries and its final `advance` are queued like live messages, so a long restart log is sliced and published as it runs instead of blocking the worker; its sim events are dropped (`quietThrough`), as a headless replay drops them.
- **`release`, `watch`, `unwatch` and `stop` bypass the inbox.** A `release` queued behind a long `advance` would starve the fallback's three-buffer pool for its whole length.
- **`SimHost` re-anchors after any advance it didn't make.** A `sim.step` (or a script's advance) is not capped by the lead, so the worker may need time to catch up; pacing re-anchors at the new tick, so time doesn't jump when the worker gets there, and keeps running (supervising the catch-up and the watchdog) while the commanded tick is ahead of progress, even at speed 0.
- **The watchdog measures liveness, not snapshot cadence.** It crashes the worker when the commanded tick is ahead of progress and nothing has been heard from it for `WATCHDOG_MS`: `SimLink.lastHeardWall` is refreshed by any message and by any accepted publish (a shared-buffer publish is no message). It is held while suspended or held. A busy worker is never silent that long: the runner drains its inbox in `WORK_SLICE_MS` slices, a burst of commands included (it used to drain one in a single task, publishing only when idle, so 1,250 commands on a loaded machine read as a hang), and at a slice's end republishes if it hasn't for `LIVENESS_PUBLISH_MS` (500 ms). Only a single message taking longer than `WATCHDOG_MS` can still trip it. The idle publish (on reaching the target) keeps a paused sim that has caught up from ever tripping it. No message was added, so no protocol bump.
- **A load is verified by `planLoad`, the same rule as headless.** `MAX_VERIFY_TICKS` is applied before any replay start is sent (`load.spec.ts` checks a too-long log never reaches a worker), so the worker never verifies a log the headless load wouldn't.
- **The read's time is reported, its allocation gated** (`docs/architecture/rendering.md`): `sim bench`'s `snapshot-read-500-devices` reports p50/p99 (p99 about 11–18 µs, against ADR 0011's 0.1 ms) and fails `verify` if a frame's read allocates 1 B or more. A renderer reading many fields should use `readAll` into a reused `Float64Array`; a `read` per field is allocation-free only while V8 inlines it. How `bytesPerRead` measures, and why: a single window's figure includes the profiler's own fixed cost (several bytes a read at 5,000 reads), so it takes slopes between window sizes; the first windows of a process carry a one-time cost of about 17.7 kB, so one window of each size is discarded; a one-off step of about 11 kB turns up now and then in one window size, so it keeps the smaller of two independent slopes (N→2N, 2N→3N), which any real per-read allocation raises both of. The 20,000-read warm-up is what lets the read reach optimised code; with 5,000 a fresh process's first measure can read 4 B. The spec's small check (`bytesPerRead(rig, 1_000, 2)`) keeps the full warm-up.
- **Specs that need the runner use `RunnerHarness`** (`libs/sim-worker/src/testing/`): a manual task queue for the yields, a fake clock (`msPerRead` makes work take wall time), and the host side of the protocol, parsing every message the runner sends with `WorkerToHost`. `minSlotBytes` makes a buffer growth cheap to provoke.
- **`netlist.dump` must stay a pure function of the materialised world** (F2.6). It starts a throwaway `SimEngine` on the world and formats from it, so headless and the game agree by construction. Never add to it anything the world doesn't hold (wall time, the topology generation, a live engine's caches), and never call `islandDiagnostics()` from a hot path: it runs the value pass and allocates. A loaded engine's adopted record has no value pass behind it, which is why `islandDiagnostics()` runs one; a mutant that skips it is caught by `dump.spec.ts`'s loaded-engine case (an unwired lamp's `unvalued` branch).
- **Changing `formatNetlist`, the solution record or a band moves the `netlist.dump` goldens** (`apps/sim-cli/src/goldens/netlist-dump/*.txt`, asserted from Chromium by `apps/game-e2e/src/netlist-dump.spec.ts`). Re-pin with `pnpm nx test sim-cli -u` and read the diff; the e2e reads the same files, so they never disagree on purpose. Engine 5 (F2.5) moved two: in `bench-leads` and `sim-step` the lamp's island went from `unmodelled … unvalued 1` to `solved`. F2.5 added `bench-lamp.txt` (the end of the bench demo: the lamp out, its island solved at tick 1990).

### First loads (F2.5)

- **Lamp abstractions** (for `electrical-realism-reviewer`): constant emissivity and heat capacity (both rise with temperature in tungsten, so the model's steady state gives P ∝ V^1.54 where the published fit says 1.6; the bench demo checks the light within 4 % of L ∝ V^3.4 from 75 % to 115 % of rated volts); no conduction loss to the lead-in wires and supports, so a filament cools by radiation alone and approaches ambient slowly (its light is under one display step about half a second after the switch opens); no burnout, evaporation or end of life (the temperature clamps at the resistivity table's 3600 K). The 2700 K rated temperature and 50 ms time constant are game-design values inside published behaviour (the catalogue says so). The heater's resistance is constant (nickel-chromium moves a few percent cold to hot), and the resistor has no tolerance, temperature coefficient or damage model: `overRated` is a flag, nothing more.
- **The re-solve trigger must follow from the bank and the solution alone.** The lamp compares R(T) now with the resistance the last solve saw, read back from the solution as |ΔV| / |I|, never a value cached at the solve: a cache isn't in the `sim` bag, so a loaded engine would re-solve at other ticks and its snapshots would differ. Below 1 µA (`LAMP_RESOLVE_MIN_A`) it never asks, since a gmin-level current's |ΔV| / |I| is rounding. The 1 % tolerance (`LAMP_RESOLVE_RELTOL`) is numerical: halving it doubles the warm-up solves and moves the inrush trace by well under 1 %.
- **A continuous re-solve never recompiles.** A continuous layer returning `true` (`SimDeviceBank.continuous`) re-solves at t + 1 with the same netlist (`stats.continuousSolves`); only the protection and discrete layers may change the topology. A model that needs a topology change from its continuous state must move it to the protection layer.
- **The 1 ms tick overstates a cold lamp's inrush I²t by about 11 %** (`electrical-realism-reviewer`, F2.5; decided: recorded, no sub-stepping in P2). In the first tick the filament gains about 200 K, but the step holds the cold current for the whole millisecond: on the bench lamp (12.9 V behind about 0.05 Ω) ∫I²dt over the warm-up is 0.159 A²s at the 1 ms tick against 0.143 A²s at 1e-5 s. The peak ratio and the 90 % warm-up time (118 ms against 120 ms) are unaffected, and it is far from the 1 A fuse's 0.7 A²s; but a later fuse sized close to a large lamp's inrush would see it as nuisance-blowing margin. Sub-step the lamp ODE while its temperature moves fast before a job depends on it.
- **The filament is frozen on an island that isn't a reading** (the validity rule): unmodelled, mixed, singular or non-converged, the current is unknown, so the lamp is neither heated nor cooled, as the battery's coulomb counting is. Its record's `status` says so, and `lightOutputRel` is then the frozen filament's, not a reading of the circuit: never draw such a lamp as dark.
- **A lamp is no longer unmodelled.** Engines 3 and 4 recorded every island holding a lamp as unsolved; since engine 5 it is solved, which moved `SIM_STEP_HASH`, `SIM_STEP_SNAPSHOT_HASH` and `BENCH_LEADS_HASH`. A test that used a lamp to get an unmodelled island needs another way (a synthetic kind in `src/testing/`).
- **`filamentTempK` is null until the engine first runs the lamp.** A newly placed lamp, and a lamp in a save from engine 4 or earlier, has `filamentTempK: null`; the bank starts it at the bench's 20 °C (`LAMP_AMBIENT_K`) and writes it back on the next export. A hand-built world without the key (the bench plant's `sim: {}`) gets the same.
- **No `dmath` yet.** The plan expected the lamp to be `dmath`'s first use; it needed no transcendental (x^(17/8) = x² · ⁸√x with `Math.sqrt`, tungsten piecewise linear, explicit Euler, T⁴ as two multiplications). ADR 0014 stays deferred to the first real transcendental. The determinism lint already bans `Math.pow`, `Math.exp` and `**` in `sim-core`; a fractional power that reduces to square roots (as 17/8 does) needs no `dmath`.
- **A ternary between a closure constant and a computed double boxes.** `next > maxK ? maxK : …` in the lamp's per-tick path, where `maxK` was a double captured by the closure, made V8 box the result into a new heap number every step (16 B/step on the allocation gate). `Math.min(maxK, Math.max(ambient, next))` doesn't. Look for this before raising a gate.
- **No loops over a constant table in the per-tick path.** A search over the tungsten table each step showed up on the gate too (16 B/step); the lookup is now by bucket, from typed copies of the table (a frozen array of doubles holds them boxed).
- **F2.5's allocation gates run in their own file** (`engine/allocation-loads.spec.ts`, with a copy of `allocation.spec.ts`'s profiler sampling; the settling rule is shared, `engine/allocation-settle.ts`, Node-free and unit-tested in the covered run), uncovered, beside F2.4's in `vitest.allocation.mts` (the second half of sim-core's `test` target, still in `pnpm verify`). Appended to `allocation.spec.ts`, after the sources' gates, a lit lamp once measured 70 B/step, all in `solveIsland`'s frame (the polymorphic-call-site regime above, not the lamp's code). A lit lamp is 0.70 B/step at worst (gate 1; worst median of 100 uncovered runs under load). Fold the two files' helper together once F2.4's allocation work has settled.

### Protection (F2.5 part 2)

- **The fuse has two thermal bodies; the breaker one time constant** (the realism review; the two-body fuse decided by the user). The fuse is a fast element (share w = `elementFraction` of the steady rise, time constant τ_e) inside a slow body (τ_b = `bodyTimeConstantS`), each a first-order lag towards its share of (I / I_min)², melting at θ_e + θ_b ≥ 1 (sim keys `elementHeat`, `bodyHeat`). τ_e is never in the catalogue: it follows from the melting I²t, τ_e = w / (I_min² / I²t − (1 − w) / τ_b) (0.151 s for the bench fuse), so the adiabatic end still melts when ∫I² dt reaches the datasheet's I²t, and `FuseParams` refuses parameters for which the slow body alone would reach it (τ_e ≤ 0). A single body melted the bench fuse in under a second at 135 %, far faster than a real fast-acting fuse; with the slow body it takes 12.05 s. The breaker's bimetal stays one lag, dθ/dt = ((I / I_n)² − θ) / τ, tripping at θ ≥ k_u² (its case's slower mass is left out, so its long-overload end is shallower than a real breaker's). Neither has a tabulated curve, and `ln` and `exp` appear only in the specs' hand calculations (D6). These are abstractions to keep, not curves to tune per point: the tests check the catalogue's own band at fixed multiples.
- **The documented figures are computed by a test.** `protection.spec.ts` ("the documented figures") works out the fuse's τ_e and melt times (12.05 s at 135 %, 0.908 s at 200 %, 0.1072 s at 300 %, 7.16 ms at 1000 %) and the breaker's trip times (116.84 s at 135 %, 29.72 s at 200 %, 3.872 s at 500 %) from the models, so a parameter change that moves them fails until the docs and citations are changed with it. The fuse's band has lower bounds as well as upper ones (carries 110 %; 135 %: 1 s–1 h; 200 %: 0.1–5 s; 1000 %: 1–20 ms), so a fuse that got much faster fails too.
- **Never below the threshold.** A fuse carries anything below I_min (θ_e + θ_b settles at (I / I_min)² < 1) and a breaker anything up to k_u I_n: exactly 125 % never trips, because θ approaches (I / I_n)² from below and the trip is θ ≥ k_u² (tested on the bank with an exact 18.75 A, since a solved current is only good to its solve). The catalogue schemas hold `minimumFusingRatio` in (1, 1.35) and `ultimateTripRatio` in (1, 1.35] (both above the rating, within the UL envelopes' 135 %), and the magnetic band above k_u. Don't widen them to fit a test.
- **A bolted short blows or trips in its first tick.** A current that takes θ_e + θ_b past 1 in one Euler step blows the fuse in that step, and a breaker trips magnetically at the first solve above its pickup; either re-solves within the step (`simTopologyKeys`), so the fault current is never integrated for a second tick. Neither models arcing or a clearing I²t (the clearing integral is the melting one), nor an interrupting or voltage rating (P4, P5): a 1 A glass fuse "clears" a utility's bolted fault here.
- **The magnetic pickup is drawn once per bank build, from the entity's stream.** The pickup is exactly I_n (min + (max − min) u), 120 + 60u A for the 15 A breaker, with u the first `deriveStream(world.seed, entityStreamKey(id)).nextFloat()` (pinned: seed 11, entity 2 gives 131.1838614474982 A). It is the same at every rebuild, after a load and on replay, and never consumes a shared stream, so two breakers draw independently and deleting one leaves the other's pickup alone. It is the same on AC and DC (a real AC breaker's DC pickup is typically higher); a different draw count or order would move every breaker's pickup, so treat it as a determinism change. It isn't stored in the `sim` bag because it follows from the seed and id alone; it is in the record (`magneticPickupA`).
- **Reset needs the `commanded` hook, not a command reading sim state.** `device.operate` never reads `tripped` (ADR 0011 §1). Turning the handle off clears `tripped` inside the engine: `SimEngine.applied` calls `SimDeviceBank.commanded(index, state)` for each netlisted device whose commanded `state` bag the command replaced (by reference, against the previous world), **before** the recompile, so the netlist compiled at that tick already sees the reset and an off-then-on at one tick closes the breaker. A new model whose commanded state resolves sim state should use the same hook; don't infer it in a layer, which would run a tick late. The hook is skipped for a device with no bank (not netlisted) and is not called for a bank build (which reads `SimDevice.state`). **It must be idempotent:** it may be called with a bag equal to the last one it saw (a command setting a control to the value it already had, or changing another key), and the same bag twice must leave the bank as once (`device-model.ts`, tested).
- **Undoing a handle-off after a trip leaves the breaker reset, and it closes.** The sim resolved the off when it ran: undo restores the commanded `on`, not the sim's `tripped`, so the handle goes back on and the breaker closes, re-energising the circuit (player-visible: trip, handle off, undo, and the load is live again; tested). This follows from commands never touching sim state (and `commanded` only ever clears `tripped`). Don't "fix" it by having undo restore sim bags. A save holding `tripped` with the handle off, which the engine never writes, likewise starts reset (at the bank build).
- **The sim never writes `on`.** A tripped breaker keeps its handle where the player left it (the record's `state` says `tripped`). Anything that shows the handle (the renderer, the inspector) must read the record's `state`, not `on`, to show a trip.
- **Frozen on an island that isn't solved, cooling while open.** On an unmodelled, mixed, singular or non-converged island the current is unknown, so neither of the fuse's bodies nor a closed breaker's bimetal moves (the validity rule, as the lamp's filament). An open breaker carries exactly no current, so its bimetal cools; a blown fuse keeps its last `elementHeat` and `bodyHeat`. Either open device reads `solved` with 0 A.
- **Other abstractions** (for `electrical-realism-reviewer`): constant link and contact resistance (both rise with temperature), no ambient-temperature compensation or derating, no pre-damage from repeated overloads below I_min. The breaker's contact resistance is 10 mΩ (2.25 W, about 150 mV at 15 A, from manufacturers' watts-loss figures of about 2 W per pole at rating). The UL 489 (135 % for ratings up to 50 A, 200 % up to 30 A) and UL 248-14 envelopes are paraphrased in the catalogue citations.
- **No recipe yet.** The renderer has no fuse or breaker recipe, so both draw as the unknown cube until one lands.
- **The 135 % breaker trip is too slow under coverage.** 117,000 ticks: it is in `apps/sim-cli/src/breaker-curve.spec.ts`, outside instrumentation, like the battery hour; sim-core's `protection.spec.ts` keeps 200 % and 500 %.
- **Allocation gates** (`allocation-loads.spec.ts`, after the lamp's; uncovered, worst median of 100 runs under load): a fuse carrying a lit lamp 0.28 B/step and a closed breaker carrying 1.3 A 0.64 (gates 1); every F2.5 kind at once in one engine (four solved islands) 2.14 on F2.4's mixed-world windows, 8 × 2,000 steps after an 80,000-step warm-up (gate 2.5). Each layer alone, on its bank with a fixed solution, measures under 1 B/call (a planted 16-byte object a call reads 48–64). Every test in the file finishes in well under a second uncovered; the per-test timeouts are Vitest's defaults.
- **Don't A/B a device inside the engine for allocation.** Swapping the fuse or breaker for a passive resistor in the same engine was tried (test review) and rejected: the solver's regime flips between about 0 and 7 B/step from one gate to the next in a process, so over 140 runs the difference read −0.9 to +5.7 B/step for the fuse and −7.0 to +1.3 for the breaker. Measure a layer on its bank alone, as the last test does.
- **Every single-island gate warms up for the full 100 000 steps.** A 20 000-step warm-up was tried for the gates after the lamp's: the fuse's median read 19.8 B/step, still tiering up. Run uncovered (`vitest.allocation.mts`) each takes about 0.1–0.2 s. The mixed world follows F2.4's mixed-world method instead (8 × 2,000-step windows after 80,000 steps, measured in place), about 0.15 s.
