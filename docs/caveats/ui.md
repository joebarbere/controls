# UI caveats

**Load this when:** working on `apps/game`, `libs/ui`, `libs/features/*` (shell, workspace, settings, palette, session, console, saves), keyboard handling, focus, dialogs, theming, or Angular component tests.

- **The UI never mutates the world.** World changes go through `Session.exec` (`@controls/feature-session`, F1.2). Navigation, open dialogs, panel layout and notifications are UI-only state in signals (`ShellState`, `NotificationService`). Settings are player preferences edited through `SettingsStore`, not Commands. A UI action the plan names as a command is a **view command**: the button calls `session.exec('view.resetLayout')` and the owning component applies the effect in `session.onCommand(...)`, so the palette, keybindings and console reach the same code (see [commands caveats](commands.md)). Viewport gestures are the same pattern (F1.7): the renderer emits intents and `Viewport` runs exactly one `entity.place` / `entity.move` per commit through `Session.exec`. Keys reach commands only through `KeybindingService` (below).
- **Angular libs run their tests with `@angular/build:unit-test` pointed at the app's build** (`"buildTarget": "game:build:development"`, plus the lib's own `tsConfig`). The Nx generator's `vitest-angular` runner refuses non-buildable libs, and making every lib buildable would add ng-packagr. Lib `test` targets list `{workspaceRoot}/apps/game/project.json` as an input, so a change to the app's build options re-runs them. New Angular libs: generate with `--unitTestRunner=none`, then copy a `project.json` `test`/`typecheck` block and a `tsconfig.spec.json` from `libs/ui`.
- **Component tests use `@testing-library/dom` role and label queries** (`screen.getByRole('button', { name: 'Back' })`) with `@testing-library/user-event`, mounted with `TestBed.createComponent` and appended to `document.body`. Both are dev-only. If a query can't find a control by role and name, the control is probably not accessible, so fix the markup rather than the query.
- **jsdom gaps that bite here:** no `HTMLDialogElement.showModal`/`close` (`ctl-dialog` falls back to toggling `open`), no layout (so `checkVisibility` is skipped and closed `<dialog>`s are still "present"), `focusin` has no `relatedTarget`, and user-event doesn't send `pointerenter`/`pointerleave` to ancestors. Specs fire those events by hand; the Playwright suites cover the real behaviour. Never weaken production code to suit jsdom.
- **Dialogs are native `<dialog>` + `showModal()`** (`ctl-dialog` in `@controls/ui`). The browser makes the page inert and handles the top layer. The component adds initial focus (`[autofocus]`, else the first tab stop), Escape that keeps `[(open)]` in sync (the native `cancel` event is prevented), a focus trap and focus restoration to the opener. Content stays in the DOM while closed. The **about box relies on this**: the `about-*` test ids are read at boot by both e2e suites while the About dialog is closed. Keep them in the DOM.
- **Closed dialogs stay light.** Because content stays mounted, a big closed dialog costs on every page, not only when open. The Key bindings dialog (~94 buttons, ~350 elements) was always in the shell, and `getByRole(…, { name })` checks each candidate's visibility with jsdom `getComputedStyle` up its ancestor chain, uncached after any DOM change. Each query in `app.spec.ts` cost ~250 ms, so every menu ↔ workspace step in a test looked slow. The transition itself is ~15 ms. A macOS CI runner under `run-many` load pushed "Escape to the menu, Resume" past Vitest's 5 s (run 40989542950). `KeybindingsDialog` now renders its editor only while open (`@if (open())`). The query dropped to ~70 ms and the test from ~850 ms to ~390 ms. `SettingsDialog` does the same for `SettingsForm` (about 110 elements; its state is `SettingsStore`'s, so reopening shows what is stored, and the dialog still focuses the checked theme radio). Heavy content that needs no state between openings goes behind `@if (open())`. `settings-dialog.spec.ts` pins this. When a jsdom test is slow, profile before splitting it: `process.getBuiltinModule('node:inspector/promises')` from inside a spec profiles the test worker (`NODE_OPTIONS=--cpu-prof` misses it), and the hot path is usually `computeAccessibleName` → `isHidden` → `getComputedStyle`. Never raise the timeout. `hidden: true` is not a fix either: it changes what the query asserts.
- **Don't find table rows with `getByRole('row', { name })` in big tables.** A row's accessible name is computed from its whole subtree, for every row, on every query, and each DOM change throws away jsdom's style cache. In `keybindings-editor.spec.ts` that cost about 1.1 s per test locally and timed out on a Windows runner. Find the row header instead, `getByText(/^Title/, { selector: 'th[scope="row"]' }).closest('tr')`, then query inside it with `within(row)`. That spec went from about 4.75 s to 0.75 s.
- **Scope shell queries to a landmark in `app.spec.ts`.** Testing Library computes the accessible name of every candidate before it drops the hidden ones, so an unscoped `screen.getByRole('button', { name })` in the shell also names the buttons inside the closed dialogs (12 of the 17–21 in the page). Each name is a jsdom `getComputedStyle`, and each element's first one scans every stylesheet rule (about 180 once the console's CodeMirror styles are in). A button query cost 130–450 ms locally, so the F1.8b autosave test, with four of them, reached 5.5 s on a macOS runner (PR #67) after F2.3b's sim controls added buttons. The sim, saves and hashing were under 5 % of its profile. Query menu items through `mainMenu()` (`within` the `Controls` navigation), toasts `within` the `Notifications` region and dialog buttons `within` their dialog, and reuse a handle the page keeps (the workspace `Menu` button is the same element each time the toolbar shows). CodeMirror's style-mod keeps one `<style>` (about 80 rules) in `<head>` for the life of the document, so it leaked from the first console test into every later one; `app.spec.ts`'s `afterEach` detaches it (style-mod puts it back when the next editor mounts). With `SettingsForm` behind `@if (open())` as well, the spec's sum of medians went from 5.6 s to 3.3 s and the autosave test from 714 to 389 ms (median of 10 under coverage). Scoping adds to what a query asserts: never use `hidden: true` instead.
- **macOS CI runners vary about 5× in speed, so budget a jsdom test for the slow one.** On PR #75 the 389 ms autosave test took 5.4 s on macOS and timed out. It was not a wall-clock wait. That job's `run-many` took 9 min 49 s, against 1 min 45 s to 5 min 39 s for the three green macOS runs before it, and every app test in it was 4–14× its local time. Locally, on one core shared with six busy loops (about a 7× CPU squeeze), every step of the test slowed in proportion and none had a fixed floor. Keep each app test to one flow and well under 0.5 s locally: the autosave and save-by-name flows are now two tests. Go to the menu as a player does, with Escape from the viewport (the viewport consumes Escape only to cancel or deselect), rather than querying the `Menu` button. To show that something did _not_ happen after an async step, await the next serialised call (`await saves.autosave()` resolves after the menu's own autosave has decided) rather than waiting. To reproduce a slow runner: `taskset -c 0` on the test command plus a few `taskset -c 0 sh -c 'while :; do :; done' &` loops.
- **A radio group is one tab stop.** `focusableElements()` returns only the checked radio of a named group (or its first one). Before this fix, Shift+Tab from a checked radio escaped the settings dialog's trap. Any custom focus code must use `focusableElements()` rather than a raw selector.
- **Escape is layered.** A dialog handles Escape first and calls `preventDefault()` + `stopPropagation()`. The app's document-level handler (`App.onEscape`) ignores handled events: it opens the menu from the workspace and resumes from the menu. Keep the "inner handler wins" rule, or Escape in a dialog will also open the menu. **On the canvas, Escape cancels before it clears.** The order is: cancel a move, cancel placement (the tool is put away with `ToolBelt.clear()`, no command), clear the selection, then the menu. The renderer calls `preventDefault()` on a triggered input action only when it did something (`onTrigger` returns `true`), so with nothing to cancel or clear Escape falls through and opens the menu. A test that picks a tool and then expects Escape to open the menu must press it twice. The palette (a dialog) and the console (CodeMirror's keymap) handle their own Escape before any of this, and closing them leaves an armed tool armed (`placement.spec.ts` checks the whole order). Escape stayed in `App` in F1.4 rather than becoming a binding: it is the fixed "back" key, and the keybinding service reserves it (with Tab and Shift+Tab) so no rebinding can strand a keyboard user.
- **One document `keydown` listener runs commands: `KeybindingService`.** Don't add per-component shortcut handlers for anything that is a command; add a `keybinding` to its `CommandDef` (or a fixed-argument binding like `toolbelt.select.slotN`). The service ignores `defaultPrevented` events, so an inner handler that consumes a key must call `preventDefault()`. It is created by injection: `App` injects it so the listener exists from start-up. A component spec that needs keys to run commands must inject it too.
- **Typing never runs commands.** In an `<input>` that takes text, a `<textarea>`, a `<select>`, `contenteditable`, a CodeMirror editor (`.cm-editor`) or any open `<dialog>`, only `globalKeybinding` commands fire (`palette.open` and `console.toggle`). Checkboxes, radios, ranges and buttons don't count as typing. jsdom has no `isContentEditable`, so that branch is covered by Playwright only. A global binding also swallows its key in text fields: backtick can't be typed in the console (or any text field while the console is available) unless the toggle is rebound.
- **Key capture must stop the event at the button.** The Key bindings dialog's Change button calls `preventDefault()` and `stopPropagation()` on every captured key, so Escape cancels only the capture (not the dialog) and the captured chord never reaches the keybinding service. Tab is let through (reserved for focus) and cancels the capture on blur. Inactive buttons use `aria-disabled`, not `disabled`: a button that turns `disabled` under focus drops focus to `<body>`, outside the dialog.
- **Nested dialogs are siblings.** `ctl-keybindings-dialog` sits next to the settings `ctl-dialog` inside `SettingsDialog`, not inside it, so the outer dialog's Escape handler and focus trap never see the inner dialog's keys. `showModal()` stacks them in the top layer. Use `linkedSignal`, not an `effect`, to reset the inner dialog's open state when the outer one closes.
- **`@for` over short string lists tracks `$index`.** Tracking a one-key list by identity re-creates it on every rebind and logs NG0956 in dev builds (seen in the e2e console).
- **Don't name outputs after DOM events** (`toggle`, `resume`, `close`, …): `@angular-eslint/no-output-native` fails lint. Use `collapseToggle`, `resumeGame` and so on. Keyboard handlers for non-focusable containers go in `host` listeners, not on a `<nav>` or `<dialog>` in the template (`interactive-supports-focus`).
- **Theming is `light-dark()` tokens** in `libs/ui/src/styles/_tokens.scss`, loaded once through `apps/game/src/styles.scss`. `:root` has `color-scheme: light dark` (it follows `prefers-color-scheme`). The settings override sets `data-theme="light|dark"` on `<html>`, which pins `color-scheme`. Reduced motion follows the schema's `display.reducedMotion`: `system` uses `prefers-reduced-motion`, `reduce` (`data-motion="reduce"`) forces it on, and `full` (`data-motion="full"`) overrides the OS preference. Reduced motion zeroes `--ctl-duration` and clamps animations. Use the tokens; never hard-code colours or durations in a component.
- **Visible focus is global** (`:focus-visible` outline, 2 px, `--ctl-focus`). The keyboard e2e asserts `:focus-visible` plus an outline of at least 2 px on every step, so don't remove outlines in component styles. Don't make a container around a positioned canvas focusable: the canvas paints over the container's outline (the F1.1 viewport region did, before F1.7 made the canvas focusable). The viewport has **one** focus target, the canvas, with an inset outline; the "3D viewport" region is a landmark without `tabindex`, and `Workspace.focusViewport()` focuses the canvas.
- **The workspace is always mounted.** Behind the main menu it runs with `[chrome]="false"` (viewport only, as the menu backdrop) and is `inert`. That keeps `ctl-viewport` booting at start-up, which the e2e suites rely on (`data-status="ready"`), and avoids recreating the WebGPU context on every New sandbox.
- **`Viewport` lives in `feature-workspace`** (moved from `apps/game` in F1.1). It is owned jointly with `renderer-engineer`: keep its outputs, `data-*` host attributes (F1.7 added `data-placing`, `data-placement-ref`, `data-placement-valid`, `data-placement-target`), the `?e2e=1` hook, the dev frame-time HUD and the crosshair stable. It reads the active prop from `ToolBelt` plus `SettingsStore` (`toolBelt.slots`), so `feature-workspace` depends on `feature-settings`. It also publishes the viewport context keys (`mode`, `selection.*`); only it should set them. Its mode and selection readout is the shell `ctl-hud` (fed from `Workspace.viewState()`), which keeps the `viewport-status` test id that `apps/game-e2e/src/viewport.spec.ts` reads.
- **The sim-time HUD takes clicks over the canvas** (F2.3b). At the web suite's 960 × 540 the bench framed by `focus('bench')` puts the bench-lamp switch under the speed radios, so a real double-click there hits the HUD. A spec that aims the mouse at a device checks `document.elementFromPoint` is the canvas (`pointOver` in `bench-lamp.spec.ts`) and pins 1280 × 720.
- **The viewport's lamps follow the sim snapshot, not the world** (F2.5): `LampSnapshotFeed` (`feature-workspace`) is a `SimHost.subscribe` listener, so a lamp redraws as the worker publishes, while time runs; the world signal and commands don't drive it. Its map is updated in place (the renderer re-reads it on every call). A `null` view (no game, a crash, a restart, a new generation's descriptor not yet in) is every lamp unknown.
- **Viewport e2e tests must start a sandbox first.** At boot the workspace is `inert` behind the main menu, so the canvas can't take focus and clicks hit the menu. `viewport.spec.ts` clicks New sandbox in its `open()` helper; new viewport tests should do the same.
- **CSP:** no inline event-handler attributes and no runtime template compilation. Angular's `[style.--x]` bindings go through CSSOM, which `style-src` doesn't restrict for script-set properties, and component styles need the existing `style-src 'unsafe-inline'`, as do CodeMirror's `<style>` element and the inline `style` attributes it sets (ADR 0008). `desktop-e2e` records `securitypolicyviolation` events while it drives the menu, a dialog and the workspace; keep that assertion when adding UI.
- **Settings are `Settings` from `@controls/save-format`**; never add a parallel interface. The UI converts at the edge only (sliders show whole percentages, the document stores volumes in [0, 1] and look sensitivity as a multiplier). `apps/game` provides `SETTINGS_SERVICE` from `Platform.settings` (`provideSettingsFromPlatform()` in `app.config.ts`). A spec that renders `App` must add that provider, or it silently gets `MemorySettingsService`.
- **`SettingsStore` never loses an early edit and never writes before it has loaded.** Edits made while `load()` is pending are kept and replayed on top of the loaded document, and a debounced save first awaits `loaded`. Otherwise, a slow load would overwrite the player's change, or an early save would replace a stored file with defaults. A stored file that is unusable is left alone until the player changes something.
- **`SettingsStore` flushes before quit, not on destroy.** `DestroyRef.onDestroy` never runs when Electron closes the window, so a change inside the 300 ms debounce used to be lost on Quit (and made `settings-persistence.spec.ts` flaky on macOS CI). The store registers `flush()` with `APP_LIFECYCLE` (`feature-shell`, provided from `Platform.lifecycle` by `provideLifecycleFromPlatform()` in `app.config.ts`), and `flush()` resolves only after the pending save **and** any save already in flight have settled. Any other buffered writer must do the same: register with `APP_LIFECYCLE`, and wait for in-flight writes (`SaveGames` does, for autosave; F1.8b). The token's default never calls back, so component specs are unaffected; a spec that renders `App` and needs the hook must add `provideLifecycleFromPlatform()`, and its fake `Platform` needs a `lifecycle`. In the web harness the flush runs on `pagehide`, which doesn't wait for promises: `runFlushes` calls each flush synchronously, so the `localStorage` write completes, but keep anything that must survive a tab close synchronous.
- **Capped lists must be trimmed by their writer** (palette recents ≤ 20 with no repeats, console history ≤ 200 lines × 2000 chars). One over-cap field makes `settings:set` refuse the whole document and `loadSettings` discard the whole file.
- **Projected content exists even when its slot doesn't render.** `ctl-dev-console [ctlBottomPanel]` is created by `App` at boot, although the workspace renders the bottom panel only with `chrome` on. So a projected component can't use its own creation or destruction as a signal of "the workspace is showing"; the console gets `[available]` from `App` instead, and publishes `console.available` from that.
- **`afterNextRender` waits for a render that may never come.** In zoneless Angular it runs after the next change detection, and a command that changes no signal schedules none. `Workspace.toggleConsole` focuses the already-open panel synchronously and uses `afterNextRender` only after expanding a collapsed one (the layout change guarantees a render, and the `[hidden]` panel can't take focus before it).
- **Focus targets in a docked panel are `[data-autofocus]`**, not the HTML `autofocus` attribute (the browser acts on that by itself when the element is inserted). The console's editor host has `data-autofocus` and `tabindex="-1"` and forwards focus into CodeMirror, including focus that arrives while the lazy chunk is still loading.
- **CodeMirror is a lazy chunk.** `console-editor.ts` is loaded with `import()` and imported elsewhere only as a type; exporting it from the package index or importing it statically puts about 200 kB back into the initial bundle (the 2 MB budget warns). The component's `data-editor="ready"` host attribute tells tests when it has loaded.
- **CodeMirror in jsdom** needs `Range.prototype.getClientRects` and `getBoundingClientRect` shims (jsdom has no layout), and jsdom's `Blob` has no `text()`. The console specs add them in `beforeAll`. Drive the editor through `EditorView.findFromDOM(content).dispatch(...)` for text and user-event for keys. user-event's key map has no backtick: press it by code, `[Backquote]`.
- **A file input's `click()` inside a keydown handler doesn't open the picker in Chromium** (the click happens, with user activation, but no chooser appears). Seen with Enter in CodeMirror (the console's `run`) and with Mod+O (`file.open`). Since F1.8b the web harness's Open picker (`browserPickers().pickFile` in `platform-web`) defers the click one task itself; the activation is still live then. The console's own `setTimeout` predates that and is harmless.
- **Playwright `toHaveText` on a CodeMirror input counts its placeholder.** The console has no placeholder; its hint line says what to type.
- **Every e2e round trip waits for the page's main thread, so it costs about a frame while the viewport is drawing.** Since the viewport renders on demand (see the [rendering caveats](rendering.md)), it is idle unless something changed: behind the main menu, while a dialog is open, between steps. Measured on the same dev machine (load average about 7, 12 cores, SwiftShader WebGL2), median per call before and after on-demand rendering: `page.evaluate` 65 → 1 ms at 960 × 540 on the menu (107 → 1 ms at 1280 × 720), an `expect(locator)` matcher 59 → 2 ms, `keyboard.press` 123 → 2 ms, `locator.evaluate` 365 → 11 ms (637 → 3 ms at 1280 × 720). The whole web suite with `--workers=2` went from 1.9 min to 42 s; the console flow from 10.6 s to 3.4 s and the palette flow from 8.2 s to 1.7 s. A frame still costs 100–200 ms under SwiftShader when one is drawn (hover, held keys, a world change), and CI runners are slower again. So: (1) the web e2e default viewport stays **960 × 540** (`apps/game-e2e/playwright.config.mts`); specs where the 3D image or pixel aim is the contract (harness, viewport, placement, workshop) pin 1280 × 720 themselves. (2) **Prefer `page.evaluate` or an `expect(locator)` matcher to `locator.evaluate`**, which takes several round trips (resolve the selector to a handle, evaluate, release it). Use `expectVisibleFocus(page, locator)` and `tabTo` from `apps/game-e2e/src/support/focus.ts`. (3) **One flow per test, from a fresh page.** The F1.1 walk-through as one test took 28 s locally and hit the 30 s timeout on Windows CI before on-demand rendering. Don't raise the timeout instead. (4) **Wait on the renderer, not on time or animation frames.** A browser `requestAnimationFrame` no longer implies a render. Use the `?e2e=1` hook: `whenIdle()` once everything requested is drawn (before a screenshot or a GPU-counter read), and `afterFrames(n)` to draw n frames (to show a held movement key does nothing, `frames()` in `keybindings.spec.ts`). Poll for an effect that needs a held key (`expect.poll` on the camera position) rather than holding it for a fixed time.
- **Typing in e2e waits for a frame only when the keys change the picture.** Text fields don't, so `keyboard.type` is fast again. Keys the viewport handles (WASD while held, selection cycling) draw one frame each, 100–200 ms under SwiftShader. `keyboard.insertText` is still the better tool for long literals.
- **`pnpm e2e` reuses whatever serves port 4200**, including another worktree's dev server (`reuseExistingServer`), and Nx's `game:serve` dependency then fails with "Port 4200 is already in use". To test this checkout while another runs, serve it on another port (`pnpm exec nx run game:serve:development --port 4310`) and run `BASE_URL=http://localhost:4310 pnpm exec playwright test -c apps/game-e2e/playwright.config.mts`.
- **`workspace.layout` is opaque JSON in the schema.** `feature-workspace` owns its shape (`serialiseWorkspaceLayout` / `parseWorkspaceLayout`, a Zod-checked `{ kind: 'split-panes', version: 1, … }`). `null` or anything unrecognised gives the default layout; out-of-range sizes are clamped, not discarded.
- **The palette runs a command after it has closed.** `CommandPalette` validates, closes its `ctl-dialog`, and calls `Session.exec` from the dialog's `(closed)` output, after focus has gone back to the opener. Running first and closing second would let the dialog's focus restoration steal focus from anything the command opened (the console, F1.5). If the command is refused, the palette reopens on that command with the message. Keep that order.
- **Escape inside the palette must be handled below `ctl-dialog`.** The dialog's own `(keydown.escape)` host listener closes it, and its host is an ancestor of the palette's content, so a handler on the palette's host element runs too late. The form (`ctl-palette-arg-form` host listener) and the cheat confirmation (on each button) call `preventDefault()` + `stopPropagation()` and go back a step; only Escape in the search field reaches the dialog.
- **Validation errors never move focus while typing.** The form re-validates as the player types once a Run has failed, and an earlier version focused the first invalid field on every change, so typing `100` into X put `00` into Y. Focus moves to the first invalid field only on Run (`PaletteArgForm.focusFirstInvalid`).
- **Argument forms come from `z.toJSONSchema(args, { io: 'input' })`**, so defaulted keys are not required and defaults prefill the fields. Shapes JSON Schema can't express or the form doesn't support (arrays, unions, nullable, records, recursion, transforms) make `buildArgForm` fail, and `arg-form.spec.ts` plus `palette-arg-form.spec.ts` build and render a form for every registered command. If one fails after adding a command, extend the form model (and its specs) rather than loosening the test. Labels come from `.meta({ title })`, else the key (`positionMm` → "Position (mm)", `id` → "ID").
- **Numbers are typed as text** (`type="text"` with `inputmode`), not `type="number"`: a number input uses Up/Down to step its value (here they move between fields), and its `value` is `""` for text it can't parse, which would hide the player's typo from Zod. Text that isn't a JSON number is passed to Zod as a string, so the schema reports it.
- **Lint rejects `autofocus` and keyboard handlers on static elements** (`@angular-eslint/template/no-autofocus`, `interactive-supports-focus`). `ctl-dialog` focuses the first focusable element, so put the field you want focused first in the DOM; put keyboard handlers on the focusable control or in a component's `host` listeners.
- **Entity-reference fields read the `selection.entityId` context key** (`SELECTION_ENTITY_ID_KEY` in `@controls/commands`). Nothing publishes it yet: the viewport's selection is still the panel scene's, not world entities. When F1.7 selects world entities, it should `session.setContext(SELECTION_ENTITY_ID_KEY, id)` (and `null` when cleared); the palette then prefills Delete, Move and Rotate.
- **New sandbox opens the new-game dialog (F1.9).** `NewGameDialog` (`feature-shell`) offers a fresh seed from `SEED_SOURCE` (`crypto.getRandomValues` by default; tests provide a fixed one) and validates a typed one with `parseSeed` (decimal digits, 0…4294967295). The seed field is the dialog's first control, so `ctl-dialog` focuses it, and Enter submits because it is the form's only text field. It emits `start` from its `ctl-dialog` `(closed)` output, after focus has returned to the opener, like the palette; `App.startSandbox` then runs `Session.newSandbox({ seed, difficulty })`, clears the tool belt and focuses the canvas. E2E sessions must type seed 0 (`apps/game-e2e/src/support/sandbox.ts`), or their hashes are random.
- **The sandbox level is an injection token.** `SANDBOX_LEVEL` (`feature-session`) is the untrusted level JSON; `apps/game` provides `content/levels/workshop.json` (`provideSandboxLevel()` in `levels.ts`). Without a provider, `Session` uses an empty world, which is what most component specs get. A spec that needs the workshop (like `app.spec.ts`) must add the provider. Behind the main menu the session shows the level as it is (seed 0).

### Saving and loading (F1.8b part 3)

- **Save and load are unlogged `file.*` commands registered by `Session`**, not by `createWorldRegistry()` (ADR 0006, "Saving and loading"). `SaveGames` (`feature-saves`) performs them through `Session.onCommand`, so it must exist from start-up: `App` injects it. A component spec that presses Mod+S and expects a save must inject `SaveGames` too.
- **`SAVE_FILES` / `SAVE_DIALOGS` default to "no storage"** (every call rejects with `unavailable`; the listing fails silently). `apps/game` provides the platform's with `provideSaveIoFromPlatform()`. A spec that renders `App` and saves or loads must add that provider and give its fake `Platform` `files` and `dialogs`; `MemorySaveIo` (`@controls/feature-saves/testing`) is an in-memory directory with queued Open and Save As picks. It also registers a second flush with `APP_LIFECYCLE`, so a spec counting flushes sees two.
- **A load replaces the session only after `loadGame` succeeded**, and a dialog's choice runs after the dialog has closed and returned focus (like the palette and the new-game dialog). `SaveGames.onLoaded` then lets `App.enterGame()` clear the tool belt, show the workspace and focus the canvas, whichever surface started the load. Open file… is the exception: it calls the picker inside its click (the web harness needs the gesture) and keeps the dialog open if the player cancels.
- **Never read the session after an `await` in a save.** A New sandbox or a load can replace it while a thumbnail is captured. Take `Session.saver()` before the first `await`: it is bound to the game running then. `SaveGames` also serialises its writes.
- **"Unsaved changes" is a hash comparison per session generation**, not a log length: view commands are logged but don't change the world, and undoing back to the saved state isn't a change. An untouched New sandbox is never autosaved, so it can't push a real game out of the autosave slots. It is measured against the **save directory**, not against any file: a game opened with Open counts as unsaved until autosave copies it in, and Save As doesn't clear it. Otherwise Continue would have nothing to resume after Open or Save As.
- **Continue goes by a pointer, not by "newest"** (`settings.saves.lastPlayed`, ADR 0009). Loading a save over unsaved changes autosaves the game being left, and that autosave is then the newest file, so "newest" resumed the wrong game. Every load from the directory and every write of the **current** game sets the pointer (`markStored` checks the snapshot's generation; a write of a replaced game moves nothing); Open sets it to `null`. Keep that rule if you add a way to load or save.
- **A flush that changes settings must flush them itself.** The host runs every `APP_LIFECYCLE` flush at once, so `SettingsStore.flush` can finish before the quit autosave has set the pointer. `SaveGames.flush` autosaves, then calls `settings.flush()`. The external-file spec in `save-games.spec.ts` checks the stored pointer after a simulated quit.
- **Specs model a relaunch** with one `MemorySaveIo` and one `MemorySettingsService` across two TestBeds: run every registered flush (as the host would on quit), `resetTestingModule`, `io.relaunch()` (the next autosave takes the lowest free slot, else the oldest, like main) and set up again (`relaunch()` in `save-games.spec.ts`).
- **Returning to the menu autosaves a game with unsaved changes**, so an e2e flow that saves through the menu writes an autosave slot first (the desktop Continue test sees two slots, not one). Save with Mod+S from the workspace if a test needs exactly one autosave.
- **Continue is one button with conditional `aria-disabled`.** The save list arrives after the menu has rendered and focused its first item; swapping between two `@if` branches would destroy the element under the player's focus.
- **Load entries are named by their name span (`aria-labelledby`)** and described by the meta line (`aria-describedby`). Without the label the accessible name was the whole content ("Shop Saved game · 28 Oct … · 2.1 KB"), which Playwright's exact names and screen readers both got wrong.
- **`linkedSignal` tracks every signal its `computation` reads.** The Save game dialog resets its name when it opens; reading `session.world()` there unwrapped would also reset it on every command. Wrap such reads in `untracked`.
- **jsdom matches `<option>` text without trimming**, and Prettier moves long option content onto its own lines, so `user.selectOptions(select, '15 minutes')` fails in a spec while the browser shows "15 minutes". Select by value in specs.
- **The thumbnail is rendered and copied in one task** (`ViewportRenderer.captureThumbnail`): the drawing buffer isn't preserved, so the 2D copy must follow `render()` directly. Joint with `renderer-engineer`, like the rest of the viewport.
- **Palette scalar fields** (P2 kickoff): an argument whose JSON Schema is a union of scalar types (`anyOf` of plain `boolean`/`number`/`string` schemas, or Zod's `type: [...]` list for bare scalars) becomes a `ScalarField`: one text input typed like a console word by `scalarValue`, with a hint (`scalarHint`). Nothing else with `anyOf`/`oneOf` is accepted.
- **The sim runs in a worker; the hash and saves are asynchronous** (F2.3b, ADR 0011 §9.4). `Session.hash` and `Session.save` are gone: use `Session.hashAt()` (`SimHost.hashAt()`) and `Session.saver()`, whose `save()` and `hash()` resolve once the worker has answered for the captured tick. `Session.world()` is the commanded world after the last command: never show its `tick` or `sim` bags; read `SimHost.simTick` and snapshots. The `?e2e=1` hook's `world()` is now `busWorld()`, and `hash()` / `snapshotHash()` return promises.
- **Specs that need the sim provide a worker.** `SIM_WORKER_FACTORY` defaults to `null`, which makes the sim `unavailable` (queries reject, `prepareLoad` says `sim-unavailable`); the menu backdrop (`Session.start`) has no worker and hashes the world as it is, so most component specs need nothing. Feature specs use `FakeSimWorker` from `@controls/feature-session/testing` (the real engine on the calling thread, answering through the protocol; it can `hold`, `hang` or `crash`, and with `{ sab: true }` publishes over a `SharedArrayBuffer`); app specs use the real runner, `createInProcessSimWorker()` from `@controls/sim-worker` (features can't import it). Provide `SIM_TRANSPORT` explicitly in specs: its default reads `crossOriginIsolated`, which jsdom doesn't set.
- **`FakeSimWorker` can misbehave on purpose** (`@controls/feature-session/testing`): `failInit` (an error instead of `ready`), `silent` (never ready), `onQuery` (a crash or `hang` instead of an answer), `hold`/`release`, `hang`, `crash`; options can differ per worker (`FakeSimWorker.factory((index) => …)`). Like the runner, it answers a query below its tick with `desync`. Load specs that test a deadline use a manual `SIM_CLOCK` and fire the timer they expect, never wait.
- **Event toasts live in `SimEventToasts`** (`apps/game`), on `SIM_CLOCK`, and forget their window on every source reset (a listener gets `null`).
- **An `Atomics.waitAsync` waiter wakes on a task, not a microtask.** A spec that waits for a shared-buffer publish must yield a real task turn (`setTimeout(0)`), not only `await Promise.resolve()`. `SimLink` wakes its own parked waiter on dispose or on a replacement buffer, so none is left, and after a miss (both slots busy) it re-reads on a task, never in a microtask spin; `waitForTick` rejects when the worker is replaced or crashes; the disposal spec in `sim-host.spec.ts` checks `waitersParked`, `timersPending` and `workerCount`.
- **`SimHost` paces through `SIM_CLOCK`**, never the global clock: specs inject a fake clock and step it (`sim-host.spec.ts`'s `FakeClock`). Its signals (`simTick`, `commandedTick`, `effectiveSpeed`, `behind`) are written at most at `PANEL_SAMPLE_HZ` with a trailing sample, never at the 100 Hz pacing rate; a component reading them is redrawn at most ten times a second.
- **One `@if` block can project only one node into a slot** (Angular NG8011). Two siblings with `ctlViewportOverlay` inside `@if (!shell.menuOpen())` went to the default slot instead (the warning shows in `nx serve`, not in tests); `App` wraps the HUD and the time controls in one `<ng-container ctlViewportOverlay>`.
- **The time keys are bindings on the sim commands, not on the HUD** (`sim-args.ts`): add or change one there, and the conflict specs (`keymap.spec.ts`, `entity-commands.spec.ts`) check it against every other default. `P` toggles through two bindings on disjoint `when`s, like `V`. Number keys with Shift are positional, so `Shift+1` stays distinct from the tool belt's `1`.
- **In e2e, wait for the palette's search field before typing.** Keys typed while it opens reach the canvas, where `.` steps the sim and `p` pauses it (`time-control.spec.ts` once logged a stray `sim.step`).
- **`SimHost.simTick()` is sampled at the panel rate**: after `waitForTick(t)` it can lag the read by up to 100 ms. Poll it (`expect.poll`), or read the sim time from the HUD with a web-first assertion.
- **Toasts can carry an action** (`NotificationService.notify(message, { action: { label, commandId } })`). The app sets the runner (`setActionRunner(id => session.exec(id))`), so an action is a command through the one registry: the crash toast's **Restart simulation** runs `sim.restart`. The action button is a plain `<button>` inside the toast's live region.
- **A console-line file holds the sim** (`SimHost.hold()`) while it runs, and the console is `aria-busy` and refuses input until it ends: a `world.hash` line waits for the worker, so the next line must not run first. An interactive `world.hash` shows `world.hash: computing…`, then the hash.
- **Multi-line console queries replace their placeholder with one entry per line** (`netlist.dump`, F2.6): `netlist.dump: computing…` becomes the dump's lines in place, at the placeholder's position; the output cap (`MAX_CONSOLE_OUTPUT`) still applies.
- **The HUD's "Last solve" keys off `islandCount > 0`** (`lastSolveOf`, F2.6): a snapshot with no islands writes `lastSolveTick` 0, which is not a solve at tick 0, so it reads `None`. Never display `lastSolveTick` without that check.
- **`SimHost.select` starts from the latest snapshot** (F2.6). The sim publishes only while time runs, so a panel mounted while paused would otherwise wait for a snapshot that never comes (the netlist inspector opened after `sim.step` showed "No sim snapshot yet"). Since F2.6 `select` samples `reader.current` when it subscribes, as the generation's first sample (later snapshots inside the window trail); opened while crashed it starts `stale`, like every frozen selection. A panel that subscribes itself through `SimHost.subscribe` gets no such first call: read through `select`, or start from the latest view yourself.
- **The netlist inspector is a flat ARIA tree** (`ctl-netlist-inspector`, F2.6): every row is a `treeitem` sibling carrying `aria-level`, `aria-setsize` and `aria-posinset` (valid when the DOM doesn't nest), with a roving `tabindex`; the key handler is on each `treeitem` (lint rejects handlers on the static `ul`). Arrow keys it handles are stopped at the row, so `KeybindingService` never sees them. The focused row is the selection, and only a selected **node** highlights terminals. Rows are keyed by identity (first member, element), not index, so a new topology generation keeps expansion and selection. Its specs find rows by their `.label` text and `closest('[role="treeitem"]')`, never `getByRole('treeitem', { name })`: a row's name includes its live value, and naming every row is the slow path (above).
- **`view.netlistInspector` replaces the side panel's projected content while open** (`@if (netlistOpen()) … @else { <ng-content select="[ctlInspector]"> }`), so the app's inspector content (none yet) needs no change. It is `logged: false`, like `console.toggle`: opening a panel is UI chrome, never in a replay log, and its id is not save format.
- **`game.probe` doesn't exist in the game** (the engine runs in the worker; `Game.probe` throws `NotAvailableError`), and `type:e2e` may import no libs. An E2E that compares with a probe reads a golden that `sim-cli` pins under Node (`apps/sim-cli/src/goldens/inspector/bench-lamp-lit.json`), the same cross-runtime pattern as the `netlist.dump` goldens; re-pin with `pnpm nx test sim-cli -u`.
