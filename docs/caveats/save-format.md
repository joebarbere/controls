# Save-format caveats

**Load this when:** changing anything in `libs/domain/save-format` (schemas, migrations, fixtures, settings, JSON Schema, the `.ctrl` container), changing how `world-model` reads or writes the world, changing the device catalogue (`libs/domain/catalog`, `content/devices/`, `MODEL_KINDS`), adding or renaming a command (its id and args end up in `replay.log`), saving or loading a game (`Game.save`, `loadGame`), or when a save or settings file fails to load. Decisions: [ADR 0004](../decisions/0004-save-format.md), [ADR 0007](../decisions/0007-world-document-v1.md), [ADR 0013](../decisions/0013-world-document-v2.md) (v2). Architecture: [world and saves](../architecture/world-and-saves.md).

- **Never `.parse` untrusted JSON directly.** Use `migrateWorld` / `migrateManifest` / `migrateReplayLog` / `migrateSettings` / `loadSettings`. They pre-check two things Zod gets wrong on hostile input:
  - **Deep nesting:** Zod parses recursively, so a deeply nested file throws `RangeError` (stack overflow) out of `safeParse`. The loaders refuse documents nested deeper than 64 levels, checked iteratively first.
  - **`"__proto__"` keys:** `JSON.parse` creates `"__proto__"` as an own key, and Zod 4's `z.record` silently skips it (strict objects do report it). A key schema can't catch it, so the loaders reject it up front with `findProtoKey`.
- **`z.object` strips unknown keys silently, which loses data.** Every persisted shape is `z.strictObject`; unknown data goes in `extensions`.
- **`-0`:** `JSON.stringify(-0)` is `"0"`, so a document holding `-0` doesn't survive a round trip (and Vitest's `toStrictEqual` tells `-0` and `0` apart). Build every number from `Int` / `FiniteNumber`, which normalise with `.overwrite(n => n + 0)`. Use `.overwrite`, not `.transform`: a transform changes the input/output types and can't be expressed in `z.toJSONSchema`.
- **NaN and ±Infinity:** Zod 4's `z.number()` already rejects them (`JSON.stringify` would write `null`). `z.int()` means a _safe_ integer.
- **Unpaired surrogates** survive `JSON.stringify`/`JSON.parse`, but `TextEncoder` (UTF-8, used for the ZIP entries) replaces them with U+FFFD. Every free-text string is a `SafeString`.
- **No `.optional()` and no `.default()` in persisted schemas.** Use `null` for "absent". A test walks the exported JSON Schema and fails if any object property isn't required. Defaults belong in constructor functions (`defaultSettings()`, `createWorld()`), which can change without a version bump; the persisted shape can't.
- **Frozen means frozen.** After v0.2.0, never edit `v1/*.ts`, `settings/v1.ts`, `settings/v2.ts` or anything under `fixtures/v1/` or `fixtures/settings/v1/` and `v2/`. Shared primitives in `primitives.ts` are part of every version that uses them, so tightening one changes published versions. Add a new primitive for the new version instead. Until v0.2.0 ships, v1 may still change (F1.8b), with fixtures updated in the same PR.
- **One `schemaVersion` for the whole save.** Manifest, world and replay log bump together; a document that didn't change gets an identity step (`.then(ManifestV2, (m) => ({ ...m, schemaVersion: 2 }))`). The fixtures test requires a `fixtures/v<N>/<kind>/` directory for every kind at every version. Settings have their own `settingsVersion` and `fixtures/settings/v<N>/`.
- **Adding a version:** add `vN/<doc>.ts` (new `.meta({ id })` names with a `VN` suffix: ids are global in Zod's registry), append `.then(DocVN, step)` to the chain in `documents.ts`, repoint the `World`/`Manifest`/… aliases, bump `CURRENT_SCHEMA_VERSION`, add fixtures, add the `*.vN.schema.json` export, regenerate, and record it in [`history.md`](../history.md) and the changelog. Old migration steps stay forever.
- **Migrations must be pure.** They receive a freshly parsed copy, but the tests deep-freeze the input to prove it isn't mutated, and run each migration twice to prove it is deterministic.
- **Command ids and `args` are persisted** in `replay.log`. Renaming a command or changing its argument schema is a save-format change: bump `schemaVersion` and migrate the log entries. Command ids must match `category.verb` with camelCase segments (`view.resetLayout`). A single-segment id such as `help` can't be logged. Persisted so far: `entity.place` / `move` / `rotate` / `delete`, `edit.undo` / `redo`, `view.resetLayout`, `toolbelt.select {slot}`, and since F1.7 `view.mode {mode: 'walk' | 'work'}` and `view.focus {target}` (a lower-case hyphenated view target id, at most 64 characters). The mouse logs `entity.place` with an explicit `orientationMdeg`, so its entries match a console line that spells the orientation out. **Not persisted:** the unlogged commands `palette.open`, `console.toggle` and (F1.8b) `file.save`, `file.saveAs`, `file.open` and `file.load`. Making one of them logged later would make its id and args save format from then on.
- **`nextEntityId` is world state.** Undoing `entity.place` must restore it, or "undo everything returns the initial hash" fails. Undoing a delete must reinsert the same id, and `entities` must stay sorted by id.
- **JSON Schema files are generated** (`json-schema/*.schema.json`) and listed in `.prettierignore`, because Prettier would collapse short arrays and the staleness test would then fail. Regenerate with `pnpm nx test save-format -u`. `toMatchFileSnapshot` writes a _missing_ file locally but fails under `CI=true`, so commit the files. Zod stays authoritative: refinements (sorted ids, surrogates, nesting limits, no repeated recents) don't appear in JSON Schema.
- **Settings fall back to defaults as a whole.** One bad field (for example a 201st console history line) makes `loadSettings` discard the entire file. Writers must cap lists themselves (`MAX_CONSOLE_HISTORY`, `MAX_PALETTE_RECENTS`).
- **No timestamps in documents.** Container bytes must be deterministic, and domain code can't read the clock anyway. Use the file's mtime.
- **The determinism lint covers specs:** a test that needs a `Date` instance uses a fixed epoch with a justified `eslint-disable-next-line no-restricted-syntax`.
- **Coverage includes `src/testing/`** (the fast-check arbitraries, excluded from `tsconfig.lib.json`). Keep the helpers exercised.
- **`controls.keybindings` is keyed by binding id, not only command id** (F1.4): command ids, fixed-argument bindings (`toolbelt.select.slot3`, `view.mode.walk`, `view.mode.work`), context-argument bindings (`view.focus.selection`, `entity.delete.selection`, F1.7) and input actions (`input.moveForward`), all in the `CommandId` grammar. F1.7 retired `input.toggleMode` and `input.focusSelection`: stored overrides under those ids are now unknown, ignored by the keymap and left in the file (no settings migration). The values are canonical chords whose grammar lives in `@controls/commands` (`normaliseChord`); the schema only bounds the string (`KeyChord`, 1–64). A chord the keybinding service can't use is ignored and shown, never "repaired" on load.
- **`fixtures` is part of `WorldV1` (F1.9).** Fixture ids are strings in the view-target grammar (`^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`, at most 64), sorted strictly by UTF-16 code units (so `din-rail` < `din-rail-1` < `dinrail`), and may not start with `entity-` (reserved for entity view ids). Those rules are Zod refinements and don't appear in the JSON Schema. Adding the field changed every world's canonical JSON and so every golden hash; it was added to v1 because v1 is unpublished until v0.2.0. After that, a change to the fixture shape is a `schemaVersion` bump like any other.
- **Levels are world documents** (`content/levels/*.json`) and load through `migrateWorld` (`loadLevel` in `world-model`). `libs/domain/save-format/src/lib/levels.spec.ts` checks every level is canonical (loading changes nothing), lossless, at tick 0, not assisted, and has fixtures. Keep level files in canonical form, or that test fails; Prettier formats them like any JSON.

### The `.ctrl` container (F1.8b)

Never feed untrusted bytes to anything but `readCtrl` (or `loadGame`, which calls it). It never throws and returns a typed `CtrlError` whose messages never echo content.

- **Don't use fflate's `zipSync` / `unzipSync`.** `zipSync` stamps each entry with a DOS date computed in the _local time zone_ (`getHours()` …), so the same save gets different bytes on different machines. `unzipSync` allocates whatever uncompressed size the header claims and inflates in one go, so a hostile header or a zip bomb costs memory before any check runs. `container/zip.ts` writes and parses the archive itself (a strict subset: stored or DEFLATE, no encryption, no ZIP64, one disk, ASCII names) and uses fflate only for `deflateSync` and the streaming `Inflate`.
- **Inflation is checked as it grows.** Compressed data goes to the inflater in 4 KiB slices, and extraction aborts as soon as the output passes the entry's _declared_ size; the declared sizes are capped (per entry and in total) before anything is inflated. A finished entry must match its declared size and CRC-32 exactly. So the real total is bounded by the declared total, and a bomb is refused after at most a few MiB of output.
- **The manifest is read before the entry list is judged.** A later `schemaVersion` may add entries (files under `prints/`, `plc/`, `hmi/`), and a v1 build must answer `newer-than-build`, not `unexpected-entry`. Structure, names (traversal), counts and declared sizes are checked first, since they're version-independent. When a version adds entries, make the allowed layout depend on the manifest's version (`isV1Entry` today).
- **Caps** (`CTRL_LIMITS`): container 48 MiB, total uncompressed 48 MiB, `world.json` 16 MiB, `replay.log` 32 MiB, `thumbnail.png` 4 MiB, `manifest.json` 64 KiB, 64 entries. P1 worlds are a few KiB; a late-game plant of ~10k entities at ~300 bytes each is ~3 MiB, so 16 MiB is ample headroom. A log entry is ~150 bytes, so 32 MiB holds ~200k commands. The caps aren't schema: raising one needs no version bump, but an older build refuses saves over its own caps, so raise them before saves can grow past them. `readCtrl(bytes, { limits })` can only _lower_ them (for an IPC payload cap). `writeCtrl` applies the same caps, so the game never writes a save it would refuse. Any IPC or storage size cap for saves must be at least `CTRL_LIMITS.maxContainerBytes`.
- **Container bytes are deterministic, but they include `appVersion`.** Entries sorted by name, DOS time 1980-01-01 00:00, no extra fields or comments, DEFLATE level 6 / mem 12, the PNG stored, and JSON written by `ctrlJson` (keys sorted, two-space indent, final newline). The golden SHA-256 in `ctrl.spec.ts` uses fixture documents, not `createManifest()`, because a version bump changes `APP_VERSION` and so every new save's bytes (never `world.hash`). Re-pin the golden only for a deliberate change to the writer, the JSON formatting or fflate's DEFLATE output (a fflate upgrade can move it), and say so in the changelog. Old saves load either way.
- **`ctrlJson` key order:** keys are sorted, but JavaScript always lists integer-like keys (`"1"`, `"20"`) first in numeric order, so `JSON.stringify` can't follow a pure code-unit sort for them. The output is still a pure function of the document, which is what determinism needs; the world hash uses its own canonical JSON (`world-model`).
- **No `TextEncoder` / `TextDecoder` in domain code** (they aren't ECMAScript globals, and the domain tsconfig has no DOM lib). `container/utf8.ts` encodes strictly (throws on an unpaired surrogate) and decodes strictly: overlong forms, encoded surrogates, truncated sequences and a byte-order mark make the entry `not-utf8`, never U+FFFD.
- **`writeCtrl` writes current-version documents only.** It validates each through its migrator (so the depth and `__proto__` pre-checks apply) and refuses one at an older version; migrate first.
- **One `schemaVersion` per save, checked across entries.** A `world.json` or `replay.log` whose `schemaVersion` differs from the manifest's is `version-mismatch`, even if each would migrate on its own.
- **`.ctrl` fixtures are binary and frozen** (`fixtures/v<N>/ctrl/*.ctrl`, `*.ctrl binary` in `.gitattributes`). The fixtures test requires at least one per version. Make new ones with `pnpm sim run <scenario> --world … --save <file>` or `writeCtrl`; never regenerate an existing one, even when the golden moves.
- **Loading a save keeps the world, and keeps the log only if it reproduces the world** (`loadGame` in `@controls/scripting-api`). The log is replayed from its `initialWorld`; if it fails, or reaches a different `world.hash` than `world.json`, the world still loads and a new log starts from it (`replay.status: 'restarted'`, for a notification). The undo stack is cleared (`CommandBus.clearHistory`) and the log continues with the next `seq`. Replay stays exact because the live undo/redo stacks are always the top part of what a full replay rebuilds (property-tested in `bus.spec.ts` and `save.spec.ts`).
- **The game loads through `loadGame(bytes, { registry: session.registry })` and `Session.adopt`** (F1.8b part 3). Pass the session's registry: it holds the host's `file.*` commands as well as the world's, and `adopt` refuses a game on any other registry. A restarted log is a warning by default; `REPLAY_MISMATCH_POLICY` (`feature-saves`) switches it to a refusal.
- **Player-facing load errors are written from `CtrlError.kind` and `SaveIoError.code` only** (`feature-saves` `messages.ts`), never from `error.message`: some messages quote an entry name from the file (`unexpected-entry`) or a version string. When adding a `CtrlError` kind, add it to `loadErrorReason` (the `switch` is exhaustive, so `typecheck` fails until you do).
- **Autosave settings are F1.8a's `autosave { enabled, slotCount, intervalSeconds }`**, unchanged: F1.8b part 3 only started using them. The interval's schema floor (60 s) is also what keeps autosave from writing on every command.
- **`settingsVersion` 2 adds `saves.lastPlayed`** (Continue's pointer, ADR 0009): `{ kind: 'manual', name }` (a bounded `SafeString`, 1–255, not the platform's save-name grammar), `{ kind: 'autosave', slot }` (1–10, `slotCount`'s range) or `null`. It is a reference resolved against a fresh listing, **never a handle or a path** (handles die with the window). Build it with `lastPlayedOf(entry)` (`feature-saves`), which runs `LastPlayedSave.safeParse` and gives `null` for anything the schema refuses: an invalid pointer would make `settings:set` refuse the whole document. v1 was still unpublished (v0.1.0 had no settings) but was bumped rather than edited, so settings written since F1.1 keep loading; the v1 → v2 step adds `lastPlayed: null`. Specs that need a settings version newer than the build use 99, not `CURRENT_SETTINGS_VERSION + 1` literals.

### The device catalogue (P2 kickoff, catalogue v1)

Saves reference catalogue entries by `{ id, version }` (ADR 0004), so the catalogue's ids, versions and model kinds are part of what an old save means.

- **`content/devices/*.json` is authoritative, and `builtin-devices.generated.ts` mirrors it.** Domain code can't import `content/` (`type:content` is data for apps), and the catalogue must resolve the same way in the game, the sim worker and `sim-cli`, so `@controls/catalog` bundles a generated copy. `builtin.spec.ts` regenerates it and fails when it is stale: after editing a device file run `pnpm nx test catalog -u` and commit both. The mirror is in `.prettierignore` (Prettier would reformat it and the staleness test would then fail). Files are named `<id>.v<version>.json`, and a test checks the names.
- **State keys are save format; parameters are catalogue data.** Adding a model kind to `MODEL_KINDS` needs no `schemaVersion` bump. Changing an existing kind's state keys (adding, removing, renaming or narrowing one, or changing its owner) does, with a migration of every save's bags, and `json-schema/device-state.<kind>.schema.json` changes with it. Changing a kind's parameter schema or an entry's values changes the catalogue (`catalogVersion`, or the entry's `version` if old saves must keep the old values), never the save.
- **Catalogue v1 can still change until v0.3.0 ships**, like `schemaVersion` 1 before v0.2.0: the P2 device-model PRs (F2.4, F2.5) finalise the provisional parameters and keys of their kinds. From v0.3.0 it is frozen.
- **Every number needs a source, and loading checks it.** `parseCatalog` refuses an entry whose `model.params` key, `sizeMm` or terminal layout isn't covered by a `sources[].covers` path, or a source that covers something the entry lacks. `game-design` sources say so in their citation. Brands are fictional, and lead resistance comes from resistivity, length and area (`leadResistanceOhm`), never from NEC (or any) conductor tables; a gauge's area comes from the AWG diameter formula. `leadResistanceOhm`'s linear α model holds over about −50 to +150 °C and doesn't clamp: callers clamp the conductor temperature.
- **`prop.*` is reserved for the built-in props** (`BUILTIN_PROPS` in `world-model`, D4); catalogue ids starting with `prop.` are refused.
- **A control is a commanded state key.** `controls[].id` must name a `commanded` key of the entry's kind, of a matching type (toggle ↔ boolean, setpoint ↔ number, selector ↔ enum). `checkControlValue` is what `device.operate` checks against.
- **Model-kind lookups use own properties** (`modelKind`, `parseCatalog`), so `toString` or `__proto__` is never a kind.

### World v2 (P2 kickoff, ADR 0013)

- **`schemaVersion` 2 is current; v1 is frozen.** v2 may still change until v0.3.0 ships (fixtures updated in the same PR), then it is frozen too. `v2/from-v1.ts` holds the v1 → v2 steps forever. v2 reuses v1's fixture and transform schemas, so their JSON Schema `$defs` keep their `V1` names.
- **Two bags per entity, two owners.** `state` is written only by commands; `sim` only by `materialiseWorld` (ADR 0011 §1). A world change must keep every surviving entity's `sim` bag (the same object), the solution record and `tick`: `properties.spec.ts` in `world-model` checks it. A change that rebuilt an entity from scratch, or captured and restored a whole world, would break save-and-load parity once time passes.
- **The world schema checks only the bags' generic shape** (`DeviceStateBag`: lower camelCase keys, at most 64; finite numbers, booleans, strings of at most 32, `null`). The keys of each device kind are checked at load by `checkWorldDevices` against `MODEL_KINDS` (`invalid-device-state`), because the schema can't see the catalogue. A ref the catalogue doesn't know keeps its bags untouched; a built-in prop must have empty ones.
- **Every key is present; absent is `null`.** `initialBags(kind)` gives a new device every key at its initial value; never write a bag with a key missing.
- **Connection ids follow entity ids' rule with their own counter** (`nextConnectionId`): undoing a connect restores the counter, undoing a disconnect or a delete reinserts the same id. `entity.delete` removes the entity's connections in the same change. The schema refuses a connection to an entity that doesn't exist or from a terminal to itself.
- **`WorldV2.sim` is hashed.** The solution record is in `world.hash` (U3), and its numbers must survive JSON under `Object.is` (`-0` is normalised; subnormals and 17-digit floats survive). Its lengths are checked against the netlist by the engine at start, not by the schema (`fixtures/v2/start-failed/`).
- **`ReplayLogV2.firstSeq` and `endTick`:** `entries[i].seq === firstSeq + i` and `endTick ≥ last entry tick ≥ initialWorld.tick` (refused otherwise, `fixtures/v2/refused/`). `createReplayLog(world, entries, { firstSeq, endTick })` defaults `endTick` to the last entry's tick. A bus continuing a log must start at its `firstSeq` (`createWorldBus(world, registry, { firstSeq })`), or replay reports `out-of-order`.
- **`createManifest` needs the catalogue and engine versions** (`{ catalogVersion, simEngineVersion }`); save-format can't import `@controls/catalog` or `@controls/sim-core` (they depend on it). Use `createSaveManifest()` from `@controls/scripting-api` for a save this build writes. A migrated v1 manifest has `catalogVersion` 0 and `simEngineVersion` 0 ("before the catalogue and the engine").
- **A migrated P1 world can be refused** if one of its entities used a catalogue v1 id (only possible by typing it in the P1 console): it migrates with empty bags, which the load check refuses. The migration can't read the catalogue to fill them.
- **Fixture layout:** `fixtures/v2/{world,manifest,replay-log,ctrl}/` load; `fixtures/v2/refused/<kind>/` must be refused by the loader; `fixtures/v2/start-failed/<kind>/` are valid documents the engine must refuse at start (F2.3a's test). The fixtures test ignores the last two when it walks the kinds.
- **`replay.log`'s `endTick` must equal `world.json`'s `tick`** (ADR 0013): `readCtrl` refuses a container where they differ (`end-tick-mismatch`, a damaged save) and `writeCtrl` refuses to write one. Take both at the same tick (`Game.save`, `Session.saver()`); a test that pairs an arbitrary world with an arbitrary log must align them.
