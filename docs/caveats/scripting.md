# Scripting caveats

**Load this when:** working on `libs/domain/scripting-api`, the console-line parser in `libs/domain/commands/src/lib/console/`, `apps/sim-cli` or its scenarios, writing a scenario script, or changing a command's args shape. Decisions: [ADR 0008](../decisions/0008-console-and-scripts.md). Architecture: [scripting](../architecture/scripting.md). How-to: [scripting guide](../guides/scripting.md).

- **Args key order is console grammar.** Positional console words fill a command's args keys in declaration order (`entity.delete 3` → `{ id: 3 }`). Reordering the keys of an args `z.strictObject` silently changes what existing `.console` files mean (replay logs are unaffected). Treat it as a breaking change with a CHANGELOG line.
- **The console mapping types words; Zod validates them.** `consoleArgs` only decides number versus string versus boolean from the leaf schema and rejects unknown flags with a column. Bounds and required fields come from `exec`. Don't add validation to the mapping, or the console and the palette will disagree.
- **New Zod wrapper kinds need a look at `unwrap()`** in `console/args.ts` (it strips optional, default, prefault, nullable, readonly, catch, nonoptional and pipe input). An unrecognised wrapper falls back to the word's lexical type, which may turn `"12"` into a number for a string field.
- **Arrays have no console syntax.** `formatConsoleLine` throws `ConsoleFormatError` for arrays and empty objects, so `toConsoleScript` throws for a log containing one. The first command with an array arg must extend the grammar (ADR 0008).
- **`Game.world()` snapshots are deep-frozen, in place.** `createGame({ world })` freezes the world you pass (it keeps the object, so `Session.world()` is still that object), and every later state is frozen as it's committed. Code that mutated a world document worked by accident before; now it throws in strict mode. Copy first.
- **`Session` must not touch the bus.** It drives a `Game` (`createGame`, `game.on('executed')`); don't reach past it to a `CommandBus`, or the UI and scripts stop running identical code.
- **The renderer never loads scripts.** Only `apps/sim-cli` bundles and imports TypeScript, with esbuild, in Node. Never add a loader to a library or the game, and never relax the CSP's eval ban to run one. In-game, `run <file>` takes console-line files only.
- **esbuild is a run-time dependency of `sim-cli` only**, loaded with `import('esbuild')` when a module script runs and kept external in the bundle. `replay`, `hash` and console-line runs must keep working without it.
- **Script imports are allow-listed** (relative, `type:domain` aliases read from `tsconfig.base.json`, `zod`). A new domain lib is allowed automatically once its path is in `tsconfig.base.json` under `libs/domain/`. `@controls/save-format/testing` is allowed but needs fast-check, which isn't, so it fails to bundle. The check applies to imports made by the script's own files: imports made by a domain lib's production source (`libs/domain/*/src`, not `src/testing/`) or from inside `node_modules` pass, because the `type:domain` lint already bounds them. That's how `@controls/save-format` brings fflate in (F1.8b) while `import 'fflate'` in a script is still refused.
- **`pnpm sim` rebuilds the bundle each time** (`bin/sim.mjs`) instead of going through Nx, so stdout stays data-only. Use `pnpm --silent sim …` to also drop pnpm's script banner when piping.
- **Relative paths resolve against `INIT_CWD`**, the directory `pnpm sim` was typed in, not the repository root pnpm switches to.
- **The palette scenario hash is pinned too** (`PALETTE_PLACE_UNDO_HASH` in `apps/sim-cli/src/palette-place-undo.spec.ts` and `apps/game-e2e/src/palette.spec.ts`). `scenarios/palette-place-undo.console` must list exactly the logged commands the palette e2e runs (the e2e compares its replay log's ids with the file); `palette.open` is unlogged, so it isn't in either. Change the file, both literals and the e2e steps together.
- **The four-surface hash is pinned** (`FOUR_SURFACE_HASH` in `apps/sim-cli/src/four-surface.spec.ts`). It changes only if the scenario, a command's semantics or the world hash changes; the game-e2e drivers (F1.3, F1.5, F1.7) must assert the same value, so change them together. `apps/game-e2e/src/console.spec.ts` runs `four-surface.console` through the in-game console's `run` and asserts it.
- **The phase-acceptance hash is pinned** (`PHASE_ACCEPTANCE_HASH` in `apps/sim-cli/src/phase-acceptance.spec.ts` and `apps/game-e2e/src/phase-acceptance.spec.ts`). The mouse, palette and console drivers each assert it and that their log has exactly `scenarios/phase-acceptance.console`'s command ids, so a driver step, the file and both literals change together. The palette driver presses Enter in the last field it types: ArrowDown past the last field reaches the form's Back button, and an entity id field is a combobox (a text field with the world's entities as suggestions), not a textbox.
- **The console place-then-undo hash is pinned too** (`CONSOLE_PLACE_UNDO_HASH` in `apps/sim-cli/src/console-place-undo.spec.ts`, for `scenarios/console-place-undo.console`: one place, then undo). Undoing the place restores the world exactly, so it equals the empty seed-0 world's hash. `apps/game-e2e/src/console.spec.ts` types those lines and asserts the literal, and also types the lines of F1.3's `palette-place-undo.console` from a fresh session and asserts `PALETTE_PLACE_UNDO_HASH`: the direct console-versus-palette cross-check. Change the literals in both e2e files and the sim-cli specs together.
- **`consoleFields` shares `unwrap()` with `consoleArgs`** (`console/args.ts`), so completion and `help` offer exactly the flags the mapping accepts. Change both together, and keep the spec that maps every listed field.
- **`sim-cli`'s `test` target depends on `build`** and lists the root `eslint.config.mjs`, `tsconfig.base.json` and every `apps/*/project.json` and `libs/**/project.json` as inputs (the boundary and determinism lint tests lint probe files with the real config and the project graph's tags, and the script loader reads the aliases). Keep them, or Nx can replay a stale pass.
- **`sim bench` is the performance gate** (P2 kickoff step 6; F2.7 fills it). Cases live in `apps/sim-cli/src/bench/cases.ts`: each has a warm-up count, a run count, an optional `budgetMs` (checked against the median) and a `run()` returning a checksum that must be the same on every run. Output is a JSON report on stdout (`{ cases: [...], ok }`, with each case's median and margin); exit 1 if any case is over budget or not deterministic. The Nx `bench` target (`dependsOn: build`, uncached) runs `dist/apps/sim-cli/main.mjs bench`, so timings are never taken under Vitest's coverage instrumentation. `src/bench/clock.ts` is the only file in sim-cli exempt from the determinism lint; everything else takes the clock as a parameter (`CliIo.now`), so `bench.spec.ts` drives budgets with a fake clock. **`sim bench --smoke`** proves every case runs, not how fast: 3 timed runs each, no warm-up, the invariants in their smoke form (the snapshot-read allocation probe at 5,000-read windows, 3 of each size), determinism and invariants gated, budgets reported but never failing it, and `"smoke": true` in the report. `bench.spec.ts`'s from-the-bundle test spawns it (about 4 s locally, against about 13 s for the full bench), so the suite doesn't re-measure what the Nx `bench` target measures: the full run took the spawn's whole 30 s timeout on CI's Windows runner (#66). The Nx target never smokes; never use `--smoke` as a gate. What a smoke run still costs is mostly fixed set-up (the per-tick case's 750-device world, the probe's 20,000-read warm-up), not iterations.
- **The determinism lint covers `apps/sim-cli`** (including `scenarios/`), not just `libs/domain/`. A scenario that reads the clock can't be re-run to the same hash.
- **Scenarios start from the workshop level (F1.9).** Every `apps/sim-cli/scenarios/*` file and its spec runs with `--world content/levels/workshop.json` (in-process: `createGame({ world: workshopWorld() })` from `src/testing/workshop.ts`), because New sandbox with seed 0 starts from exactly that world, so the game-e2e drivers and the headless drivers share golden hashes. `CONSOLE_PLACE_UNDO_HASH` therefore equals the workshop's own hash (`WORKSHOP_HASH`, pinned by `src/workshop.spec.ts`, which also runs `sim hash content/levels/workshop.json`). A level edit moves every scenario golden: re-pin them all, in sim-cli and game-e2e, together.
- **`--world <file> --seed N`** starts a new game on that level with seed N (`newGameWorld`, what New sandbox does); `--world` alone runs the document as it is, and `--seed` alone seeds an empty world. Before F1.9 the two flags were mutually exclusive. `--world <save.ctrl>` loads the save as the game does (`gameFromSave`: undo cleared, its replay log continued, or restarted with a warning on stderr); with `--seed N` it's a new game on the save's world.
- **`.ctrl` is recognised by extension or by the ZIP signature** (`looksLikeZip`), so a renamed save still reads as one; everything else is JSON, told apart by content. `sim hash <save>` hashes `world.json`; `sim replay <save>` replays `replay.log` from its `initialWorld` and fails unless the result hashes like `world.json` (a save without a log fails: use `hash`). `sim run --save <file>` writes the session with `Game.save()`.
- **Don't pin a golden of `sim run --save` output.** Its manifest holds `APP_VERSION`, so the bytes change with every release (the hash doesn't). The container's golden lives in `save-format` with a fixed manifest.
- **Scripts snap against `worldSnapTargets(game.world())`**, the world they were given, not a fixed table. The pre-F1.9 `demoPanelSnapTargets()` is gone.
- **World v2 re-pinned every scenario golden once** (ADR 0013): every world now serialises `connections`, `nextConnectionId` and `sim`. The `.ctrl` fixtures of the four-surface scenario exist at both versions (`fixtures/v1/ctrl/` and `fixtures/v2/ctrl/workshop-four-surface.ctrl`), and both replay to `FOUR_SURFACE_HASH` (`four-surface.spec.ts` 5b): a migrated P1 save reaches the same world as a fresh v2 run.
- **`sim run --world <save.ctrl>` fails on `invalid-device-state`** (a save whose device bags or leads don't match the catalogue), like the game's Load.
- **The bench-leads hash is pinned** (`BENCH_LEADS_HASH` in `apps/sim-cli/src/bench-leads.spec.ts` and `apps/game-e2e/src/console.spec.ts`, for `scenarios/bench-leads.{console,ts}`: three devices, three test leads, `device.operate` with undo). Since engine 5 (F2.5) it is `562b5681ff82adb4b1576f63cefe8fc1bdbd0f50ba32598ec5b3e9c05d952d26`: the lamp is modelled, so its island is solved. The spec also checks the console file logs exactly the script's entries, and that `fixtures/v2/ctrl/bench-leads-engine-3.ctrl` (written by `sim run … --save`, still hashing to engine 3's `b2124245…`) replays to the new hash, so `sim replay` on it fails naming engines 3 and 5. Change the files, both literals and the fixture together (a new fixture, never a regenerated one); `fixtures/v2/ctrl/sim-step-engine-3.ctrl` is the sim-step scenario's save at tick 1234 from engine 3, `sim-step-engine-4.ctrl` engine 4's (both now loaded as `engine-changed`) and `sim-step-engine-5.ctrl` engine 5's, all checked by `sim-step.spec.ts`; `sources-engine-4.ctrl` and `sources-engine-5.ctrl` are the sources scenario's (`sources.spec.ts`), `bench-lamp-engine-5.ctrl` the bench-lamp scenario's and `protection-engine-5.ctrl` the protection scenario's (`protection.spec.ts`). Each was written with `pnpm sim run apps/sim-cli/scenarios/<scenario>.console --world content/levels/workshop.json --save libs/domain/save-format/fixtures/v2/ctrl/<scenario>-engine-<N>.ctrl`. F2.3a re-pinned it (`1825e8ba…` → `b2124245…`) because the hash now covers the materialised solution record; the engine-1 fixture `bench-leads.ctrl` still hashes to the old value, and `sim replay` on it fails, naming both engine versions (D8).
- **The sim-step hashes are pinned in Node and Chromium** (`SIM_STEP_HASH` `e065dd0a3e81636b487a7c49514f4276a7ae70fe146cdf33d1f5cdecb0c74648` and `SIM_STEP_SNAPSHOT_HASH` `eddf0d39a957c7c0f11d95a7f061a26640d747df153c065c8ac33ba0b7c966c7` since engine 5, in `apps/sim-cli/src/sim-step.spec.ts` and `apps/game-e2e/src/sim-engine.spec.ts`, for `scenarios/sim-step.console`: a battery shorted through two leads by a switch, an unwired lamp, `sim.step 1234`). The game-e2e test runs the file through the in-game console's `run`, with the engine in the page, so a difference between the two is float drift between Node's and Chromium's V8, not a golden to re-pin. Change both files together, and a numeric change also bumps `SIM_ENGINE_VERSION`. It was the D6 golden until F2.5 moved that to the bench lamp.
- **The bench-lamp hashes are the D6 cross-runtime golden** (F2.5): `BENCH_LAMP_LIT_HASH` `ed42d957348f2c2f79aad6ed892228a20e59bb543ba3e348399595c37d7b3fbc` and `BENCH_LAMP_LIT_SNAPSHOT_HASH` `52010da7436ce267029b58a73aadc43c6e3ddb4ca0db17f1c3a3bf695b9fd517` (after the switch is closed and 1.5 s pass), `BENCH_LAMP_HASH` `0b533c942486866c3d8757b94dfdb6c2d891f66ae0401f97a96aac4d1ea6cb28` and `BENCH_LAMP_SNAPSHOT_HASH` `d5bbbaaf731e59d67fd7a1e459504f9198a7d5d563d0ef0f1a52cb7e010ac11f` (after it is opened and 0.5 s pass), in `apps/sim-cli/src/bench-lamp.spec.ts` and `apps/game-e2e/src/bench-lamp.spec.ts`, for `scenarios/bench-lamp.{console,ts}`. The e2e types the console file's place and lead lines, closes the switch with E and opens it with a double-click, and steps time from the console: every action is one logged command, the same ones the file runs. It runs over both transports (the shared buffer and `?sab=0`), the engine in the sim worker, and reads the hashes through the async `hash()`/`snapshotHash()` hooks after `waitForTick`. The lamp's filament ODE runs every tick, so this is where Node's and Chromium's V8 would first disagree. Change the scenario files, the spec, the e2e and these literals together.
- **The protection hashes are pinned** (F2.5 part 2): `PROTECTION_HASH` `ecbabf42dd94bc78853ca50cf0d6d62221dbfdb6b06a8967283ca4af0a9566bc` and `PROTECTION_SNAPSHOT_HASH` `5054a1b4127ba47e9894c1c6f184ade2789ea3ab0ccc228b35c9bc4fd444144e` in `apps/sim-cli/src/protection.spec.ts`, for `scenarios/protection.console`: three batteries on the workshop bench, one through a fuse into the heater (the fuse blows), one through a second fuse into the resistor (part-melted after 2.5 s) and one shorted through the breaker (it trips), then `sim.step 2500`. The spec also checks that `fixtures/v2/ctrl/protection-engine-5.ctrl` loads as `continued` at the same hashes and runs on into the same future. Node only (no game-e2e twin). Change the scenario, the spec, the fixture (a new one, never regenerated in place) and these literals together; a numeric change also bumps `SIM_ENGINE_VERSION`.
- **`game.device(id)` decodes a record on every call** (F2.5, `SimEngine.deviceRecord`, through `sim-protocol`'s `decodeDeviceRecord`): it allocates, so call it from a script or test, never inside a per-tick loop you are measuring. It needs the in-process engine (headless); the game has none on the main thread, and reads records from the worker's snapshot instead. Its `values.status` must be `solved` before a field is a reading.
- **`sim replay` on a save from another engine fails, saying why on every failure** (the versions, `ENGINE_CHANGED_MESSAGE`, and the hint to `sim run <empty.console> --world <save>` to load it as the game does, or `sim hash <save>`). Loading (`sim run --world`) never verifies such a save, nor one whose log spans more than `MAX_VERIFY_TICKS`; `sim replay` replays any length, because replaying is what it was asked to do.
- **`runConsoleScript` is asynchronous everywhere** (F2.3b, ADR 0011 §9.4): it returns a promise, and a `world.hash` line awaits the target's `hash()` (a string headless, a promise in the game) before the next line runs. Await it in specs and in `sim-cli`; `expect(await runConsoleScript(...)).toMatchObject(...)`, and `(await runConsoleScript(...)).ok`, not `await runConsoleScript(...).ok`.
- **A console file steps time with `sim.step`** (F2.3a): headless and in the game the time host advances right after the line is logged, so the next line is stamped at the new tick. A file's `world.hash` line after a step covers the solve at the last cadence tick before it.
- **`netlist.dump` is a console query, not a command** (F2.6): `CONSOLE_QUERIES` holds it beside `world.hash`, and a registered command with the same id wins over it. A query prints one output line per text line (`runConsoleQuery`), so a `.console` file with a `netlist.dump` line prints many lines on `sim run`'s stdout: a spec that reads stdout must expect them. `ConsoleTarget` now needs `netlistDump()` as well as `hash()`.
